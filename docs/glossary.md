# 용어

이 문서에 있는 말만 쓴다. 같은 것을 두 이름으로 부르면 읽는 사람이 다른
것으로 읽는다. 실제로 그랬다 — 「프로 존재감」과 「대회 존재감」이 같은 값인데
문서마다 다르게 적혀 있었다.

새 말이 필요하면 **여기에 먼저 적고** 쓴다.

## 데이터

| 용어 | 뜻 |
| --- | --- |
| **솔랭 지표** | u.gg 아카이브의 승률·픽률·밴율. 범위는 `world` · `emerald_plus` 다 |
| **프로 경기** | Oracle's Elixir 의 프로 경기 기록(29,977경기 · 72패치). **리그 정규시즌이 대부분이고 대회는 일부다** |
| **프로 픽·밴율** | 한 패치에서 그 챔피언이 프로 경기에 나온 비율 — **픽률 + 밴율.** 코드의 `pro_presence` 다. **1.0 을 넘을 수 있다** — 양 팀이 같은 챔피언을 뽑는 형식이 있다 |
| **대조군** | 그 패치에 조정되지 않은 챔피언 |
| **모집단** | 지표를 잰 플레이어 집단. u.gg 는 `emerald_plus`, 프로 경기는 상위 리그다. 개발사는 넷(Average · Skilled · Elite · 프로)을 따로 본다. **다른 모집단의 값을 한 시계열에 잇지 않는다** |
| **공개 밸런스 기준** | 개발사가 공개한 판정 방식 — 모집단 넷과 각각의 문턱, 그리고 버프 편중 안전장치. 2019·2020년 문서이고 **지금도 이대로인지는 모른다.** 주소는 [data-sources](spec/data-sources.md#6-공개-밸런스-기준--개발사가-적어-둔-문턱) · [측정](results/README.md#개발사가-공개한-기준-2026-09-01) |

「대회」는 국제 대회·정규시즌 같은 실제 대회를 가리킬 때만 쓴다. 데이터
출처를 가리킬 때는 **「프로 경기」**다 — 우리 데이터의 대부분이 리그 정규시즌
이라 「대회」로 부르면 틀린 말이 된다.

## 챔피언 분류

| 용어 | 뜻 |
| --- | --- |
| **통산 픽·밴율** | 그 챔피언이 나온 **모든 패치의 프로 픽·밴율 평균**. 한 패치만 튀는 것과 늘 나오는 것을 가르려고 쓴다 |
| **프로 경기에 자주 나오는 챔피언** | 통산 픽·밴율이 **상위 25%(0.182 이상)**인 챔피언. 42종이다. 표에서는 **「자주 나오는 챔피언」**으로 줄여 쓴다 |

「프로형」은 쓰지 않는다. 「-형」은 만든 말이고 기준이 안 보인다.

## 조정 분류

| 용어 | 뜻 |
| --- | --- |
| **높은 쪽 너프** | 조정 직전 프로 픽·밴율이 **중앙값 위**인 너프 |
| **낮은 쪽 너프** | 중앙값 **아래**인 너프 |

「프로발 너프」·「솔랭발 너프」는 쓰지 않는다. 만든 말이고, 「무엇 때문에
너프했나」를 아는 것처럼 들린다 — **우리는 그것을 모른다.** 아는 것은 프로
픽·밴율이 높았다는 사실뿐이다.

## 분석 범위

| 용어 | 뜻 |
| --- | --- |
| **본 분석** | **공개 데이터**를 쓰는 arm 들 — 솔랭 승률·픽률·밴율과 프로 경기 픽·밴. 한때 솔랭만이었다([ADR 0008](adr/0008-pro-play-in-the-main-analysis.md)) |
| **프로 픽·밴** | 프로 경기에서의 픽률 + 밴율. 두 값을 더한 것이라 1.0 을 넘을 수 있다 |
| **솔랭만** | 프로 피처를 뺀 arm(`A7`·`A7h`·`B5`). 「프로를 넣으면 얼마나 오르나」를 같은 표에서 읽으려고 남겨 둔다 |

「본선」은 쓰지 않는다. 대회 용어다.

## 측정

| 용어 | 뜻 |
| --- | --- |
| **arm** | 비교하는 예측 방법 하나. `A…` 는 ① 대상, `B…` 는 ② 방향이다 — [번호 규칙](#arm-번호) |
| **줄 세우기** | 패치 안에서 챔피언을 점수순으로 정렬하는 것. **R-정확도와 AUC 가 재는 것이 이것이다** |
| **R-정확도** | 한 패치에서 **실제로 조정된 수만큼** 위에서 뽑아 맞힌 비율. 조정이 15종이면 상위 15종을 보고 몇이 맞는지 센다 |
| **AUC** | 아무 「너프된 챔피언」과 아무 「버프된 챔피언」을 뽑았을 때 **너프 쪽에 더 높은 점수를 줄 확률**. 1.0 이 완벽, 0.5 가 찍기 |
| **P@k** | 상위 `k` 종 중 맞은 비율. R-정확도와 달리 `k` 를 우리가 정한다 |
| **기준선** | 아무 지식 없이 찍었을 때의 값. ① 은 조정률(15.0%), ② 는 다수 클래스(51.0%) |
| **배수** | 성적 ÷ 기준선. **기준선이 다른 줄은 배수로만 비교한다** |
| **해상도** | 한 arm 이 내는 **서로 다른 점수의 가짓수**. 낮으면 같은 점수가 뭉쳐 줄 세우기가 안 된다 |
| **의도대로** | 너프 뒤 승률이 내려갔거나 버프 뒤 올라간 비율 |
| **균형 접근** | 조정 뒤 \|승률 − 50%\| 가 **줄어든** 비율. **성패가 아니다** — 아래 참조 |

「계기판」은 쓰지 않는다. 비유이고, 라이엇이 무엇을 보는지 아는 것처럼
들린다. **「지표」로 쓰고, 둘이 안 맞을 때는 「어긋난다」로 쓴다.**

#### AUC 를 읽을 때 걸린 것 셋

0.5 아래도 뜻이 있다 — 뒤집혔다는 뜻이다. 승률 높은 순으로 조정 대상을 줄
세우면 `A0c` 가 **0.448** 로 무작위보다 나쁘다. 조정되는 쪽이 양 끝이라 한 방향
줄 세우기가 거꾸로 간다. 거리(`wr_gap`)로 바꾸면 0.569 로 뒤집힌다.

AUC 는 「맞혔나」가 아니라 「줄을 잘 세웠나」다. `B4` 규칙이 한때 0.807 이었는데
점수 종류가 **5개**뿐이었다 — 5칸에 몰아넣으면 칸 안에 순서가 없다. 규칙을 안
바꾸고 점수 내는 방식만 고쳐 19종으로 늘리니 0.837 이 됐다.

절대값보다 기준선과의 거리를 본다. 0.900 이 좋아 보여도 「승률만 봐도
0.796」이 먼저다. 그래서 표에 기준선을 항상 같이 적는다.

### arm 번호

같은 번호는 두 과제에서 같은 방법을 뜻한다.

| | ① 대상 | ② 방향 | |
| --- | --- | --- | --- |
| `0` | `A0`… | `B0`… | 기준선 — 무작위·단일 지표 순 |
| `1`·`2` | `A1` `A2` | `B1` `B2` | 로지스틱 회귀 |
| `3` | `A3` | `B3` | k-NN |
| `4` | `A4` | `B4` | **규칙 엔진** — 대화 중 제안 |
| `5` | `A5` | `B5` | **사례 검색** (RAG 검색부) |
| `6` | — | `B6` | **검색 위의 판단** — 대화 중 |
| `7` | `A7` | `B7` | 부스팅 트리 |
| 접미사 `p` | | | 프로 픽·밴율을 쓴다 |
| 접미사 `h` | | | 이력·역할 피처를 더한다 |
| 접미사 `b` | | | 참고 범위를 매 패치 갱신한다 |

`A6` 은 비어 있고, 만들 수 없다. ① 은 **패치 안 전체를 줄 세워야** R-정확도가
성립하는데(20패치 · 패치당 170~173종 · 3,433행), 표본만 판단하면 순위가 안
만들어져 채점이 안 된다. ② 의 239건과는 규모가 14.7배 다르다.

에이전트에는 번호를 주지 않는다. 만들 때 붙인다 — 조회→검색→판단 루프는
단발 arm 과 다른 것이라 `A5`~`B6` 줄에 끼워 넣으면 뜻이 흐려진다.
[ADR 0003](adr/0003-llm-provider-and-calling-convention.md)이 한때 에이전트를
`arm A6` 로 불렀는데, 그 자리는 ① 대상의 판단이 됐다.

### 「균형 접근」을 성패로 읽지 않는다

50% 를 정확히 맞추는 것은 가능한 밸런싱 작업이 아니다. 그러므로 50% 아래로
내려간 것 자체를 실패로 적지 않는다. 이 지표가 재는 것은 **솔랭 지표와 프로
경기 지표가 어긋나는 방향과 크기**다.

대조군이 50.4% 라는 것도 같이 적는다 — 아무것도 안 해도 절반은 50% 에
가까워진다. 이번에 높게 나온 챔피언은 다음에 내려오기 때문이다.

## RAG — **판단을 올려 봤고, 못 이겼다**

| 용어 | 뜻 |
| --- | --- |
| **RAG** | 검색(**R**etrieval)해서 생성(**G**eneration)한다는 뜻이다 |
| **사례 검색** | 표준화한 피처 거리로 과거 이웃 `k` 개를 찾는 것. `CaseSearch` |
| **RAG 검색부** | `A5` · `B5` 가 하는 일 — 사례를 찾아 **이웃 라벨의 다수결**로 답을 낸다 |
| **검색 위의 판단** | `B6` — **같은 이웃 25종**을 보고 대화 안에서 매긴 점수. 실행 시점 API 호출은 0회다 |

「RAG」를 단독으로 쓰지 않는다. `B5` 는 검색부뿐이고 `B6` 이 그 위에 판단을
올린 것이라, 둘을 가려 불러야 한다. `B5` 를 「RAG」라고만 부르면
**「검색해서 LLM 이 판단했다」로 읽히는데** 실제로는 다수결이다.

```python
def _retrieved(...):
    """사례 검색만으로 두 과제를 예측한다. 모델이 없다 — 이웃의 다수결이다."""
```

### 판단이 다수결을 못 이긴다

| arm | AUC | 정확도 | 점수 종류 |
| --- | ---: | ---: | ---: |
| **B5s** 사례 검색만 (다수결) | **0.850** | 76.0% | 25 |
| **B6** 사례 검색 + 판단 | **0.830** | **77.7%** | 50 |

차이 −0.020, 95% [−0.045, +0.004]. 짝지어 부트스트랩 2만 회에서 **구간이 0 을
포함한다.** 줄 세우기로는 져 보이지만 유의하지 않고 정확도로는 이긴다 — 지금
말할 수 있는 것은 **「이긴다고 말할 수 없다」**까지다. 둘 다 같은 229종에서 잰
값이다(`B5s`).

해상도는 병목이 아니었다. 점수 종류가 25 → 50 으로 두 배가 됐는데 AUC 는
내려갔다. `B4` 에서 해상도를 고쳐 0.807 → 0.837 이 된 것과 다르다.

### 벡터화는 하고 있다 — **벡터 DB 를 안 쓸 뿐이다 (2026-08-28 측정)**

「벡터화 없이 RAG 라고 할 수 있나」를 확인했다. **검색 둘 다 이미 벡터 공간
모델이다.**

| 검색기 | 무엇 | 벡터인가 |
| --- | --- | --- |
| **R1** `CaseSearch` | 표준화한 수치 피처 4개의 유클리드 k-NN | **밀집 벡터** |
| **R2** `NoteSearch` | BM25 — 항 가중 벡터 공간 모델 | **희소 벡터** |

없는 것은 **신경망 임베딩**과 **벡터 DB** 둘이고, 그것은 RAG 의 정의가 아니라
구현 선택이다.

#### 벡터 DB 를 안 만드는 근거

```
문서 3,843개 · 256차원 밀집 행렬 7.9 MB
질의 (전수 스캔)  0.06 ms
```

FAISS·Chroma 는 선형 스캔이 느려질 때 쓰는 물건인데 그 문제가 없다.
[ADR-0004](adr/0004-processed-data-storage-format.md)에 「에이전트 도구가 벡터
검색을 필요로 하면 저장 형식을 다시 본다」는 재검토 조건이 걸려 있다.

#### 밀집 임베딩이 희소를 못 이겼다

「챔피언 + 패치」로 질의해 그 패치의 그 챔피언 블록을 찾는 과제 1,599건이다.

| 방법 | MRR@10 | Recall@10 |
| --- | ---: | ---: |
| BM25 (지금) | 0.189 | 56.3% |
| TF-IDF + SVD 256차원 (밀집) | 0.504 | 79.4% |
| **TF-IDF 희소** | **0.697** | **93.1%** |

정확 일치가 중요한 코퍼스라 압축이 손해다. 챔피언 이름·패치 번호·변경 수치가
그대로 맞아야 하는데, 밀집 벡터는 그것을 뭉갠다.

단, 이것이 트랜스포머 임베딩까지 정리하지는 않는다. SVD 는 약한 대리물이고,
제대로 재려면 키나 로컬 모델이 필요하다.

#### 그리고 R2 에 더 큰 결함이 있었다 — **고쳤다**

BM25 가 유독 낮았던 것은 방법이 아니라 **토크나이저 때문**이었다.

```python
_WORD = re.compile(r"[a-z]+")            # 전
_tokens("Ahri 16_13 cooldown")  →  ['ahri', 'cooldown']
```

숫자가 통째로 사라졌다. 패치 번호도, `reduced to 60 from 85` 의 60·85 도
색인에 안 들어갔다. 색인 문서에 패치도 없었다. 그래서 **어느 패치의 Ahri 인지를
원리적으로 못 가렸고**, 코드가 그걸 알고 바깥에서 패치로 좁혀 쓰고 있었다.

숫자를 살리고 패치를 색인에 넣었다.

| 질의 「챔피언 + 패치」 1,599건 | MRR@10 | Recall@10 |
| --- | ---: | ---: |
| BM25 (전) | 0.189 | 56.3% |
| TF-IDF + SVD 밀집 | 0.504 | 79.4% |
| TF-IDF 희소 | 0.697 | 93.1% |
| **BM25 (후)** | **0.924** | **98.1%** |

임베딩을 넣는 것보다 이쪽이 컸다. `./scripts/score-retrieval` 로 언제든 다시
잰다 — 나중에 임베딩을 넣을지 정하는 것도 그 위에서 한다.

### 판단자의 오염은 재서 배제했다

방향 라벨 1,599종을 대화 안의 Claude 가 붙였으므로 기억이 남았는지 재야 했다.
**이름과 패치만 주는 조건**을 따로 돌렸다.

```
전체 80건                        AUC 0.505   찍기와 구별 안 됨
이 대화에서 정답을 본 6건 제외 74건   AUC 0.421   찍기 아래
```

「일부러 50점으로 채운 것 아니냐」에 대한 답도 데이터에 있다 — 아는 6건에는
20·25·65·70·80 점을 매겼다. 정보가 있을 때는 기꺼이 치우쳤다. 설계 근거는
[ADR 0006](adr/0006-rag-generation-and-contamination-control.md).

### 검색기 셋 중 하나는 아직 안 쓰인다

| | | 상태 |
| --- | --- | --- |
| **R1** 사례 검색 | `CaseSearch` — 피처 공간의 근접 이웃 | ✅ `A5`·`B5`·`B6` |
| **R2** 노트 검색 | `NoteSearch` — 패치 노트 텍스트 | ✅ `B6` 의 맥락을 만들 때 |
| **R3** 수치 조회 | `StatLookup` — 패널 직접 조회 | ⏸ **에이전트용 · 아직 부르는 arm 이 없다** |

셋 다 `as_of` 를 **생성자에서** 받아 미래를 도구 차원에서 막는다. `B6` 은 `B5` 와
같은 경계(분할점 고정)를 쓴다 — 다르면 짝지어 비교가 안 된다.

R3 에 억지로 자리를 만들지 않는다. 그것은 에이전트가 **루프 중에 조회**하려고
만든 도구다. 단발 판단은 맥락을 한 번에 받으므로 조회할 일이 없고, 이력·추세는
`PanelRow` 가 이미 담고 있다(`d_win_rate` · `history_len` · `recent_adjustments`
· `high_wr_streak`).

쓰이지 않는 도구를 쓰이는 것처럼 보이게 만드는 것이 안 쓰는 것보다 나쁘다.
실제로 `NoteSearch` 를 이름만으로 질의했다가 「스킨 이름 변경」이 최상위로 올라온
적이 있다 — 그때는 이웃의 조정 패치로 좁혀 **쓸 만한 결과가 나오게** 해결했고,
R3 에는 그런 자리가 아직 없다.

### 재순위·하이브리드·MMR 은 왜 안 하나 (2026-09-01)

RAG 실무에서 흔히 권하는 고급 검색 기법 넷을 우리 구성에 대 봤다. **하나는
재 봤고 나머지 셋은 안 하는 이유가 있다.**

| 기법 | 우리 | 근거 |
| --- | --- | --- |
| **MMR (다양성)** | **재 봤다. 나빠진다** | 아래 |
| 재순위 | 안 한다 | R2 가 이미 MRR 0.924 · Recall 98.1% 다. 그리고 **R2 는 점수에 안 쓰인다** |
| 하이브리드 | 안 한다 | R1 과 R2 는 **다른 것을 찾는다** — 패널 행과 노트 문장이다 |
| 쿼리 확장 · 생성 채점 | 안 한다 | 실행 시점 LLM 호출이 필요하다 |

#### MMR — 이웃의 중복은 잡음이 아니었다

R1 은 이웃 50종을 거리가중 다수결한다. 그 50종에 **같은 챔피언이 몰려 있다.**

    이웃 50종 안의 고유 챔피언   중앙값 27종 (최소 11 · 최대 48)
    한 챔피언이 차지하는 최대 표   중앙값  6 (최대 19)
                                (패치 `15_8` · 질의 170건)

중복을 줄이면 나아질 것 같아 **챔피언당 표에 상한**을 걸어 봤다. MMR 은 후보
사이 거리를 다시 재는 방식인데, 우리 이웃의 「비슷함」은 사실상 같은 챔피언이
인접 패치에 반복되는 것이라 상한 하나가 같은 일을 한다.

학습 구간 20겹, 패치마다 그 직전까지로 검색해 짝지어 비교했다.

    기준 (상한 없음)      ① 0.3191   ② 0.8292

    챔피언당 표 상한 1    ① −0.0312 ±0.0132   ← 유의하게 나빠진다
                  2    ① −0.0141 ±0.0089
                  3    ① −0.0010 ±0.0063
                  5    ① −0.0058 ±0.0050
                       (② 는 상한 넷 전부 표준오차 안이다)

**중복이 신호였다.** 같은 챔피언이 이웃에 여러 번 잡힌다는 것은 **그 챔피언이
그 상황에 반복해서 놓인다**는 뜻이고, 표를 깎으면 그 정보가 사라진다.

#### 재순위 — 고칠 자리가 없다

재순위는 **재현율은 좋은데 상위 정렬이 나쁠 때** 듣는다. R2 는 Recall@10 98.1%
에 MRR@10 0.924 로 상위 정렬이 이미 좋다.

그보다 앞선 이유가 있다. **R2 는 점수를 내는 arm 이 하나도 안 쓴다** — 이웃
다수결로도 피처로도 재 봤고 둘 다 기준선을 못 넘었다([results](results/README.md#여덟째아홉째--노트-검색r2은-왜-점수에-안-쓰이나-2026-08-31)).
검색을 더 좋게 만들어도 갈 곳이 없다.

#### 하이브리드 — 두 검색기가 다른 것을 찾는다

키워드 검색과 의미 검색을 **같은 문서 집합에서** 합치는 것이 하이브리드다.
우리 R1 은 패널 행을, R2 는 노트 문장을 찾는다 — 하나의 순위표로 합칠 대상이
아니다.

예측 쪽에서 둘을 합치는 것은 이미 해 봤다. R2 를 피처로 `A7h` 에 붙였고
CV 는 올랐는데 평가 구간에서 전이되지 않았다(0.2708 ≈ 0.2714).

#### 쿼리 확장 · 생성 채점 — 전제 밖이다

쿼리 확장과 HyDE 는 질문을 다시 쓰려고, `Faithfulness` 같은 생성 지표는 채점
모델을 부르려고 **실행 시점에 LLM 을 호출한다.** [API 키 없이 만든다](../CLAUDE.md)
는 전제 밖이다.

대신 생성부를 다른 방법으로 검정했다 — 지표를 빼고 이름과 패치만 주면 AUC
0.505 로 찍기와 구별되지 않는다(위 「판단자의 오염은 재서 배제했다」).

## 하지 않는 말

| 안 쓴다 | 대신 | 왜 |
| --- | --- | --- |
| 계기판 | **지표** · 어긋난다 | 비유이고 라이엇의 시야를 아는 척한다 |
| 평생 평균 | **통산** | 사람에게 쓰는 말이다 |
| 프로형 · 프로 단골 | **프로 경기에 자주 나오는 챔피언** | 「프로형」은 기준이 안 보이는 만든 말이고, 「단골」은 구어다 |
| 프로발 너프 · 솔랭발 너프 | **높은 쪽 너프 · 낮은 쪽 너프** | 원인을 아는 척한다 |
| 프로 존재감 · 대회 존재감 | **프로 픽·밴율** | 같은 값을 두 이름으로 불렀다 |
| 본선 | **본 분석** | 대회 용어다 |
| 대회 (데이터를 가리킬 때) | **프로 경기** | 우리 데이터는 리그 정규시즌이 대부분이다 |

「라이엇이 프로 경기를 본다」도 쓰지 않는다. 이 저장소가 잰 것은 상관이지 개발사의
시야가 아니다. 근거는 [followups 10번](followups.md)에 있다.
