# 용어

이 문서에 있는 말만 쓴다. 같은 것을 두 이름으로 부르면 읽는 사람이 다른
것으로 읽는다. 실제로 그랬다 — 「프로 존재감」과 「대회 존재감」이 같은 값인데
문서마다 다르게 적혀 있었다.

새 말이 필요하면 **여기에 먼저 적고** 쓴다.

## 데이터

| 용어 | 뜻 |
| --- | --- |
| **솔랭 지표** | u.gg 아카이브의 승률·픽률·밴율. 범위는 `world` · `emerald_plus` 다 |
| **직접 집계** | Riot API 로 받은 경기에서 **우리가 센** 승률·픽률·밴율. 솔랭 지표와 같은 식으로 세지만 출처가 다르다 — **솔랭 지표 뒤에 잇지 않는다.** 키가 필요하다([ADR 0010](adr/0010-riot-api-direct-aggregation.md)) |
| **진화형** | 게임 중에 다른 아이템으로 바뀌는 완성템(Manamune → Muramana). 살 수 없어 완성템 표에 없고, 원래 아이템을 쓴 것으로 센다 |
| **직접 조정** | 그 패치 노트의 챔피언 절에 이름이 오른 것. 아이템 변경으로 흔들린 것과 가르려고 쓴다 |
| **권역** | Riot API 가 경기를 묶는 단위(`asia` · `europe` · `americas`). 플랫폼(`kr` · `euw1` · `na1`)보다 크고, 요청 한도가 권역마다 따로 걸린다 |
| **최종 아이템** | 경기가 끝났을 때 인벤토리에 있던 일곱 칸(마지막이 장신구). **구매 이력이 아니다** — 판 것 · 다 쓴 것 · 바꿔 산 것은 남지 않는다. 직접 집계가 경기마다 남긴다 |
| **완성템** | 협곡에서 살 수 있고 총 골드가 2,000 이상인 아이템. 완성 여부를 가르는 칸이 Data Dragon 에 없어 골드로 근사한다. 신발은 이 아래라 빠진다 |
| **아이템 사용률** | 한 패치에서 그 챔피언 판 중 최종 아이템에 그 완성템이 있는 판의 비율. **구매율이 아니다** — 최종 아이템으로 세서 판 것은 안 보인다([ADR 0011](adr/0011-champion-item-usage.md)) |
| **주요 아이템** | 그 챔피언의 아이템 사용률 상위 셋 중 20% 이상인 것. 그 패치에서 100판이 안 되는 챔피언은 「표본 부족」으로 두고 말하지 않는다 |
| **개인 키** | Riot 개발자 포털의 Personal API Key. 24시간마다 꺼지는 개발 키와 달리 만료가 적혀 있지 않고, 개인 연구에 쓸 수 있다. **공개 서비스에는 못 쓴다** |
| **프로 경기** | Oracle's Elixir 의 프로 경기 기록(29,977경기 · 72패치 — 2026-08-26 내려받기 기준. 갱신본은 [data-sources](spec/data-sources.md#4-oracles-elixir--프로-경기--2020-확인) 참조). **리그 정규시즌이 대부분이고 대회는 일부다** |
| **프로 픽·밴율** | 한 패치에서 그 챔피언이 프로 경기에 나온 비율 — **픽률 + 밴율.** 코드의 `pro_presence` 다. **1.0 을 넘을 수 있다** — 양 팀이 같은 챔피언을 뽑는 형식이 있다 |
| **출시일** | 위키 노트 머리의 「Release Date (US)」 — 그 패치가 북미에 나온 날. **날짜 단위로만** 쓴다 |
| **출시일 경계** | 다음 패치의 출시일. 그날부터 정답(누가 조정됐나)이 공개되므로, **그 뒤에 열린 경기는 앞 패치의 예측에 못 쓴다** |
| **최근 14일 프로 픽·밴율** | 출시일 경계 직전 14일에 열린 프로 경기로 센 픽·밴율. **패치를 가리지 않는다** — 예측하는 날 실제로 보이던 값이다 |
| **대조군** | 그 패치에 조정되지 않은 챔피언 |
| **모집단** | 지표를 잰 플레이어 집단. u.gg 는 `emerald_plus`, 프로 경기는 상위 리그다. 개발사는 넷(Average · Skilled · Elite · 프로)을 따로 본다. **다른 모집단의 값을 한 시계열에 잇지 않는다** |
| **공개 밸런스 기준** | 개발사가 공개한 판정 방식 — 모집단 넷과 각각의 문턱, 그리고 버프 편중 안전장치. 2019·2020년 문서이고 **지금도 이대로인지는 모른다.** 주소는 [data-sources](spec/data-sources.md#6-공개-밸런스-기준--개발사가-적어-둔-문턱) · [측정](results/README.md#개발사가-공개한-기준-2026-09-01) |

「대회」는 국제 대회·정규시즌 같은 실제 대회를 가리킬 때만 쓴다. 데이터
출처를 가리킬 때는 **「프로 경기」**다 — 우리 데이터의 대부분이 리그 정규시즌
이라 「대회」로 부르면 틀린 말이 된다.

## 챔피언 분류

| 용어 | 뜻 |
| --- | --- |
| **통산 픽·밴율** | 그 챔피언이 나온 **모든 패치의 프로 픽·밴율 평균**. 한 패치만 튀는 것과 늘 나오는 것을 가르려고 쓴다 |
| **프로 경기에 자주 나오는 챔피언** | 통산 픽·밴율이 **상위 25%(0.182 이상)**인 챔피언. 42종이다. 표에서는 **「자주 나오는 챔피언」**으로 줄여 쓴다 |

「프로형」은 쓰지 않는다. 「-형」은 만든 말이고 기준이 안 보인다.

## 조정 분류

| 용어 | 뜻 |
| --- | --- |
| **높은 쪽 너프** | 조정 직전 프로 픽·밴율이 **중앙값 위**인 너프 |
| **낮은 쪽 너프** | 중앙값 **아래**인 너프 |

「프로발 너프」·「솔랭발 너프」는 쓰지 않는다. 만든 말이고, 「무엇 때문에
너프했나」를 아는 것처럼 들린다 — **우리는 그것을 모른다.** 아는 것은 프로
픽·밴율이 높았다는 사실뿐이다.

## 분석 범위

| 용어 | 뜻 |
| --- | --- |
| **본 분석** | **공개 데이터**를 쓰는 arm 들 — 솔랭 승률·픽률·밴율과 프로 경기 픽·밴. 한때 솔랭만이었다([ADR 0008](adr/0008-pro-play-in-the-main-analysis.md)) |
| **프로 픽·밴** | 프로 경기에서의 픽률 + 밴율. 두 값을 더한 것이라 1.0 을 넘을 수 있다 |
| **솔랭만** | 프로 피처를 뺀 arm(`A7`·`A7h`·`B5`). 「프로를 넣으면 얼마나 오르나」를 같은 표에서 읽으려고 남겨 둔다 |

「본선」은 쓰지 않는다. 대회 용어다.

## 측정

| 용어 | 뜻 |
| --- | --- |
| **arm** | 비교하는 예측 방법 하나. `A…` 는 ① 대상, `B…` 는 ② 방향이다 — [번호 규칙](#arm-번호) |
| **줄 세우기** | 패치 안에서 챔피언을 점수순으로 정렬하는 것. **R-정확도와 AUC 가 재는 것이 이것이다** |
| **R-정확도** | 한 패치에서 **실제로 조정된 수만큼** 위에서 뽑아 맞힌 비율. 조정이 15종이면 상위 15종을 보고 몇이 맞는지 센다 |
| **AUC** | 아무 「너프된 챔피언」과 아무 「버프된 챔피언」을 뽑았을 때 **너프 쪽에 더 높은 점수를 줄 확률**. 1.0 이 완벽, 0.5 가 찍기 |
| **P@k** | 상위 `k` 종 중 맞은 비율. R-정확도와 달리 `k` 를 우리가 정한다 |
| **기준선** | 아무 지식 없이 찍었을 때의 값. ① 은 조정률(15.0%), ② 는 다수 클래스(51.0%) |
| **배수** | 성적 ÷ 기준선. **기준선이 다른 줄은 배수로만 비교한다** |
| **해상도** | 한 arm 이 내는 **서로 다른 점수의 가짓수**. 낮으면 같은 점수가 뭉쳐 줄 세우기가 안 된다 |
| **의도대로** | 너프 뒤 승률이 내려갔거나 버프 뒤 올라간 비율 |
| **균형 접근** | 조정 뒤 \|승률 − 50%\| 가 **줄어든** 비율. **성패가 아니다** — 아래 참조 |
| **잡음 안 · 잡음 밖** | 직접 집계와 솔랭 지표를 챔피언마다 견준 z 가 **표본 잡음으로 설명되는가.** \|z 평균\| ≤ 0.2 이고 z 표준편차 ≤ 1.2 면 잡음 안이다. **같다는 증명이 아니다** — 그 표본 크기에서 구분이 안 된다는 뜻이다 |
| **날짜 균등** | 승률을 낼 때 수집이 몰린 날이 패치를 대표하지 않도록 **날짜마다 같은 무게**를 주는 것. `16_15` 는 처음 2.5일에 60% 가 몰려 있어 이것 없이는 그 날의 메타가 패치 전체가 된다 |
| **위약 비교** | 아이템 변경이 없는 **같은 패치 안**에서 앞 반 → 뒤 반을 같은 무리로 견준 것. 여기서도 차이가 나오면 그 차이는 아이템이 아니라 시간과 표본이 만든 것이다 |
| **전향 평가** | 정답이 나오기 **전에** 예측을 적어 두고 패치가 나온 뒤 채점하는 것. 과거를 되짚는 백테스트와 달리 정답을 본 적이 없다 |
| **평가 지점** | 채점이 한 번 이뤄지는 기준 패치 하나. 「예측 지점」과 같은 뜻으로, 직접 집계 쪽에서는 이 말을 쓴다 |
| **가를 수 있는 최소 차이** | 80% 검정력 · 양측 5% 에서 그 표본이 잡아낼 수 있는 가장 작은 무리 차이 — 2.8 × 해석적 표준오차. 이 아래 차이는 「없다」가 아니라 「못 본다」다 |
| **계통 차이** | 두 출처의 차이 중 잡음으로 설명되지 않는 크기. 차이의 분산에서 표준오차² 의 평균을 뺀 것의 제곱근이다 |

「계기판」은 쓰지 않는다. 비유이고, 라이엇이 무엇을 보는지 아는 것처럼
들린다. **「지표」로 쓰고, 둘이 안 맞을 때는 「어긋난다」로 쓴다.**

#### AUC 를 읽을 때 걸린 것 셋

0.5 아래도 뜻이 있다 — 뒤집혔다는 뜻이다. 승률 높은 순으로 조정 대상을 줄
세우면 `A0c` 가 **0.448** 로 무작위보다 나쁘다. 조정되는 쪽이 양 끝이라 한 방향
줄 세우기가 거꾸로 간다. 거리(`wr_gap`)로 바꾸면 0.569 로 뒤집힌다.

AUC 는 「맞혔나」가 아니라 「줄을 잘 세웠나」다. `B4` 규칙이 한때 0.807 이었는데
점수 종류가 **5개**뿐이었다 — 5칸에 몰아넣으면 칸 안에 순서가 없다. 규칙을 안
바꾸고 점수 내는 방식만 고쳐 19종으로 늘리니 0.837 이 됐다.

절대값보다 기준선과의 거리를 본다. 0.900 이 좋아 보여도 「승률만 봐도
0.796」이 먼저다. 그래서 표에 기준선을 항상 같이 적는다.

### arm 번호

같은 번호는 두 과제에서 같은 방법을 뜻한다.

| | ① 대상 | ② 방향 | |
| --- | --- | --- | --- |
| `0` | `A0`… | `B0`… | 기준선 — 무작위·단일 지표 순 |
| `1`·`2` | `A1` `A2` | `B1` `B2` | 로지스틱 회귀 |
| `3` | `A3` | `B3` | k-NN |
| `4` | `A4` | `B4` | **규칙 엔진** — 대화 중 제안 |
| `5` | `A5` | `B5` | **사례 검색** (RAG 검색부) |
| `6` | — | `B6` | **검색 위의 판단** — 대화 중 |
| `7` | `A7` | `B7` | 부스팅 트리 |
| `8` | — | `B8` | **에이전트** — 조회→검색→판단 루프를 모델이 돈다. 로컬 모델 |
| 접미사 `p` | | | 프로 픽·밴율을 쓴다 |
| 접미사 `h` | | | 이력·역할 피처를 더한다 |
| 접미사 `b` | | | 참고 범위를 매 패치 갱신한다 |

`A6` 은 비어 있고, **대화 안에서는** 만들 수 없다. ① 은 **패치 안 전체를 줄
세워야** R-정확도가 성립하는데(20패치 · 패치당 170~173종 · 3,433행), 표본만
판단하면 순위가 안 만들어져 채점이 안 된다. ② 의 239건과는 규모가 14.7배 다르다.

에이전트에는 번호를 미리 주지 않았다. 만들 때 붙인다고 적어 두었고, **2026-09-18
에 만들어 `8` 을 붙였다.** 조회→검색→판단 루프는 단발 arm 과 다른 것이라
`A5`~`B6` 줄에 끼워 넣지 않고 새 줄로 둔다.
[ADR 0003](adr/0003-llm-provider-and-calling-convention.md)이 한때 에이전트를
`arm A6` 로 불렀는데, 그 자리는 ① 대상의 판단이 됐다.

`A8` 은 비어 있다. 자동 호출이라 3,433행을 다 판단할 수는 있지만 **돌리지 않았다**
— 이유는 [results](results/README.md#같은-이웃으로-다시-쟀다--에이전트-b8-2026-09-18)에 있다.
`B8` 은 `run-report` 표에 아직 없다. `scripts/score-agent` 가 따로 잰다([followups 24](followups.md)).

### 「균형 접근」을 성패로 읽지 않는다

50% 를 정확히 맞추는 것은 가능한 밸런싱 작업이 아니다. 그러므로 50% 아래로
내려간 것 자체를 실패로 적지 않는다. 이 지표가 재는 것은 **솔랭 지표와 프로
경기 지표가 어긋나는 방향과 크기**다.

대조군이 50.4% 라는 것도 같이 적는다 — 아무것도 안 해도 절반은 50% 에
가까워진다. 이번에 높게 나온 챔피언은 다음에 내려오기 때문이다.

## RAG — **판단을 올려 봤고, 이긴다고 말할 수 없다**

| 용어 | 뜻 |
| --- | --- |
| **RAG** | 검색(**R**etrieval)해서 생성(**G**eneration)한다는 뜻이다 |
| **사례 검색** | 표준화한 피처 거리로 과거 이웃 `k` 개를 찾는 것. `CaseSearch` |
| **RAG 검색부** | `A5` · `B5` 가 하는 일 — 사례를 찾아 **이웃 라벨의 다수결**로 답을 낸다 |
| **검색 위의 판단** | `B6` — 이웃 25종과 **대상 자신의 지표**를 보고 대화 안에서 매긴 점수. 실행 시점 API 호출은 0회다. **`B5` 와 같은 이웃이 아니다** — [되돌린 판단](results/README.md#되돌린-판단--둘이-같은-이웃을-본-것이-아니었다-2026-09-01) |
| **에이전트** | `B8` — 검색기를 도구로 쥐고 조회→검색→판단을 **모델이 스스로** 돈다. 로컬 모델이라 키가 필요 없다. 판단 기록을 텍스트로 두고 채점만 한다 — [agent](agent.md) |

「RAG」를 단독으로 쓰지 않는다. `B5` 는 검색부뿐이고 `B6` 이 그 위에 판단을
올린 것이라, 둘을 가려 불러야 한다. `B5` 를 「RAG」라고만 부르면
**「검색해서 LLM 이 판단했다」로 읽히는데** 실제로는 다수결이다.

```python
def _retrieved(...):
    """사례 검색만으로 두 과제를 예측한다. 모델이 없다 — 이웃의 다수결이다."""
```

### 판단이 다수결을 이겼다고 말할 수 없다

| arm | AUC | 정확도 | 점수 종류 |
| --- | ---: | ---: | ---: |
| **B5s** 사례 검색만 (다수결) | **0.850** | 76.0% | 25 |
| **B6** 사례 검색 + 판단 | **0.830** | **77.7%** | 50 |

차이 −0.020, 95% [−0.045, +0.004]. 짝지어 부트스트랩 2만 회에서 **구간이 0 을
포함한다.** 줄 세우기로는 져 보이지만 유의하지 않고 정확도로는 이긴다 — 지금
말할 수 있는 것은 **「이긴다고 말할 수 없다」**까지다. 표본은 같은 229종이다(`B5s`).

**입력은 같지 않다 (2026-09-01).** 오래 「같은 이웃 25종」으로 적어 뒀는데 검색
풀이 달랐다 — 판단자가 본 방향 붙은 이웃은 중앙값 2종이고 `B5` 는 25종이다.
대신 판단자는 대상 자신의 지표를 봤다. **−0.020 을 「판단 대 다수결」의 차이로
읽을 수 없다** — [되돌린 판단](results/README.md#되돌린-판단--둘이-같은-이웃을-본-것이-아니었다-2026-09-01).

해상도는 병목이 아니었다. 점수 종류가 25 → 50 으로 두 배가 됐는데 AUC 는
내려갔다. `B4` 에서 해상도를 고쳐 0.807 → 0.837 이 된 것과 다르다.

**입력을 맞춰 다시 쟀다 (2026-09-18).** 에이전트 `B8`(변형 `r1`)에게 `B5` 와 **같은
이웃 25종**과 대상 자신의 지표를 주고 판단만 맡겼다. 판단자는 로컬 모델(`qwen3.5`
2b · 9b)이다. **졌고, 유의하다** — 최종 설정이 같은 221종에서 0.727 대 `B5s` 0.854,
차이 −0.127 [−0.191, −0.067]
([결과](results/README.md#같은-이웃으로-다시-쟀다--에이전트-b8-2026-09-18)).
작은 모델의 결과라 큰 모델로 넓히지 않는다.

### 벡터화는 하고 있다 — **벡터 DB 를 안 쓸 뿐이다 (2026-08-28 측정)**

「벡터화 없이 RAG 라고 할 수 있나」를 확인했다. **검색 둘 다 이미 벡터 공간
모델이다.**

| 검색기 | 무엇 | 벡터인가 |
| --- | --- | --- |
| **R1** `CaseSearch` | 표준화한 수치 피처 4개의 유클리드 k-NN | **밀집 벡터** |
| **R2** `NoteSearch` | BM25 — 항 가중 벡터 공간 모델 | **희소 벡터** |

없는 것은 **신경망 임베딩**과 **벡터 DB** 둘이고, 그것은 RAG 의 정의가 아니라
구현 선택이다. **신경망 임베딩은 재 보고 안 넣었다** — 아래 「밀집 임베딩이
희소를 못 이겼다」.

#### 벡터 DB 를 안 만드는 근거

```
문서 3,843개 · 256차원 밀집 행렬 7.9 MB
질의 (전수 스캔)  0.06 ms
```

FAISS·Chroma 는 선형 스캔이 느려질 때 쓰는 물건인데 그 문제가 없다.
[ADR-0004](adr/0004-processed-data-storage-format.md)에 「에이전트 도구가 벡터
검색을 필요로 하면 저장 형식을 다시 본다」는 재검토 조건이 걸려 있다.

#### 밀집 임베딩이 희소를 못 이겼다

「챔피언 + 패치」로 질의해 그 패치의 그 챔피언 블록을 찾는 과제 1,599건이다.

| 방법 | MRR@10 | Recall@10 |
| --- | ---: | ---: |
| BM25 (토크나이저 고치기 전) | 0.189 | 56.3% |
| 로컬 임베딩 `nomic-embed-text` 768차원 (밀집) | 0.366 | 71.1% |
| 로컬 임베딩 `qwen3-embedding:0.6b` 1024차원 (밀집) | 0.480 | 82.1% |
| TF-IDF + SVD 256차원 (밀집) | 0.504 | 79.4% |
| **TF-IDF 희소** | **0.697** | **93.1%** |

정확 일치가 중요한 코퍼스라 압축이 손해다. 챔피언 이름·패치 번호·변경 수치가
그대로 맞아야 하는데, 밀집 벡터는 그것을 뭉갠다.

**트랜스포머 임베딩도 재 봤다 (2026-09-18).** 한때 「SVD 는 약한 대리물이고,
제대로 재려면 키나 로컬 모델이 필요하다」고 적어 뒀다. 로컬 모델 둘로 쟀다(Ollama
· 키 없음) — **SVD 보다도 낮다.** 모델이 권하는 앞말을 붙였고, 문서는 BM25 가
색인하는 문자열 그대로다. `./scripts/score-retrieval --embed ollama:…` 로 다시 잰다.

**챔피언은 맞히고 패치를 못 가린다.** 질의 1,599건에서 1위가 무엇이었나를 세면
이렇다.

```
                         맞음    같은 챔피언 · 다른 패치
BM25 (B=0.5)            1,454      132
nomic-embed-text          370    1,222
qwen3-embedding:0.6b      544    1,047
```

임베딩은 「16_13」과 「16_12」를 거의 가르지 못한다. 이 과제는 바로 그 차이를
가르는 것이라 의미 검색이 보탤 것이 없다.

#### 그리고 R2 에 더 큰 결함이 있었다 — **고쳤다**

BM25 가 유독 낮았던 것은 방법이 아니라 **토크나이저 때문**이었다.

```python
_WORD = re.compile(r"[a-z]+")            # 전
_tokens("Ahri 16_13 cooldown")  →  ['ahri', 'cooldown']
```

숫자가 통째로 사라졌다. 패치 번호도, `reduced to 60 from 85` 의 60·85 도
색인에 안 들어갔다. 색인 문서에 패치도 없었다. 그래서 **어느 패치의 Ahri 인지를
원리적으로 못 가렸고**, 코드가 그걸 알고 바깥에서 패치로 좁혀 쓰고 있었다.

숫자를 살리고 패치를 색인에 넣었다.

| 질의 「챔피언 + 패치」 1,599건 | MRR@10 | Recall@10 |
| --- | ---: | ---: |
| BM25 (전) | 0.189 | 56.3% |
| TF-IDF + SVD 밀집 | 0.504 | 79.4% |
| TF-IDF 희소 | 0.697 | 93.1% |
| BM25 (후) · `B=0.75` | 0.924 | 98.1% |
| **BM25 · `B=0.5`** | **0.946** | **99.2%** |

마지막 줄은 나중에 길이 정규화를 낮춘 것이다 — 놓치는 질의의 정답 블록이
유독 길다는 것을 [진단표](#rag-실무-점검표에-대-봤다-2026-09-01)로 찾았다.

임베딩을 넣는 것보다 이쪽이 컸다. `./scripts/score-retrieval` 로 언제든 다시
잰다 — 나중에 임베딩을 넣을지 정하는 것도 그 위에서 한다.

### 판단자의 오염은 재서 배제했다

방향 라벨 1,599종을 대화 안의 Claude 가 붙였으므로 기억이 남았는지 재야 했다.
**이름과 패치만 주는 조건**을 따로 돌렸다.

```
전체 80건                        AUC 0.505   찍기와 구별 안 됨
이 대화에서 정답을 본 6건 제외 74건   AUC 0.421   찍기 아래
```

「일부러 50점으로 채운 것 아니냐」에 대한 답도 데이터에 있다 — 아는 6건에는
20·25·65·70·80 점을 매겼다. 정보가 있을 때는 기꺼이 치우쳤다. 설계 근거는
[ADR 0006](adr/0006-rag-generation-and-contamination-control.md).

### 검색기 셋 중 하나가 오래 안 쓰였다 — **에이전트가 부른다 (2026-09-18)**

| | | 상태 |
| --- | --- | --- |
| **R1** 사례 검색 | `CaseSearch` — 피처 공간의 근접 이웃 | ✅ `A5`·`B5`·`B6`·`B8` |
| **R2** 노트 검색 | `NoteSearch` — 패치 노트 텍스트 | ✅ `B6` 의 맥락 · `B8` 의 해설 |
| **R3** 수치 조회 | `StatLookup` — 패널 직접 조회 | ✅ `B8` — 변형 `v1` 과 해설 |

셋 다 `as_of` 를 **생성자에서** 받아 미래를 도구 차원에서 막는다. `B6` 은 `B5` 와
같은 경계(분할점 고정)를 쓴다 — 다르면 짝지어 비교가 안 된다.

R3 에 억지로 자리를 만들지 않는다. 그것은 에이전트가 **루프 중에 조회**하려고
만든 도구다. 단발 판단은 맥락을 한 번에 받으므로 조회할 일이 없고, 이력·추세는
`PanelRow` 가 이미 담고 있다(`d_win_rate` · `history_len` · `recent_adjustments`
· `high_wr_streak`).

쓰이지 않는 도구를 쓰이는 것처럼 보이게 만드는 것이 안 쓰는 것보다 나쁘다.
실제로 `NoteSearch` 를 이름만으로 질의했다가 「스킨 이름 변경」이 최상위로 올라온
적이 있다 — 그때는 이웃의 조정 패치로 좁혀 **쓸 만한 결과가 나오게** 해결했다.

**에이전트를 만들고 나서야 R3 에 자리가 생겼다.** 다만 판단을 돕지는 않았다 —
변형 `v1` 에서 경계를 분할점에 고정하니 R3 가 대상보다 중앙값 12패치 전 기록을
줬고, 기권 82건 중 60건이 R3 를 부른 건이었다. 경계를 대상 직전까지 연
`r1r3` 는 돌리지 않았다([agent](agent.md#변형)).

### RAG 실무 점검표에 대 봤다 (2026-09-01)

RAG 실무에서 쓰는 **실패 진단표**와 **성능 평가 항목**을 우리 구성에 한 줄씩
대 봤다. **두 줄이 걸렸고 원인이 하나였다.**

| 증상 | 우리 (`B=0.75` · 고치기 전) |
| --- | --- |
| 아무것도 못 찾는다 | 74패치 3,843블록, **빈 패치 0**. 패치당 17~119 |
| **엉뚱한 문서가 온다** | 1위가 틀린 것 **179건(11.2%)** — 그중 **163건이 같은 챔피언의 다른 패치**다 |
| **관련 문서가 빠진다** | **31건(1.9%)** — 그 정답 블록이 유독 길다 |
| 근거는 맞는데 답이 틀림 | `B6` 이 그것이다. 다수결 0.850 을 못 넘었지만 **입력이 달라 그 차이로는 못 읽는다**(위 절) |
| 출처가 안 나온다 | `Note.source` 가 모든 줄에 R1·R2·R3·규칙·수치를 붙인다 |
| 같은 문장만 반복 | 고유 블록 3,839 / 3,843. **중복 4건** |
| 느리다 | BM25 질의당 4.2 ms. 전수 스캔이고 인덱스가 없다(위 0.06 ms 는 밀집 행렬 쪽이다) |

고친 뒤에는 놓침 31건 → 12건(0.8%), 1위 틀림 179건 → 145건(9.1%)이다.

#### 걸린 둘은 같은 원인이었다

BM25 의 길이 정규화 `B` 가 기본값 0.75 였다. 이 코퍼스는 블록 길이가 중앙값
20토큰인데 편차가 커서, **짧은 블록 하나가 두 낱말을 다 맞힌 긴 블록을 이긴다.**

    질의 「Heimerdinger 13_15」
      13_15 UPGRADE!!!   68토큰   6.17   (heimerdinger 3.46 + 13_15 2.71)
      16_3  Stats        10토큰   7.77   (heimerdinger 7.77 · 패치 안 맞음)

놓친 31건도 같다 — **정답 블록 길이가 중앙값 75토큰**으로 전체 중앙값 20 의
네 배다. 「엉뚱한 것이 온다」와 「관련 것이 빠진다」가 한 뿌리였다.

**앞 절반 패치(916건)에서 `B` 를 고르고 뒤 절반(683건)으로 확인했다.**

    B      앞 절반 MRR   뒤 절반 MRR   뒤 Recall   뒤 1위 정확
    0.75      0.9258      0.9206       97.5%       88.6%
    0.5       0.9472      0.9432       99.3%       90.6%   ← 골랐다
    0.3       0.9450      0.9452       99.6%       90.3%
    0         0.9028      0.9031      100.0%       82.4%

**0 으로 두면 재현율은 100% 인데 순서가 무너진다**(1위 정확도 82%). 길이를 아예
안 보면 긴 블록이 낱말 수만으로 이긴다. `B=0.5` 로 바꿨고 전량 재측정이
**MRR 0.924 → 0.946 · Recall 98.1% → 99.2%** 다.

#### 점검표가 권하는 메타데이터 필터는 우리가 못 쓴다

같은 진단에 「메타데이터 필터로 범위를 좁혀라」가 붙어 있다. 질의한 패치로
필터하면 **MRR 0.996 · 1위 정확 99.2%** 로 거의 완벽해진다.

**그런데 제품에서는 못 쓴다.** `ask` 는 `as_of` 로 질의 패치의 노트를 이미
빼고 시작한다 — 그 패치로 필터하면 남는 것이 없다. **채점 과제(「이 패치의 이
블록을 찾아라」)와 제품 용도(「이 챔피언에게 그동안 무슨 일이 있었나」)가 다르다.**
0.996 은 우리가 쓸 수 있는 숫자가 아니므로 기록만 한다.

#### 성능 평가 항목

| 항목 | 우리 |
| --- | --- |
| MRR · Recall@K | **0.946 · 99.2%** — 점검표의 목표는 둘 다 0.7 이상이다 |
| Precision@K | **재지 않는다.** 질의마다 정답 블록이 하나라 `P@10` 은 0.1 이 천장이다 |
| Faithfulness · Answer Relevancy | 채점 모델을 부른다. [키 없이 만든다](../CLAUDE.md)는 전제 밖이다 |
| 골든세트 | 정답지 라벨 **1,599건**. 점검표는 20건이면 방향 판단에 충분하다고 본다 |
| 개선 순서 (검색 먼저) | 그렇게 했다 — 검색은 좋은데 **생성이 진다**는 것을 그래서 찾았다 |

**생성 쪽은 다른 방법으로 검정했다.** 지표를 빼고 이름과 패치만 주면 AUC 0.505
로 찍기와 구별되지 않는다(위 「판단자의 오염은 재서 배제했다」). 채점 모델 없이
할 수 있는 것이 그것이었다.

### 재순위·하이브리드·MMR 은 왜 안 하나 (2026-09-01)

RAG 실무에서 흔히 권하는 고급 검색 기법 넷을 우리 구성에 대 봤다. **둘은 재
봤고(MMR · 하이브리드) 나머지 둘은 안 하는 이유가 있다.**

| 기법 | 우리 | 근거 |
| --- | --- | --- |
| **MMR (다양성)** | **재 봤다. 세게 깎으면 나빠진다** | 아래 |
| 재순위 | 안 한다 | R2 가 이미 MRR 0.946 · Recall 99.2% 다. 그리고 **R2 는 점수에 안 쓰인다** |
| 하이브리드 | **재 봤다. 섞으면 나빠진다** | R1 과 R2 는 다른 것을 찾는다. R2 안에서 BM25 와 임베딩을 섞으면 MRR 0.946 → 0.735 (아래) |
| 쿼리 확장 · 생성 채점 | 안 한다 | 실행 시점 LLM 호출이 필요하다 |

#### MMR — 이웃의 중복은 잡음이 아니었다

`B5p` 는 이웃 50종을 프로 피처 거리로 찾아 거리가중 다수결한다.
그 50종에 **같은 챔피언이 몰려 있다.**

    이웃 50종 안의 고유 챔피언   중앙값 27종 (최소 11 · 최대 48)
    한 챔피언이 차지하는 최대 표   중앙값  6 (최대 19)
                                (패치 `15_8` · 질의 170건 · `B5p` 의 피처)

중복을 줄이면 나아질 것 같아 **챔피언당 표에 상한**을 걸어 봤다. MMR 은 후보
사이 거리를 다시 재는 방식인데, 우리 이웃의 「비슷함」은 사실상 같은 챔피언이
인접 패치에 반복되는 것이라 상한 하나가 같은 일을 한다.

학습 구간 20겹, 패치마다 그 직전까지로 검색해 짝지어 비교했다.

    기준 (상한 없음)      ① 0.3191   ② 0.8292

    챔피언당 표 상한 1    ① −0.0312 ±0.0132   ← 유의하게 나빠진다
                  2    ① −0.0141 ±0.0089
                  3    ① −0.0010 ±0.0063
                  5    ① −0.0058 ±0.0050
                       (② 는 상한 넷 전부 표준오차 안이다)

**중복이 신호였다.** 같은 챔피언이 이웃에 여러 번 잡힌다는 것은 **그 챔피언이
그 상황에 반복해서 놓인다**는 뜻이고, 표를 깎으면 그 정보가 사라진다.

다만 유의한 것은 상한 1 하나다. 상한 3·5 는 표준오차 안이라 **적당히 깎는 것은
좋아지지도 나빠지지도 않았다** — 「중복이 신호」는 상한 1 에서 끌어낸 해석이다.

#### 재순위 — 고칠 자리가 없다

재순위는 **재현율은 좋은데 상위 정렬이 나쁠 때** 듣는다. R2 는 Recall@10 99.2%
에 MRR@10 0.946 으로 상위 정렬이 이미 좋다.

그보다 앞선 이유가 있다. **R2 는 점수를 내는 arm 이 하나도 안 쓴다** — 이웃
다수결로도 피처로도 재 봤고 둘 다 기준선을 못 넘었다([results](results/README.md#여덟째아홉째--노트-검색r2은-왜-점수에-안-쓰이나-2026-08-31)).
검색을 더 좋게 만들어도 갈 곳이 없다.

#### 하이브리드 — 두 검색기가 다른 것을 찾는다

키워드 검색과 의미 검색을 **같은 문서 집합에서** 합치는 것이 하이브리드다.
우리 R1 은 패널 행을, R2 는 노트 문장을 찾는다 — 하나의 순위표로 합칠 대상이
아니다.

예측 쪽에서 둘을 합치는 것은 이미 해 봤다. R2 를 피처로 `A7h` 에 붙였고
CV 는 올랐는데 평가 구간에서 전이되지 않았다(0.2708 ≈ 0.2714).

**R2 안에서는 섞어 봤다 (2026-09-18).** 같은 노트 블록에 BM25 와 로컬 임베딩을
돌려 순위의 역수를 더했다(RRF, k=60). 이것이 보통 말하는 하이브리드다. **나빠졌다.**

```
                           MRR@10   Recall@10
BM25 만                     0.946     99.2%
BM25 + qwen3-embedding      0.735     96.5%
BM25 + nomic-embed-text     0.599     95.1%
```

임베딩이 패치를 못 가리므로(위 「밀집 임베딩이 희소를 못 이겼다」) 섞으면 BM25 가
맞힌 1위를 같은 챔피언의 다른 패치가 끌어내린다.

#### 쿼리 확장 · 생성 채점 — 전제 밖이다

쿼리 확장과 HyDE 는 질문을 다시 쓰려고, `Faithfulness` 같은 생성 지표는 채점
모델을 부르려고 **실행 시점에 LLM 을 호출한다.** [API 키 없이 만든다](../CLAUDE.md)
는 전제 밖이고, 대신 무엇으로 검정했는지는 위 「성능 평가 항목」에 적었다.

| **코드 대조** | 해설이 칸에 옮겨 적은 것을 코드가 맞춰 보는 것 — 베이스라인 방향 · 경고 인용 · 출처 |

## 하지 않는 말

| 안 쓴다 | 대신 | 왜 |
| --- | --- | --- |
| 계기판 | **지표** · 어긋난다 | 비유이고 라이엇의 시야를 아는 척한다 |
| 평생 평균 | **통산** | 사람에게 쓰는 말이다 |
| 프로형 · 프로 단골 | **프로 경기에 자주 나오는 챔피언** | 「프로형」은 기준이 안 보이는 만든 말이고, 「단골」은 구어다 |
| 프로발 너프 · 솔랭발 너프 | **높은 쪽 너프 · 낮은 쪽 너프** | 원인을 아는 척한다 |
| 프로 존재감 · 대회 존재감 | **프로 픽·밴율** | 같은 값을 두 이름으로 불렀다 |
| 본선 | **본 분석** | 대회 용어다 |
| 대회 (데이터를 가리킬 때) | **프로 경기** | 우리 데이터는 리그 정규시즌이 대부분이다 |
| A6 (에이전트를 가리킬 때) | **`B8`** | `A6` 은 ① 대상의 판단 자리다. 에이전트는 `8` 이다 |

「라이엇이 프로 경기를 본다」도 쓰지 않는다. 이 저장소가 잰 것은 상관이지 개발사의
시야가 아니다. 근거는 [followups 10번](followups.md)에 있다.
