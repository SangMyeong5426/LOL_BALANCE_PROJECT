# ADR 0019: 프로덕션 키를 받았다 — 요청 한도와 공개 범위를 다시 정한다

- 상태: **Proposed · 결정 1 은 키 대기 · 공개 범위는 주인 결정 대기**
- 날짜: 2026-11-18
- [ADR 0010](0010-riot-api-direct-aggregation.md) 의 **키 단계 전제를 대체한다.** 0010 을
  지우지 않는다 — 개인 키로 무엇을 했고 왜 공개를 막았는지가 그 문서의 기록이다.

## 배경

[ADR 0010](0010-riot-api-direct-aggregation.md) 은 **개인 키(Personal)** 를 전제로 썼고,
프로덕션 키를 이렇게 적었다.

> **Production 키** — 공개 서비스에 나오는 것이라 개인 분석으로는 **받지 못한다**

**받았다 (2026-11-18).** 그래서 0010 이 깔고 있던 두 전제가 같이 풀린다.

| 0010 이 전제한 것 | 바뀐 것 |
| --- | --- |
| 요청 한도 1초 20회 · 2분 100회 | 프로덕션은 **10초 500회 · 10분 30,000회**(권역마다) |
| 「공개하려면 Production 키가 먼저다」 | 그 키가 생겼다 |

### 확인했다 — **아직 프로덕션 키가 아니다** (2026-11-18)

포털의 앱 정보 화면과 응답 헤더가 같은 것을 말한다.

| | |
| --- | --- |
| 화면 머리 | **`DEVELOPMENT API KEY`** |
| 화면의 한도 | **1초 20회 · 2분 100회** |
| 응답 헤더 | `X-App-Rate-Limit: 100:120,20:1` — 포털과 일치한다 |
| 프로덕션이면 | `500:10,30000:600` 이어야 한다 |

**`Status: Approved` 는 키 단계가 아니라 제품 등록이 승인됐다는 뜻이다.** 등록은
통과했고 키는 그 아래 단계다. **프로덕션 한도를 쓰려면 이 앱으로 Production 키를
따로 신청해야 한다.**

그래서 **결정 1 을 구현하지 않는다.** 아래 재검토 조건의 첫 줄이 이미 걸렸다.

> **포털 화면은 키를 평문으로 띄운다.** 앱 정보 화면의 `API Key` 칸이 그렇다. 그 화면을
> 공유·캡처·화면 읽기에 넘기지 않는다. 노출됐으면 같은 화면의 `NEW API KEY` 로 새로
> 받고 `.env` 를 바꾼다.

### 약관에서 확인한 것

포털·일반 정책·LoL 정책을 읽었다(2026-11-18).

| | 약관이 말하는 것 |
| --- | --- |
| 개인 키의 공개 금지 | "You may not run your application for public consumption using a personal key, **regardless of how long the approval process** for your production key takes." 공개에는 오픈 알파·베타가 포함된다 |
| 프로덕션 키의 용도 | "intended for large communities or **the Internet as a whole**" |
| 우리가 하는 일 | LoL 정책의 프로덕션 승인 용례에 **"Aggregate player stats (no specific players)"** 가 있다 |
| 집계 공개 금지 조항 | **없다.** 금지된 것은 **Augment · 아레나 아이템**의 승률이다 — 챔피언 승률은 그 조항에 안 들어간다 |
| 키를 코드에 넣지 말 것 | "Do not include your API key in your code" |
| 법적 고지 | 제품에 눈에 띄게 싣는다. 제품은 포털에 등록하고, **기능 변경도 감사 대상**이다 |

### 등록한 제품 설명이 이미 적고 있는 것

포털에 등록한 설명(이 상태로 `Approved`)에 두 줄이 있다.

> "Only code, methodology, and **aggregate findings may be published**, not raw match data."
> "It provides **no live in-game assistance or hidden MMR estimates**."

뒷줄은 일반 정책의 Game Integrity 금지 조항(랭킹 대안 · MMR·ELO 계산기)을 정면으로
비켜 간다. **다만 이것은 우리가 Riot 에 신고한 내용이고 Riot 이 준 허가가 아니다** —
개인 키로 「공개용 애플리케이션을 돌리지 못한다」는 줄은 그대로다. 그래서 아래 결정 2 의
보류를 이것으로 풀지 않는다.

**설명이 지금 코드와 어긋나는 데가 하나 있다.**

> "Collection will initially cover a limited sample of **Korean** ranked solo queue matches."

지금은 `kr` · `euw1` · `na1` **세 권역**을 받는다(`riot.ROUTES`). `initially` 라고 적혀
있어 거짓은 아니지만 현재 상태와 다르고, 약관은 "You must make sure its description and
metadata are **kept up to date** with the current version of your product" 라고 적는다.
**Production 키를 신청할 때 설명의 권역을 세 개로 고친다.**

**캐싱·보관 기간은 약관에 안 적혀 있다.** 그래서 「며칠까지 보관해도 된다」를 우리가
정할 수 없고, 이 ADR 도 정하지 않는다.

**판단이 갈릴 수 있는 줄이 하나 있다.** 일반 정책의 Game Integrity 에
"Products should **increase, and not decrease** the diversity of game decisions (builds,
compositions, characters, decks)" 가 있다. 픽·밴율 공개가 여기 걸리는지는 **약관이 말하지
않는다.** 우리 쪽 사정으로는 이 도구가 「조정 후보」를 내는 것이고 「이 챔피언을 하라」를
내지 않지만, 그것이 약관의 판단과 같다고 단정하지 않는다.

### 지금 지키고 있는지 먼저 봤다

| 봤다 | 결과 |
| --- | --- |
| 배포물에 키가 있나 | `docs/site` 206개 파일에 `RGAPI-` · `X-Riot-Token` · 실시간 호출이 **없다** |
| 저장소에 키가 있나 | `RGAPI` 가 테스트 셋뿐이고 전부 가짜다(`RGAPI-test` · 전부 0) |
| 법적 고지 | `docs/site/index.html` 에 Riot 문구 그대로 있다 |

**구조가 이미 맞다.** 정적 API 를 미리 만들어 두고 화면은 저장된 숫자만 읽으므로, 공개
범위를 넓혀도 키가 배포물에 들어갈 길이 없다.

## 검토한 선택지

두 결정이 한 키에서 나온다. 따로 적는다.

### 결정 1 — 요청 한도를 코드에 어떻게 반영하나

지금은 `src/lol_balance/riot.py` 에 박혀 있다.

```python
LIMITS = ((18, 1.0), (95, 120.0))   # 개인 키 한도에서 조금 남긴 값
```

| | 장점 | 단점 |
| --- | --- | --- |
| **가. 프로덕션 한도를 박는다** | 한 줄이다. 지금과 같은 꼴 | **키가 바뀌면 또 고쳐야 한다.** 이번에 고쳐야 하는 이유가 바로 이것이다. 키가 개인으로 되돌아가면 429 를 맞는다 |
| **나. 응답 헤더에서 읽어 맞춘다** | `X-App-Rate-Limit` 이 매 응답에 온다. 키 단계가 바뀌어도 코드가 그대로다 | 헤더가 없거나 꼴이 다를 때의 기본값이 필요하다. 첫 요청은 한도를 모르고 보낸다 |
| **다. 보수적으로 중간만 쓴다**(예: 개인 키의 5배) | 429 위험이 가장 낮다 | **근거가 없는 수다.** 왜 5배인지 댈 것이 없고, 열린 한도를 안 쓰는 값만 남는다 |

### 결정 2 — 공개 범위를 넓히나

지금은 배포 페이지와 정적 API 에 **u.gg 패널 구간(`16_13` 까지)만** 싣는다
([ADR 0016](0016-static-api-and-local-qa.md) · [extension](../extension.md)).

| | 장점 | 단점 |
| --- | --- | --- |
| **A. 그대로 둔다** | 약관 판단을 안 해도 된다. 지금 성적·주의가 전부 u.gg 구간에서 나온 것이라 화면과 근거가 일치한다 | 막아 둔 **이유가 없어졌는데 그대로 두는 것**이 된다. 최신 패치 예측을 공개로 못 보여 준다 |
| **B. 직접 집계까지 싣는다** | 최신 패치까지 보여 준다. 프로덕션 승인 용례와 맞는다 | 출처가 u.gg 와 다르고(픽률·밴율 0.5~1.3%p) 표본이 열 배 작다. **공개 화면에 두 출처가 섞인다** — 섞지 않는 것이 이 저장소의 규칙이다 |
| **C. 싣되 구간을 갈라 보인다** | 섞지 않는다. 표본 수와 「출처가 다르다」를 화면에 적고, 완성된 패치만 싣는다 | 화면이 복잡해진다. 「왜 두 구간이냐」를 읽는 사람에게 설명해야 한다 |

## 결정

### 결정 1 — **나(헤더에서 읽는다)** 를 택한다

**이번에 코드를 고쳐야 하는 이유가 「한도를 박아 둔 것」이다.** 같은 일을 다시 만들지
않는다. 기본값은 지금 값(개인 키 한도에서 남긴 값)으로 두고, 응답 헤더를 보면 거기에
맞춘다 — **헤더를 못 읽으면 지금처럼 돈다.** 가는 같은 함정을 다시 파는 것이고, 다는
근거 없는 수다.

### 결정 2 — **C(구간을 갈라 싣는다).** 주인이 골랐다 (2026-11-18)

**약관이 「해도 된다」를 명시하지는 않았다.** 금지 목록에 챔피언 집계가 없고 승인 용례에
「특정 선수 없는 집계」가 있다는 것까지가 읽어서 확인한 것이고, 그 사이는 판단이다.
주인이 C 를 골랐다.

**C 를 고른 이유는 약관이 아니라 이 저장소의 규칙이다.** 출처를 섞지 않기로 했고, 공개
화면에서 그 규칙을 어기면 「값이 튀는 지점」이 실제 변화처럼 읽힌다. B 는 그것을 어긴다.
A 는 막아 둔 이유가 없어졌는데 그대로 두는 것이 된다.

#### 구현하지 않는다 — **Production 키가 먼저다**

**이것은 선호가 아니라 약관이다.** 개인·개발 키로는 「공개용 애플리케이션을 돌릴 수
없다」(오픈 알파·베타 포함). 지금 키는 개발 키 한도다. **키가 나오기 전에 C 를 구현하면
그 자체가 위반**이므로, 아래를 전부 만족할 때까지 `docs/site` 와 정적 API 는 지금 범위를
유지한다.

| 게이트 | |
| --- | --- |
| 1 | Production 키 발급 — 헤더가 `500:10,30000:600` |
| 2 | 포털 제품 설명을 현재 상태로 갱신(권역 `kr`·`euw1`·`na1`) |
| 3 | 기능 변경 감사 — "Any new features or changes to a product must be audited" 에 해당하는지 포털에서 확인 |

#### C 가 뜻하는 것 — 구현 명세

**한 챔피언의 시계열에 두 출처를 이어붙이지 않는다.** 지금 정적 API 의
`champions/<id>.json` 은 `history` 배열 하나에 패치를 쌓는다. 거기에 직접 집계 패치를
덧붙이면 **그것이 바로 출처를 섞는 것**이다. 그래서 갈라 둔다.

| | |
| --- | --- |
| 자료 | 직접 집계를 **별도 이름 공간**에 둔다. u.gg 구간의 `history` 배열은 건드리지 않는다 |
| 싣는 패치 | **완성된 패치만.** 진행 중인 패치는 안 싣는다 — 이미 화면에 그 까닭을 적어 두었다 |
| 화면에 적는 것 | 패치별 **표본 판수** · 「u.gg 와 출처가 다르다」(픽률·밴율 0.5~1.3%p) · **두 구간을 나란히 읽지 말라**는 주의 |
| 안 싣는 것 | 특정 이용자를 가리키는 칸은 애초에 수집 단계에서 버린다([ADR 0010](0010-riot-api-direct-aggregation.md)). Augment · 아레나 아이템 승률은 약관이 금지한다 |

#### 완료 기준 — 테스트로 먼저 쓴다

[extension](../extension.md) 의 규칙대로 완료 기준을 테스트로 먼저 쓰고, **조용히 틀리는
결함을 잡는 장치를 같이 둔다.** 지금은 **쓰지 않는다** — 통과할 수 없는 테스트를 `main`
에 두면 `check-all` 이 막힌다. 키가 나온 뒤 구현과 같은 커밋에 넣는다.

| 테스트 | 무엇을 막나 |
| --- | --- |
| 한 챔피언의 `history` 안에 두 출처가 섞이면 멈춘다 | **이 결정의 핵심.** 지금 있는 「직접 집계가 섞이면 멈춘다」(`tests/test_site_api.py`)를 **지우지 않고 이 꼴로 바꾼다** |
| 직접 집계 구간의 모든 행에 표본 판수가 있으면 통과 | 표본을 안 적고 싣는 것을 막는다 |
| 진행 중인 패치가 0건 | 덜 찬 패치가 새는 것을 막는다 |
| 직접 집계 구간의 픽률 합이 10.00 | **합계 대조** — 파싱이 조용히 틀리는 것을 잡는다 |
| 기존 `16_13 → 16_14` 목록이 바이트까지 같다 | **알려진 출력 대조** — 이미 있다. 공개 범위를 넓히면서 기존 구간을 건드리지 않았는지 본다 |

#### 이 결정이 대체하는 줄

[ADR 0016](0016-static-api-and-local-qa.md) 의 「공개 범위 — u.gg 패널 구간만 싣는다」와
[extension](../extension.md) 의 같은 줄을 **구현 시점에** 대체한다. 지금은 그 줄들이
그대로 유효하다 — 키가 없으므로.

## 영향

| | |
| --- | --- |
| 얻는 것 | 수집 한도가 25배 열린다. **성적이 오르는 것이 아니라** `obs` 한 벌의 흔들림이 줄어 전향 지점의 성적을 읽을 수 있게 된다([results](../results/README.md#쟀다--채택-0-기준을-넘은-하나가-다른-흔들기에서-사라졌다-2026-11-18)) |
| 비용 | 패치당 저장이 32 → 96 MB(3배 기준). `data/` 는 커밋하지 않는다 |
| 위험 | 한도를 많이 쓰면 429 가 나고, 약관은 "Applications that are in violation of this policy may have their access disabled" 라고 적는다. 헤더에서 읽어 맞추는 쪽이 이 위험을 줄인다 |
| 후속 | 다섯째 전향 지점은 앞 넷과 **표본 크기가 다르다.** 대상 종수가 늘어 기준선도 달라진다 — 지점마다 48 ~ 170종으로 이미 다르므로 새로 생기는 문제는 아니지만 적어 둔다 |
| 안 바뀌는 것 | u.gg 구간의 결과(① ② ③)는 **한 자리도 안 바뀐다.** 키 없이 그대로 나온다 |

## 재검토 조건

- ~~**헤더가 `500:10,30000:600` 으로 안 나오면** — 프로덕션 키가 아니다. 이 ADR 의 결정 1 을
  구현하지 않고, 왜 다른지 적는다~~ → **걸렸다 (2026-11-18).** 포털이 `DEVELOPMENT API KEY`
  이고 한도가 1초 20 · 2분 100 이다. 결정 1 을 구현하지 않았다. 신청이 더 필요하다
- **Production 키가 발급되면** — 헤더로 한도를 확인하고 결정 1 을 구현한다. 신청할 때
  제품 설명의 권역을 세 개로 고친다
- 키가 거절·회수되면 — 개인 키 한도로 되돌아간다. 결정 1 의 기본값이 그 값이라 코드는
  그대로다. 공개 범위는 **되돌린다**(개인 키로는 공개가 금지다)
- 약관의 Game Integrity 해석이 픽·밴율 공개를 막는 것으로 확인되면 — 공개 범위를 A 로
  되돌린다
- 캐싱·보관 기간이 약관에 생기면 — `data/riot` 의 보관을 그 기준에 맞춘다
- u.gg 아카이브에 `16_15` 뒤 스냅샷이 다시 생기면 — [ADR 0010](0010-riot-api-direct-aggregation.md)
  의 같은 조건이 그대로 적용된다
