# Ascent — 프로젝트 계획

> Slay the Spire 2의 카드 밸런스를 시뮬레이션으로 검증하고,
> 그 결과를 외부 실측 데이터로 교차 검증하는 시스템

---

## 1. 프로젝트 개요

### 한 줄 정의

게임의 전투 규칙을 결정론적으로 구현하고, LLM이 설계한 플레이어 페르소나가 수천 판을 플레이하게 한 뒤, 카드별 성능 지표를 뽑아 외부 데이터와 대조 검증하는 시스템.

### 왜 이 주제인가

| 관점 | 이유 |
|---|---|
| 진로 유연성 | 게임사 · AI 엔지니어 · AX 세 방향 모두에서 읽히는 구조 |
| 검증 가능성 | 정답지가 외부에 존재 (실측 승률 통계, 개발사 패치 이력) |
| 도메인 강점 | 게임 기획 경력이 스키마 설계와 페르소나 설계에 직접 반영됨 |
| 확장성 | 최소 버전이 명확하고, 시간이 남으면 단계적으로 확장 가능 |

### 핵심 설계 원칙

**1. LLM과 결정론적 로직의 분리**
전투 판정은 룰 엔진이 담당하고 LLM은 개입하지 않는다. LLM은 페르소나 정책을 *생성*하는 단계와 결과를 *해석*하는 단계에만 관여한다.

- 재현성: 같은 시드 → 같은 결과
- 비용: 수천 판을 돌려도 LLM 호출은 페르소나당 수 회
- 신뢰성: 모델이 헛소리를 해도 시뮬레이션 결과는 오염되지 않음

이 경계를 코드로도 지킨다 — `src/ascent/engine/` 아래에는 LLM 호출이 들어가지 않는다([`AGENTS.md`](../AGENTS.md)).

**2. 정책 생성 후 코드 실행**
매 턴 LLM에 묻지 않는다. LLM이 행동 정책(구조화된 규칙 세트)을 한 번 만들고, 코드가 그것을 반복 실행한다. 정책이 텍스트로 남으므로 "왜 그렇게 플레이했는지" 설명이 가능하다.

**3. 데이터와 코드의 분리**
카드·적 데이터를 JSON으로 외부화한다. 밸런스 수치를 바꿔가며 실험하려면 필수이고, 카드 12장 → 80장 확장도 이 설계가 있어야 가능하다.

**4. 외부 정답지 기반 검증**
자기가 만든 시스템을 자기가 평가하는 순환을 피한다. 검증 기준은 전부 프로젝트 바깥에서 가져온다.

**단일 캐릭터인 이유**: 네크로바인더(동료 시스템), 리전트(별 자원)는 전투 시스템을 하나 더 만드는 수준의 부담. 또한 캐릭터를 늘려도 방법론의 타당성이 강해지지 않는다 — 표본만 늘 뿐이다.

**Act 1 한정의 알려진 한계**: 후반 스케일링형 카드(파워류)가 저평가된다. 이는 결함이 아니라 분석 대상이다 — 실측 데이터에도 Act 승률과 Run 승률이 분리돼 있으므로, 그 격차를 설명하는 것이 리포트의 한 챕터가 된다.

> **이 표의 결정들은 아직 ADR이 아니다.** 코드가 없어 후보 비교가 공허하기 때문에 미뤘고, **Phase 1 착수 전에 [`adr/`](adr/)로 옮긴다.** [`followups.md`](followups.md) 2번.

## 3. 페르소나 설계

### 문제 인식

단순 반응형 정책("버프가 없으면 버프, HP 낮으면 회복")은 밸런스 분석에 쓸 수 없다. 상대가 한 대만 맞으면 죽는 상황에서 버프를 거는 건 손해이고, 실제 플레이어는 그런 판단을 하지 않기 때문이다.

### 해결: 우선순위 규칙이 아닌 판단 순서

모든 페르소나가 매 턴 동일한 순서로 판단한다.

```
1. 이번 턴에 적을 죽일 수 있는가?
   → 가능한 카드 조합의 기대 데미지 ≥ 적 잔여 HP
   → 가능하면 무조건 실행 (버프·회복 안 함)

2. 다음 턴에 내가 죽는가?
   → 적 인텐트 예상 데미지 ≥ 내 HP + 블록
   → 위험하면 방어/회복

3. 둘 다 아니면
   → 효율 계산 (버프, 덱 순환, 자원 관리)
```

### 페르소나별 차등: 프레임워크가 아니라 인지 정확도

| 페르소나 | 1단계 (킬각) | 2단계 (생존) | 3단계 (효율) |
|---|---|---|---|
| 숙련자 | 조합까지 정확 계산, 크리 확률 반영 | 인텐트 완전 인지, 덱 잔여 추적 | 장기 자원 관리 |
| 일반 | 평균 데미지로만 판단 | 인텐트는 보되 덱 추적 안 함 | 단기 효율만 |
| 초보 | 판단 생략 | 판단 생략 | 코스트 대비 데미지만 |

### 이 설계가 만드는 것

같은 카드·같은 적에 대해 세 페르소나의 클리어율 격차가 나온다.

- 격차가 큰 **카드** = 숙련도 의존적 카드 (초보 트랩 후보)
- 격차가 큰 **적** = 난이도 벽 구간

이것이 이 프로젝트가 실제로 산출하려는 밸런스 인사이트다.

## 4. 검증 설계

프로젝트 신뢰성의 핵심. 두 축으로 교차 검증한다.

### 축 1 — 실측 승률 대조

시뮬레이터의 카드별 승률 기여도를 커뮤니티 통계 사이트(untapped.gg 등)의 실측 데이터와 대조해 스피어만 순위 상관계수를 산출한다.

**알려진 교란 요인**: 실측 승률 델타는 상관관계이지 인과관계가 아니다. 잘하는 플레이어가 좋은 덱에서 뽑는 카드는 승률이 높게 나온다. 시뮬레이터는 통제된 조건이므로 이 교란이 없고, **따라서 불일치가 발생하는 것이 정상이다.**

이 불일치를 먼저 지적하고 원인을 분석하는 것이 리포트의 질을 결정한다.

### 축 2 — 패치 노트 백테스트 (핵심)

**설계**
1. v0.107.1 이전 수치로 시뮬레이터를 구성
2. 시뮬레이션을 돌려 "과도함 / 부족함" 판정을 산출
3. v0.107.1 ~ v0.111.0에서 개발사가 실제로 조정한 카드 목록과 대조
4. 탐지율(recall)과 오탐률(false positive rate) 산출

**왜 이게 더 강한가**: 여론과의 일치가 아니라 개발사의 실제 판단과의 일치를 측정한다. 포트폴리오 서술이 "커뮤니티 의견과 상관 0.7"에서 "개발사가 이후 조정한 카드 N개 중 M개를 사전 탐지"로 바뀐다.

## 5. 작업 계획

### Phase 0-A — 스펙 문서 (게임 설치 불필요)

코드를 쓰지 않는 단계. 여기가 부실하면 이후 전 단계에서 되돌아온다.

| # | 작업 | 산출물 |
|---|---|---|
| 0-A-1 | **검증 데이터셋 스냅샷** (최우선) | `datasets/` — 카드별 통계 CSV + 패치 변경 내역 표 |
| 0-A-2 | 데미지 파이프라인 정의 | `spec/damage-pipeline.md` + 미확정 항목은 `spec/open-questions.md` |
| 0-A-3 | 상태이상 명세 | `spec/status-effects.md` |
| 0-A-4 | 카드 후보 선정 | `spec/card-selection.md` — 12~15장 목록 + 선정 근거 |
| 0-A-5 | 턴 진행 순서도 | `spec/turn-flow.md` |
| 0-A-6 | 데이터 스키마 설계 | `spec/data-schema.md` — JSON 구조 정의 |

**0-A-1을 최우선으로 하는 이유**: 패치가 나오면 통계 수치가 바뀐다. v0.111.0 기준 스냅샷을 지금 확보해야 검증 기준선이 고정된다. 패치 노트에서 아이언클래드 카드 변경 내역(카드명 / 변경 전 / 변경 후 / 버프·너프·리워크 분류)을 표로 정리한 것이 백테스트 정답지가 된다.

**0-A-2 주의**: 힘 가산 → 약화 → 취약 → 내림 → 블록 차감 순서가 StS2에서도 유효한지 확인 필요. StS2 신규 상태이상(Plating 등)이 이 파이프라인 어디에 끼는지도. 확정 못 하는 항목은 [`spec/open-questions.md`](spec/open-questions.md)에 적어 나중에 일괄 확인한다.

**0-A-4 주의**: 강한 카드와 약한 카드를 의도적으로 섞어야 한다. 양 극단과 중간이 모두 있어야 순위 상관이 의미를 갖는다.

**0-A-6이 중요한 이유**: 이 스키마 설계가 12장 → 80장 확장을 가능하게 만든다. 카드 효과를 코드에 하드코딩하지 않는 것이 원칙.

### Phase 0-B — 데이터 추출 (게임 설치 후)

StS2는 공식 모딩을 지원하며, 위키에 디컴파일 튜토리얼이 제공된다. 게임 데이터에서 카드·몬스터·패턴을 직접 추출할 수 있다.

| # | 작업 |
|---|---|
| 0-B-1 | 게임 설치 후 디컴파일 (ilspycmd) |
| 0-B-2 | 카드·몬스터·인텐트 패턴 데이터 추출 |
| 0-B-3 | `spec/open-questions.md`의 미확정 항목 일괄 검증 |
| 0-B-4 | 적 3종 확정 (패턴이 명확한 것 우선) |
| 0-B-5 | 카드 범위 확장 여부 판단 |

**이 단계가 해결하는 것**: 위키에는 적 수치는 있으나 **행동 패턴 로직이 불완전하다.** 어떤 조건에서 어떤 기술이 나오는지가 문서화돼 있지 않은 경우가 많고, 이것이 없으면 페르소나의 "생존 판단"이 성립하지 않는다. 게임 데이터에서 추출하면 이 구멍이 메워진다.

**대안 (게임 설치가 어려울 경우)**: 확률 분기 없이 결정론적으로 순환하는 적만 골라 회피. 또는 해당 적과 20판 정도 직접 플레이하며 인텐트 순서를 기록해 역추출. 후자의 경우 README에 "위키 미기재 패턴은 플레이 로그로 역추출"이라고 명시하면 그 자체로 좋은 재료가 된다.

**주의**: 디컴파일한 코드나 원본 데이터 파일을 리포지토리에 올리지 않는다. 추출한 수치를 자체 형식 JSON으로 정리한 것까지만 포함하고, README에 "v0.111.0 게임 데이터에서 추출, 원본 미포함"을 명시한다. `.gitignore`와 pre-commit의 `check-added-large-files`가 이를 막는다.

### Phase 1 — 룰 엔진 (LLM 없음)

순수 파이썬. 이 프로젝트에서 코딩 역량이 실제로 붙는 유일한 구간.

| # | 작업 | 비고 |
|---|---|---|
| 1-1 | 데이터 로더 (JSON → 객체) | pydantic 으로 스키마 검증 |
| 1-2 | 코어 객체 (Player, Enemy, Card, CombatState) | 상태 그릇만 먼저 |
| 1-3 | **데미지 계산 함수 + 단위 테스트** | 테스트를 먼저 작성 |
| 1-4 | 덱 관리 (드로우·셔플·버림·소진) | 시드를 인자로 받아 재현 보장 |
| 1-5 | 턴 루프 | 행동은 일단 랜덤 |
| 1-6 | 배치 러너 (N판 → CSV) | 승률·턴수·잔여HP·카드 사용 횟수 |
| 1-7 | 실제 게임과 대조 검증 | 최소 5~10 케이스 |

**착수 전 선행 조건**: 0-A 완료 + [2장의 범위 결정을 ADR로 이관](followups.md).

**1-3이 이 Phase의 핵심.** "힘 2, 취약 상태에서 타격은 N 데미지" 같은 케이스를 10개 정도 만들어두면 이후 코드를 고쳐도 안전하다. 데미지 공식 하나가 틀리면 프로젝트 전체 결과가 무의미해진다.

**완료 기준**: 덱 + 적 → 승률 파이프라인이 돌고, 데미지 계산이 실제 게임과 일치.

**작업 습관 (이 구간 한정)**
- AI가 준 코드를 머지하기 전에 한 줄씩 왜 이런지 스스로 설명해본다. 막히는 줄이 현재의 구멍이다.
- 에러가 나면 AI에 던지기 전에 3분간 혼자 읽는다. 어느 파일 몇 번째 줄, 무슨 타입 문제인지까지만 파악하고 넘어간다.

### Phase 2 — 에이전트

| # | 작업 | 비고 |
|---|---|---|
| 2-1 | 행동 인터페이스 분리 | `choose_action(state) -> Card` |
| 2-2 | 판단 순서 구현 | 킬각 → 생존 → 효율 |
| 2-3 | 페르소나 3종 인지 한계 차등 | 입력 정보를 다르게 제공 |
| 2-4 | LLM 정책 생성 | 구조화 출력(JSON), 페르소나당 수 회 호출 |
| 2-5 | LLM 직접 조작 모드 (선택) | 100판만, 비교용 |
| 2-6 | 평가 하네스 | 프롬프트 변경 시 자동 회귀 비교 |

**착수 전 선행 조건**: LLM 호출 방식 ADR ([`followups.md`](followups.md) 3번). 제공자는 Anthropic Claude로 정했으나 구조화 출력을 무엇으로 강제할지는 미정.

**2-1이 설계의 요점.** 랜덤 정책·규칙 정책·LLM 정책이 모두 동일 인터페이스를 구현하게 하면 이후 비교 실험이 쉬워진다.

**2-5의 가치**: 정책 모드와 직접 조작 모드의 결과·비용·지연을 비교하면 "왜 정책 생성 방식을 택했는가"를 숫자로 답할 수 있다. 선택 사항이지만 포트폴리오 재료로는 강하다.

**2-6은 과소평가되는 항목**: LLM 시스템에서 "돌아간다"와 "잘 된다"는 다르다. 평가셋을 만들고 회귀 테스트를 돌리는 능력이 데모와 제품을 가른다.

---

### Phase 3 — 분석과 검증

| # | 작업 | 비고 |
|---|---|---|
| 3-1 | 지표 정의 | 사용률 / 사용 시 승률 / **덱 포함 시 승률 변화** |
| 3-2 | 페르소나 격차 분석 | 숙련도 의존 카드, 난이도 벽 식별 |
| 3-3 | 분석 에이전트 | 통계 → 자연어 리포트 |
| 3-4 | **외부 검증 2축** | 실측 승률 상관 + 패치 백테스트 |
| 3-5 | 밸런스 패치 실험 | 죽은 카드 수치 조정 후 재측정 |

**3-1에서 가장 의미 있는 지표**는 "덱에 포함됐을 때와 아닐 때의 승률 차이"다. 사용률만으로는 카드 성능을 알 수 없다.

**3-5가 최종 산출물**: 어떤 수치를 왜 바꿨고, 바꾼 뒤 클리어율과 사용률이 어떻게 달라졌는지의 before/after 비교표. 이것이 있어야 프로젝트가 완결된다.

---

### Phase 4 — 정리

| # | 작업 |
|---|---|
| 4-1 | README를 결과로 채운다 |
| 4-2 | 서술 3종 (게임사 / AI 엔지니어 / AX) |
| 4-3 | 포트폴리오 통합 |

**4-1의 성격이 바뀌었다.** [`README.md`](../README.md)는 이미 있다 — 문제 정의·아키텍처·검증 방법·알려진 한계가 들어가 있고 결과 항목만 비어 있다. 이 단계에서 할 일은 "쓰기"가 아니라 "결과로 채우기"다.

**4-2 서술 방향**

| 대상 | 강조점 |
|---|---|
| 게임사 | 밸런스 검증 방법론, 플레이테스트 자동화 |
| AI 엔지니어 | 에이전트 설계, LLM/결정론 분리, 평가 체계 |
| AX | 수동 검증 업무 자동화, before/after 정량 지표 |

내용은 동일하고 강조점만 다르다. 프로젝트 완료 후 하루면 되는 작업.

**4-3 포트폴리오 배치**

```
출시작 (4인 팀 기획 전반, 실무 증명)
  └ 제약 조건 → 판단 기준 → OP.GG 3만 노출 → 전환 실패 원인 분석

역기획서 (시스템 분석력)
  └ 상용 게임을 뜯어 시스템을 역으로 문서화

Ascent (분석을 코드와 AI로 확장)   ← 이 프로젝트
  └ "분석한 시스템을 직접 구현하고 검증까지 자동화"

인턴십 + 부트캠프
```

역기획서와 이 프로젝트를 나란히 두는 것이 핵심. "분석만 하던 사람이 검증까지 한다"는 성장 서사가 한눈에 보인다.

## 6. 기술 스택

버전의 단일 기준은 [`requirements.txt`](../requirements.txt)와 [`requirements-dev.txt`](../requirements-dev.txt)다. 선택 근거는 [ADR-0001](adr/0001-python-environment-and-tooling.md)에 있다.

### 필수 — 런타임

| 기술 | 용도 |
|---|---|
| Python 3.11 | 룰 엔진, 시뮬레이션 |
| pandas | 로그 집계, 지표 산출 (3-1) |
| scipy | 스피어만 순위 상관계수 (3-4) |
| pydantic | 카드·적 데이터 스키마 검증, LLM 구조화 출력 파싱 실패 처리 (1-1, 2-4) |
| python-dotenv | API 키를 코드에 두지 않는다 |
| matplotlib | 결과 시각화 — 발표에 화면이 필요하다 (3) |
| **anthropic** | 페르소나 정책 생성, 분석 리포트 (2-4, 3-3) |
| JSON | 카드·적 데이터 스키마 |
| Git | 버전 관리 |

**LLM 제공자는 Anthropic Claude로 확정했다.** 모델은 `claude-opus-5`(`.env`의 `ASCENT_LLM_MODEL`). 페르소나 정책을 구조화 JSON으로 뽑는 작업이라 tool use 기반 구조화 출력이 안정적이고, 호출이 페르소나당 수 회뿐이라 모델 등급을 낮출 이유가 없다. **호출 방식은 아직 미정이다** — [`followups.md`](followups.md) 3번.

**스키마 형식은 JSON 단독이다.** 초안은 "JSON/YAML"로 열어 뒀으나 두 형식을 다 받으면 로더가 갈리고 "어느 쪽이 기준인가"가 생긴다. 되돌리려면 `requirements.txt` 한 줄이므로 비용은 낮다.

### 필수 — 개발 도구

| 기술 | 용도 |
|---|---|
| pytest · pytest-cov | 데미지 계산 단위 테스트 (1-3). **절대 줄이지 않는 항목** |
| ruff | 린팅·포매팅 (flake8 + black + isort 대체) |
| mypy | 정적 타입 검사 |
| pre-commit | 커밋 전 ruff 자동 실행 |

**초안에는 pytest만 있었다.** SKALA 강의(`데이터 분석을 위한 Python 이해`)가 이 넷을 하나의 세트로 가르치고, 계획서가 "절대 줄이지 않을 두 가지"로 꼽은 데미지 계산 정확성에 직접 붙는 도구들이라 필수로 올렸다.

ruff 규칙은 강의가 제시한 `E`·`F`·`I`·`UP`에 `B`(flake8-bugbear)를 더했다. 가변 기본 인자나 루프 변수 캡처처럼 "돌긴 도는" 결함을 잡는다.

### 선택

`ilspycmd` / .NET SDK (Phase 0-B 한정), SQLite (로그가 CSV로 감당 안 될 때).

### 도입하지 않는 것과 그 이유

| 기술 | 미도입 사유 |
|---|---|
| Vector DB / RAG | 검색할 문서가 없음. 이 프로젝트에 들어갈 자리가 없음 |
| LangChain / LangGraph | 정책 생성이 단발성 호출이라 오케스트레이션이 과함. 단, 분석 에이전트를 다단계로 쪼갤 경우 재검토 |
| FastAPI | 시뮬레이터를 API로 감쌀 필요가 현재 없음 |
| uv / poetry | 의존성이 6개. 잠금 파일의 이득보다 도구를 하나 더 설명해야 하는 비용이 큼 ([ADR-0001](adr/0001-python-environment-and-tooling.md)) |
| Docker / Streamlit | 보여 줄 결과가 나온 뒤에 붙인다. 지금 만들면 빈 화면을 컨테이너에 넣는 일 ([`followups.md`](followups.md) 5번) |

**README에 미도입 사유를 명시한다.** 안 쓴 이유를 설명할 수 있는 것이 도구를 판단할 줄 안다는 증거다.
