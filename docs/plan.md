# Ascent — 프로젝트 계획

> Slay the Spire 2의 카드 밸런스를 시뮬레이션으로 검증하고,
> 그 결과를 외부 실측 데이터로 교차 검증하는 시스템

---

## 1. 프로젝트 개요

### 한 줄 정의

게임의 전투 규칙을 결정론적으로 구현하고, LLM이 설계한 플레이어 페르소나가 수천 판을 플레이하게 한 뒤, 카드별 성능 지표를 뽑아 외부 데이터와 대조 검증하는 시스템.

### 왜 이 주제인가

| 관점 | 이유 |
|---|---|
| 진로 유연성 | 게임사 · AI 엔지니어 · AX 세 방향 모두에서 읽히는 구조 |
| 검증 가능성 | 정답지가 외부에 존재 (실측 승률 통계, 개발사 패치 이력) |
| 도메인 강점 | 게임 기획 경력이 스키마 설계와 페르소나 설계에 직접 반영됨 |
| 확장성 | 최소 버전이 명확하고, 시간이 남으면 단계적으로 확장 가능 |

### 핵심 설계 원칙

**1. 룰 엔진은 판정을 맡고, AI는 그 위에서 판단한다**

**전투 판정에는 LLM이 개입하지 않는다.** 데미지 계산, 덱 셔플, 턴 진행은 전부 결정론적 파이썬이다. 같은 시드에 같은 결과가 나와야 검증이 성립한다.

**그 위에서 AI가 판단한다.** 룰 엔진은 AI 에이전트가 쓰는 **환경**이다. 무대가 튼튼해야 에이전트가 의미 있게 행동할 수 있다.

```text
[룰 엔진 = 환경]   결정론적. 게임판 그 자체
       ↑ 도구로 노출
[AI 에이전트]      플레이 판단 · 실험 설계 · 결과 해석
```

이 경계를 코드로도 지킨다 — `src/ascent/engine/` 아래에는 LLM 호출이 들어가지 않는다([`AGENTS.md`](../AGENTS.md)).

> **2026-08-24 방향 변경.** 초안은 "LLM은 페르소나 정책을 한 번 만들고 코드가 반복 실행한다"였다. AI 비중을 늘리기로 하면서 **경계를 옮겼지 없애지 않았다** — 전투 판정은 여전히 LLM 밖이다. 구체적으로 어디까지 AI에게 넘길지는 Phase 2에 적었고 일부는 미결정이다.

**2. 정책은 텍스트로 남는다**
AI가 어떻게 판단했는지가 기록으로 남아야 한다. 매 턴 직접 조작하는 모드에서도 판단 근거를 로그로 남긴다. "왜 그렇게 플레이했는지" 설명할 수 없으면 밸런스 분석에 쓸 수 없다.

**3. 데이터와 코드의 분리**
카드·적 데이터를 JSON으로 외부화한다. 밸런스 수치를 바꿔가며 실험하려면 필수이고, 카드 12장 → 80장 확장도 이 설계가 있어야 가능하다.

**4. 외부 정답지 기반 검증**
자기가 만든 시스템을 자기가 평가하는 순환을 피한다. 검증 기준은 전부 프로젝트 바깥에서 가져온다.

## 2. 확정 범위

| 항목 | 결정 | 비고 |
|---|---|---|
| 대상 게임 | Slay the Spire 2 | 직접 플레이 경험 있음 |
| 버전 | v0.111.0 고정 | 2026-08-13 패치 기준. `src/ascent/config.py`의 `GAME_VERSION` 상수 |
| 캐릭터 | 아이언클래드 단일 | 신규 메커닉 없음, 통계 표본 가장 두꺼움 |
| 층 | Act 1 | 유물·덱 변수 최소화, 카드 기여도 격리 측정 가능 |
| 적 | 3종 | 패턴이 확정 가능한 것 우선 |
| 카드 | 12~15장 시작 | 데이터 확보 시 80장까지 확장 |

### 범위 결정 근거

**단일 캐릭터인 이유**: 네크로바인더(동료 시스템), 리전트(별 자원)는 전투 시스템을 하나 더 만드는 수준의 부담. 또한 캐릭터를 늘려도 방법론의 타당성이 강해지지 않는다 — 표본만 늘 뿐이다.

**Act 1인 이유**: 후반으로 갈수록 덱 30장 + 유물 15개로 조합이 폭발해 특정 카드의 기여도를 격리 측정하기 어렵다. Act 1은 통제된 실험 환경에 가깝다.

**Act 1 한정의 알려진 한계**: 후반 스케일링형 카드(파워류)가 저평가된다. 이는 결함이 아니라 분석 대상이다 — 실측 데이터에도 Act 승률과 Run 승률이 분리돼 있으므로, 그 격차를 설명하는 것이 리포트의 한 챕터가 된다.

### 아직 정하지 못한 범위 — **먼저 정해야 한다**

2026-08-24 웹 조사에서 드러났다. 셋 다 게임에서 확인할 항목이 아니라 **결정**이다.

| | 항목 | 왜 지금 정해야 하나 |
|---|---|---|
| **A** | **Act 1 변종** — Overgrowth / Underdocks | Act 1 은 두 갈래이고 **적 풀·엘리트·보스가 통째로 다르다.** 상호 배타적이라 둘 다 하면 적 구현량이 두 배다 |
| **B** | **유물 범위** — 시작 유물만인가, Act 1 획득분까지인가 | Burning Blood(전투 종료 시 6 회복)는 클리어율에 직접 영향을 준다. 뺄 수 없다 |
| **C** | **Ascension 레벨** | 적 HP·피해가 전부 달라지고, 실측 통계와 어느 구간을 맞출지가 여기서 갈린다 |

**C 가 조용한 함정이다.** 초안 어디에도 Ascension 이 없는데 실측 승률은 구간별로 크게 다르다. 시뮬레이터를 A0 로 만들고 A20 통계와 대조하면 상관이 낮게 나오고, **그 원인을 4장이 미리 적어 둔 「교란 요인」으로 오진하게 된다.**

> **이 표의 결정들은 아직 ADR이 아니다.** 코드가 없어 후보 비교가 공허하기 때문에 미뤘고, **Phase 1 착수 전에 [`adr/`](adr/)로 옮긴다.** [`followups.md`](followups.md) 2번.

## 3. 페르소나 설계

### 문제 인식

단순 반응형 정책("버프가 없으면 버프, HP 낮으면 회복")은 밸런스 분석에 쓸 수 없다. 상대가 한 대만 맞으면 죽는 상황에서 버프를 거는 건 손해이고, 실제 플레이어는 그런 판단을 하지 않기 때문이다.

### 해결: 우선순위 규칙이 아닌 판단 순서

모든 페르소나가 매 턴 동일한 순서로 판단한다.

```
1. 이번 턴에 적을 죽일 수 있는가?
   → 가능한 카드 조합의 기대 데미지 ≥ 적 잔여 HP
   → 가능하면 무조건 실행 (버프·회복 안 함)

2. 다음 턴에 내가 죽는가?
   → 적 인텐트 예상 데미지 ≥ 내 HP + 블록
   → 위험하면 방어/회복

3. 둘 다 아니면
   → 효율 계산 (버프, 덱 순환, 자원 관리)
```

### 페르소나별 차등: 두 축으로 나눈다

**셋 다 인텐트는 본다.** 인텐트를 안 보는 것은 초보가 아니라 게임을 하지 않는 것이다. 차이는 **그것을 보고 무엇을 하느냐**에 있다.

| | 인텐트 | 적 패턴 | 덱 잔여 | 조합 계산 대행 | 고민 시간 |
|---|---|---|---|---|---|
| **숙련자** | ✅ | ✅ 외움 | ✅ 추적 | 전부 | 충분히 |
| **일반** | ✅ | ❌ | ❌ | 일부 | 보통 |
| **초보** | ✅ | ❌ | ❌ | ❌ | 짧게 |

차등의 축은 둘이다.

| 축 | 무엇을 바꾸나 | 현실의 무엇 |
|---|---|---|
| **정보** | 적 패턴·덱 잔여를 알려주는가, 조합 계산을 대신 해주는가 | 몰라서 못 함 |
| **고민 시간** | 얼마나 깊이 생각하게 하는가 (`effort`) | 안 따져봐서 못 함 |

**초보와 일반 사이는 정보가 아니라 고민 시간만 다르다.** 같은 것을 보고도 한쪽은 계산하고 한쪽은 하지 않는다.

같은 상황(`Chomp 16 피해 예정`)에서 셋의 행동이 이렇게 갈린다.

```text
초보    "16 오네, 방어해야지"  → 방어 카드 한 장(5 블록) → 11 맞음
                                  보긴 봤는데 16을 막으려면 몇이 필요한지 세지 않음

일반    "16이면 블록 16 이상 필요. Defend 둘이면 10, 에너지가 모자라니 6은 맞자"
                                  계산은 하되 이번 턴까지만

숙련자  "16 온다. 그런데 다음은 Swipe 6×2로 약하니 지금 좀 맞고
         다음 턴에 공격을 몰아넣는 게 이득이다"     패턴을 아니까 손해를 감수함
```

### 모델 등급으로 나누지 않는다

한때 검토했다가 접었다 — 숙련자는 Opus, 초보는 Haiku 로 두는 방식이다.

**약한 모델은 "초보처럼" 플레이하지 않고 그냥 "다르게" 플레이한다.** 인간 초보의 실수에는 패턴이 있지만(회복 카드 과대평가, 블록을 어중간하게 쌓음) 약한 모델은 그런 식으로 틀리지 않는다. 그리고 "Haiku = 초보"라는 주장을 검증할 방법이 없다.

**셋 다 같은 모델을 쓴다.** 그래야 차이가 나면 그것이 정보 차이거나 고민 차이지 모델 성격 차이가 아니다. 코드를 보면 무엇을 숨겼는지 확인된다.

### 이 설계가 만드는 것

같은 카드·같은 적에 대해 세 페르소나의 클리어율 격차가 나온다.

- 격차가 큰 **카드** = 숙련도 의존적 카드 (초보 트랩 후보)
- 격차가 큰 **적** = 난이도 벽 구간

이것이 이 프로젝트가 실제로 산출하려는 밸런스 인사이트다.

### 두 축을 갈라 쓰면 처방이 갈린다

정보 축과 고민 축을 따로 움직이면 이 질문에 답할 수 있다 — **초보가 못 하는 이유가 몰라서인가, 안 따져봐서인가.**

| 무엇을 늘렸더니 승률이 오르나 | 원인 | 처방 |
|---|---|---|
| 정보 | **몰라서** | 튜토리얼·UI 를 고친다 |
| 고민 시간 | **안 따져봐서** | 카드를 단순하게 만든다 |

같은 "초보가 못 쓰는 카드"라도 처방이 정반대다. **어느 쪽인지 실험으로 가려내는 것**이 이 프로젝트가 낼 수 있는 가장 날카로운 결과다.

**조합 수는 미결정이다.** 정보 3단계 × 고민 3단계 = 9조합을 모두 돌리면 원인 분리가 되고, 대각선 3개만 돌리면 초안과 판 수가 같다. [`followups.md`](followups.md).

## 4. 검증 설계

프로젝트 신뢰성의 핵심. 두 축으로 교차 검증한다.

### 축 1 — 실측 승률 대조

시뮬레이터의 카드별 승률 기여도를 커뮤니티 통계 사이트(untapped.gg 등)의 실측 데이터와 대조해 스피어만 순위 상관계수를 산출한다.

**알려진 교란 요인**: 실측 승률 델타는 상관관계이지 인과관계가 아니다. 잘하는 플레이어가 좋은 덱에서 뽑는 카드는 승률이 높게 나온다. 시뮬레이터는 통제된 조건이므로 이 교란이 없고, **따라서 불일치가 발생하는 것이 정상이다.**

이 불일치를 먼저 지적하고 원인을 분석하는 것이 리포트의 질을 결정한다.

**교란 요인이 셋 더 있다** (2026-08-24 추가).

| # | 교란 | 왜 |
|---|---|---|
| 1 | **문맥 평균끼리의 비교** | 실측의 카드별 승률도 문맥 평균이고 시뮬레이터도 그렇다. 다만 **문맥의 분포가 다르다** — 실측은 Act 3까지, 시뮬은 Act 1 이다 |
| 2 | **Ascension 구간 불일치** | 2장 미결정 C. 맞추지 않으면 상관이 낮게 나오고 원인을 오진한다 |
| 3 | **표본 수를 모른다** | 출처가 표본 수를 공개하지 않는다. 저표본 카드의 순위는 사실상 잡음이고, 그 잡음이 상관을 0 쪽으로 끌어내린다 ([`../datasets/README.md`](../datasets/README.md)) |

**3 이 특히 위험하다.** 아이언클래드 카드 승률이 대략 45~57% 구간에 몰려 있어 인접 카드 간 실제 차이는 0.1~0.3%p 다. 표본이 적으면 순위가 통째로 뒤섞이고, 스피어만은 순위만 쓰므로 그대로 얻어맞는다. **대응은 픽률을 표본 수의 대리 지표로 써서 저픽률 카드를 거르거나 가중치를 주는 것**이고, 그렇게 했다는 사실을 리포트에 적는다.

### 축 2 — 패치 노트 백테스트 (핵심)

**설계**
1. v0.107.1 이전 수치로 시뮬레이터를 구성
2. 시뮬레이션을 돌려 "과도함 / 부족함" 판정을 산출
3. v0.107.1 ~ v0.111.0에서 개발사가 실제로 조정한 카드 목록과 대조
4. 탐지율(recall)과 오탐률(false positive rate) 산출

**왜 이게 더 강한가**: 여론과의 일치가 아니라 개발사의 실제 판단과의 일치를 측정한다. 포트폴리오 서술이 "커뮤니티 의견과 상관 0.7"에서 "개발사가 이후 조정한 카드 N개 중 M개를 사전 탐지"로 바뀐다.

**축 1의 교란 요인이 늘면서 이 축의 무게가 더 커졌다.** 개발사도 카드를 조정할 때 문맥 평균을 본다 — Rampage 를 9→10 으로 올린 것은 특정 콤보 때문이 아니라 전반적으로 약해서다. **시뮬레이터가 재는 것과 개발사가 보는 것이 같은 종류의 값이다.** 축 1이 앓는 병을 축 2는 앓지 않는다.

**창은 확보됐다** (2026-08-24 확인). v0.111.0 이 최신이고 창 안에 패치 7개가 있다 — v0.107.1 · 0.108.0 · 0.109.0 · 0.109.1 · 0.110.0 · 0.110.1 · 0.111.0. v0.111.0 의 아이언클래드 변경 3건은 수치까지 확보했다. **나머지 6개 패치의 변경 내역을 모아야 탐지율·오탐률이 통계적으로 의미를 갖는다.**

### Phase 2 — 에이전트

**2026-08-24 에 이 Phase 를 키우기로 정했다.** AI 를 조연이 아니라 중심에 놓는다. 다만 **어디까지 넘길지는 아직 정하지 않았다** — 아래 「미결정」 참조.

| # | 작업 | 비고 |
|---|---|---|
| 2-1 | 행동 인터페이스 분리 | `choose_action(state) -> Card` |
| 2-2 | 판단 순서 구현 | 킬각 → 생존 → 효율 |
| 2-3 | **페르소나 3종 차등** | 정보 축 + 고민 시간(`effort`) 축. 3장 참조 |
| 2-4 | LLM 정책 생성 | 구조화 출력(JSON) |
| 2-5 | LLM 직접 조작 모드 | **선택이 아니라 비교군으로 승격.** 100판 |
| 2-6 | 평가 하네스 | 프롬프트 변경 시 자동 회귀 비교 |
| 2-7 | **룰 엔진을 에이전트의 도구로 노출** | 신규 |

**착수 전 선행 조건**: LLM 호출 방식 ADR ([`followups.md`](followups.md) 3번).

**2-1이 설계의 요점.** 랜덤 정책·규칙 정책·LLM 정책·직접 조작이 모두 동일 인터페이스를 구현하게 하면 비교 실험이 쉬워진다. AI 비중을 어디까지 늘리든 이 인터페이스는 안 바뀐다.

**2-5를 승격한 이유**: 정책 모드와 직접 조작 모드의 결과·비용·지연을 비교하면 "왜 이 방식을 택했는가"를 숫자로 답할 수 있다. AI 가 중심이 된 이상 이 비교는 선택이 아니다.

**2-7이 새로 생긴 것.** 룰 엔진을 에이전트가 호출할 수 있는 도구로 감싼다. 그러면 이런 것이 가능해진다.

> **사람**: "Body Slam 픽률이 왜 8% 인지 알아내라"
> **에이전트**: 시뮬레이터를 돌린다 → "블록 없는 덱에서 약하다" → 블록 덱으로 다시 돌린다 → "여기선 강하다" → **"약한 카드가 아니라 조건부 카드입니다. 근거는 이 실험 3개입니다"**

에이전트가 **스스로 실험을 설계하고 돌리고 결론을 낸다.** 사람이 지표를 미리 정해 주지 않는다.

그리고 이 결과도 **똑같이 패치 백테스트로 검증할 수 있다** — "에이전트가 스스로 지목한 문제 카드 N개 중 M개를 개발사가 실제로 조정했다." 4장의 검증 축이 그대로 살아 있고 주인공만 사람에서 에이전트로 바뀐다.

**2-6은 과소평가되는 항목**: LLM 시스템에서 "돌아간다"와 "잘 된다"는 다르다. 평가셋을 만들고 회귀 테스트를 돌리는 능력이 데모와 제품을 가른다. **AI 비중이 커질수록 더 중요해진다.**

#### 미결정 — Phase 2 착수 전에 정한다

| 항목 | 후보 |
|---|---|
| AI 를 어디까지 중심에 놓을 것인가 | ① 매 턴 직접 조작 / ② 정책 자기 개선 루프 / ③ 시뮬레이터를 도구로 쓰는 분석 에이전트 / ④ 역할 분담 멀티 에이전트 |
| 페르소나 조합 수 | 9조합(정보 3 × 고민 3) / 대각선 3조합 |
| API 예산 | ① 을 몇 판까지 돌릴지가 여기서 갈린다 |

**① 만으로는 통계가 안 나온다.** Act 1 한 판이 대략 80턴이라 1,000판이면 8만 회 호출이다. 승률 통계에는 수백~수천 판이 필요하므로 ① 은 소규모 비교군으로 두고 주 측정은 다른 방식이어야 한다.

**2-6은 과소평가되는 항목**: LLM 시스템에서 "돌아간다"와 "잘 된다"는 다르다. 평가셋을 만들고 회귀 테스트를 돌리는 능력이 데모와 제품을 가른다.

### Phase 3 — 분석과 검증

| # | 작업 | 비고 |
|---|---|---|
| 3-1 | 지표 정의 | 사용률 / 사용 시 승률 / **덱 포함 시 승률 변화** / **문맥 의존도** |
| 3-2 | 페르소나 격차 분석 | 숙련도 의존 카드, 난이도 벽 식별 |
| 3-3 | 분석 에이전트 | 통계 → 자연어 리포트 |
| 3-4 | **외부 검증 2축** | 실측 승률 상관 + 패치 백테스트 |
| 3-5 | 밸런스 패치 실험 | 죽은 카드 수치 조정 후 재측정 |

**3-1에서 가장 의미 있는 지표**는 "덱에 포함됐을 때와 아닐 때의 승률 차이"다. 사용률만으로는 카드 성능을 알 수 없다.

**그런데 그것도 "어떤 덱에?"가 빠져 있다.** 슬레이 더 스파이어에서 카드의 값은 고정된 성질이 아니라 덱 문맥의 함수다. Body Slam 은 블록 덱에서 사기이고 그 밖에서는 쓰레기다. "Body Slam 은 48% 카드다"는 애초에 성립하지 않는 문장이다.

그래서 **여러 베이스 덱에 같은 카드를 넣었다 뺐다 하며 승률 변화의 폭을 본다.**

```text
Body Slam            Strike
  공격 덱   −2%        공격 덱   +1%
  블록 덱  +11%        블록 덱   +1%
  평범 덱   −1%        평범 덱   +2%
  → 널뛴다: 문맥 의존   → 안정적: 스탠드얼론
```

이 **널뛰는 폭**이 곧 시너지 의존도다. "이 카드는 수치가 아니라 접근성이 문제다"를 말할 수 있게 된다.

**실측 통계는 원리상 이것을 못 한다.** 실제 유저는 덱도 실력도 제각각이라 "덱만 고정하고 카드 한 장만 바꾸기"가 불가능하다. 관찰과 실험의 차이이고, **시뮬레이터를 만드는 이유가 여기서 선명해진다.**

**카드를 12~15장으로 좁힌 것이 여기서는 이득이다.** 2장 조합이 66쌍이라 전부 훑을 수 있다. 80장이면 3,160쌍이라 조합당 표본이 모자란다.

**알려진 한계**: Act 1 은 덱이 12~15장이라 시너지가 덜 여문다. Act 1 한정이라 파워류가 저평가되는 것과 같은 부류의 한계이고, 마찬가지로 리포트에서 설명할 대상이다.

**3-5가 최종 산출물**: 어떤 수치를 왜 바꿨고, 바꾼 뒤 클리어율과 사용률이 어떻게 달라졌는지의 before/after 비교표. 이것이 있어야 프로젝트가 완결된다.

| python-dotenv | API 키를 코드에 두지 않는다 |
| matplotlib | 결과 시각화 — 발표에 화면이 필요하다 (3) |
| **anthropic** | 페르소나 정책 생성, 분석 리포트 (2-4, 3-3) |
| JSON | 카드·적 데이터 스키마 |
| Git | 버전 관리 |

**LLM 제공자는 Anthropic Claude로 확정했다.** 모델은 `claude-opus-5`(`.env`의 `ASCENT_LLM_MODEL`). 페르소나 정책을 구조화 JSON으로 뽑는 작업이라 tool use 기반 구조화 출력이 안정적이고, 호출이 페르소나당 수 회뿐이라 모델 등급을 낮출 이유가 없다. **호출 방식은 아직 미정이다** — [`followups.md`](followups.md) 3번.

**스키마 형식은 JSON 단독이다.** 초안은 "JSON/YAML"로 열어 뒀으나 두 형식을 다 받으면 로더가 갈리고 "어느 쪽이 기준인가"가 생긴다. 되돌리려면 `requirements.txt` 한 줄이므로 비용은 낮다.

### 필수 — 개발 도구

| 기술 | 용도 |
|---|---|
| pytest · pytest-cov | 데미지 계산 단위 테스트 (1-3). **절대 줄이지 않는 항목** |
| ruff | 린팅·포매팅 (flake8 + black + isort 대체) |
| mypy | 정적 타입 검사 |
| pre-commit | 커밋 전 ruff 자동 실행 |

**초안에는 pytest만 있었다.** SKALA 강의(`데이터 분석을 위한 Python 이해`)가 이 넷을 하나의 세트로 가르치고, 계획서가 "절대 줄이지 않을 두 가지"로 꼽은 데미지 계산 정확성에 직접 붙는 도구들이라 필수로 올렸다.

ruff 규칙은 강의가 제시한 `E`·`F`·`I`·`UP`에 `B`(flake8-bugbear)를 더했다. 가변 기본 인자나 루프 변수 캡처처럼 "돌긴 도는" 결함을 잡는다.

### 선택

`ilspycmd` / .NET SDK (Phase 0-B 한정), SQLite (로그가 CSV로 감당 안 될 때).

### 도입하지 않는 것과 그 이유

| 기술 | 미도입 사유 |
|---|---|
| Vector DB / RAG | 검색할 문서가 없음. 이 프로젝트에 들어갈 자리가 없음 |
| LangChain / LangGraph | 정책 생성이 단발성 호출이라 오케스트레이션이 과함. 단, 분석 에이전트를 다단계로 쪼갤 경우 재검토 |
| FastAPI | 시뮬레이터를 API로 감쌀 필요가 현재 없음 |
| uv / poetry | 의존성이 6개. 잠금 파일의 이득보다 도구를 하나 더 설명해야 하는 비용이 큼 ([ADR-0001](adr/0001-python-environment-and-tooling.md)) |
| Docker / Streamlit | 보여 줄 결과가 나온 뒤에 붙인다. 지금 만들면 빈 화면을 컨테이너에 넣는 일 ([`followups.md`](followups.md) 5번) |

**README에 미도입 사유를 명시한다.** 안 쓴 이유를 설명할 수 있는 것이 도구를 판단할 줄 안다는 증거다.

| **0-A 에서 막힘** | 초안에 없던 리스크다. **코드 한 줄 못 쓰고 스펙 문서만 붙잡는 것이 이 프로젝트에서 가장 그럴듯한 실패 모드다.** 미확정 항목이 5건을 넘으면 그 항목을 피해 가는 쪽으로 범위를 좁히고 Phase 1로 넘어간다 |
| **재현성이 부분적으로 깨짐** | AI 비중을 늘린 대가다. 완전 재현 대신 **모든 호출을 로그로 남겨 「재현 가능한 기록」**을 만든다. 전투 판정 자체는 여전히 결정론적이다 |

### 절대 줄이지 않을 두 가지

1. **1-3 데미지 계산 단위 테스트** — 정확성의 근거
2. **3-4 외부 검증** — 결과의 신뢰성 근거

나머지는 다 줄여도 이 둘은 유지한다. "의미 있는 지표가 나오는가"에 대한 답이 여기 있다.
