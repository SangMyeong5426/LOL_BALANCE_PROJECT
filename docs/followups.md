### 2b · 2d. `rankings` 해독이 커버리지 결정을 가로막고 있다

`rankings` 원본은 다 받았다(807파일). 그런데 **패치 단위가 아니라 챔피언 단위로 흩어져 들어왔다.**

```
16_3  106종 (62%)      15_16  59종 (34%)      14_18  11종 ( 6%)
16_14  73종 (43%)      15_22  44종 (26%)      14_24  10종 ( 6%)
14_16  60종 (35%)      15_17  39종 (23%)      15_7    5종 ( 3%)
14_17  60종 (35%)      16_7   35종 (20%)      14_20   2종 ( 1%)
15_9   59종 (34%)      15_10  26종 (15%)      15_3   15종 ( 9%) · 14_19 13 · 14_22 13
```

**승률은 멀쩡하다** — 챔피언 자체의 승/판이라 남이 없어도 값이 안 변한다. **픽률·밴율은 못 쓴다** — 분모가 「그 역할의 총 판수」라 전 챔피언이 있어야 선다. 대조군 3패치에서 직접 쟀다.

| 패치 | 커버리지 | 픽률 배율 중앙값 | 최소 | 최대 |
| --- | --- | --- | --- | --- |
| 15_14 | 45.6% | 2.48배 | 1.16 | 3.26 |
| 16_9 | 31.4% | 3.06배 | 1.30 | 21.64 |
| 16_13 | 28.3% | 3.37배 | 1.61 | 18.11 |

**한 패치 안에서도 배율이 챔피언마다 다르다.** 상수라면 나눠서 되돌리는데 그럴 수 없다. 역할별 누락 비율이 달라서다.

누락은 **인기 편향이 아니다** — 판수 상위·하위 구간의 보유율이 거의 같다. 아카이브 크롤러가 무작위로 긁었다.

**그래서 임계값 문제가 아니다.** 60% 임계값을 걸어도 픽률이 1.6배 틀린다. 유일하게 남은 길은 **`rankings` payload 가 u.gg 가 계산해 둔 픽률·밴율(또는 분모)을 들고 있는가**이고, 그건 2b 를 해야 안다.

**2026-08-25 추가 — 2b 결과와 무관하게 결정할 수 있다는 쪽으로 기운다.** 처음에는 「payload 에 분모가 있으면 부분 패치를 쓸 수 있다」고 봤으나, 두 가지가 그것과 상관없이 걸린다.

| # | 걸리는 것 |
| --- | --- |
| ① | **평가 단위.** 대표 지표 `precision@15` 는 그 패치의 후보 171종을 다 세워야 성립한다. 14_20 은 챔피언이 2종이다. 피처가 완벽해도 순위를 못 만든다 |
| ② | **수집 시점이 다르다.** 두 엔드포인트의 절대값이 어디에서도 안 맞았다 — 아카이브 스냅샷 시각이 달라서다. `champion_ranking(t) − rankings(t−1)` 로 만든 변화량은 실제 변화와 시점 차이가 뒤섞인 값이 된다 |

여기에 이득이 **632행 / 8,940행 = 6.6%** 라는 점을 더하면, **권고는 「전 챔피언 보유 53패치만 쓴다, 임계값 없음」이다.**

**2026-08-25 결정됨 — [ADR-0002](adr/0002-prediction-point-coverage-criterion.md).** 전 챔피언 보유 53패치만 쓴다, 임계값 없음. 후보 넷(A 53패치만 · B 챔피언×패치 단위 · C 임계값 · D payload 해독)을 비교했다.

D 를 빠르게 확인해 보려 한 두 시도가 실패했고, **그 실패 원인이 D 를 무력화했다** — 두 엔드포인트의 절대값이 어디에서도 안 맞았는데 아카이브 스냅샷 **수집 시각이 다르기** 때문이다. 해독에 성공해도 부분 패치로 만든 추세는 실제 변화와 시점 차이가 뒤섞인다.

### 8. CommunityDragon 에 스킬 피해량이 있다

**「Data Dragon 에 없다」를 「어디에도 없다」로 넘겨짚고 있었다.** 라이엇 게임 데이터를 미러링하는 CommunityDragon 에는 피해량과 계수가 **버전별로** 들어 있다.

```
Ahri Q   BaseDamage [40, 65, 90, 115, 140]
         TotalDamage = BaseDamage + 0.45×AP     ← 툴팁의 {{ totaldamage }} 가 이것
```

**확인한 것**

| | |
| --- | --- |
| 버전 커버리지 | 우리 범위 표본 12개(13.14~16.15) **전부 200** |
| 값 일치 | 쿨다운·코스트가 Data Dragon 과 맞는다 — 8개 중 7개 |
| **함정** | 배열이 0~6랭크 7칸인데 **항목마다 오프셋이 다르다.** Q 코스트만 `[0:maxrank]` 이고 나머지는 `[1:1+maxrank]` |
| **함정** | 필드 이름이 챔피언마다 다르다 — `BaseDamage` · `RBaseDamage` · `RAPCoefficient` |
| 부담 | 챔피언 170종 × 74버전 = **12,580 요청 · 약 2.9 GB**. 지금 `data/` 전체의 7배 |

**얻는 것**: 채점 범위가 25% → 대부분으로 늘어난다. 지금은 13.15 기록 52건 중 13건만 검증된다.

**전량 확보 완료 (2026-08-25).** 전량 12,580 요청이 아니라 **노트에 이름이 오른 챔피언의 그 버전 + 직전 버전**만 받아 2,795쌍으로 줄였다.

| | |
| --- | --- |
| 받음 | **2,788 / 2,788** · 360 MB · 68분 |
| 못 받은 7건 | **전부 신규 챔피언 출시** — briar · hwei · smolder · aurora · mel · yunara · locke |
| 깨진 파일 | **0** (2,788개 전부 파싱 확인) |

**「직전 버전이 없다」는 실패가 아니라 출시 이벤트다.** 일곱 건 모두 그 버전 Data Dragon 에 없고 다음 버전에 있는 것을 확인했다. **채점기가 이 둘을 구분해야 한다** — 지금 코드는 「파일 없음」을 한 가지로만 본다.

**도입하기로 정했다 — [ADR-0005](adr/0005-skill-damage-data-source.md).** 후보 넷을 재 보니 Data Dragon 툴팁은 자리표시자를 풀 값이 응답에 아예 없고(못 푸는 비율이 51%→66% 로 **커진다**), 패치 노트만으로는 조용한 변경 **8.3% 이상**을 못 본다. 읽는 코드는 아직 없다 — 파서가 다음 작업이다.

구 사이트(`lol.timsevenhuysen.com/gamedata/{season}/`)는 2020 까지만 살아 있다 — 2021 이후는 404 다. **우리 범위(2023~2026)는 이쪽으로 못 받는다.**

### 9. 잘린 응답이 재시도를 안 탄다

CommunityDragon 전량 수집(2,795쌍)에서 `15_19/sivir` 하나가 실패했는데, 없는 파일이 아니라 **HTTP 200 으로 오다가 중간에 끊긴 응답**이었다.

```
1차   84,469 B 에서 끊김  →  json.loads 실패
재시도 149,054 B 정상
```

**구조가 이렇게 돼 있다.**

```python
body = get_with_retry(url, attempts=3)   # HTTP 실패만 재시도한다
json.loads(body)                         # ← 여기서 깨져도 재시도가 안 붙는다
```

잘린 응답은 HTTP 로는 성공이라 `get_with_retry` 를 그냥 통과하고, 바깥의 `json.loads` 에서 `ValueError` 로 죽는다. **한 번 더 부르면 멀쩡히 온다.** `fetch-ugg-rankings` 도 같은 모양이다.

### 고쳤다 (2026-08-26)

두 겹으로 막았다. **한 겹으로는 안 된다** — 종료 코드는 curl 이 끊긴 것만 잡고, 서버가 잘못된 `Content-Length` 로 깨끗이 끊으면 curl 도 0 을 낸다.

| 겹 | 자리 | 무엇을 잡나 |
| --- | --- | --- |
| ① | `get()` 이 `result.returncode` 를 본다 | curl 이 끊겼다고 말해 주는 경우 (exit 28) |
| ② | `get_with_retry(..., validate=json.loads)` | curl 은 0 인데 내용이 깨진 경우 |

②가 핵심이다. **검증이 재시도 루프 안으로 들어왔다** — 전에는 받는 쪽에서 따로 `json.loads` 를 불렀고, 그 실패는 영구 실패라 재시도 예산이 한 번도 안 쓰였다. 수집기 네 개에서 중복 검사를 걷어냈다.

**확인한 것**

```
실제 네트워크   큰 파일을 1초에 끊음
              → curl 종료 28(382,311 B 받음)  Retryable 로 잡힘
              옛 코드는 이 382 KB 를 성공으로 돌려줬다

테스트         새 테스트 5개 중 4개가 옛 코드에서 실패한다
              (5번째는 「검증기 없으면 동작 그대로」라 양쪽 통과가 맞다)
```

`get()` 은 그동안 **테스트 커버리지가 0** 이었다 — 기존 테스트가 `get_with_retry` 를 통째로 갈아 끼워 `get_archived` 의 형식 선택만 봤다. 이제 `subprocess.run` 을 갈아 끼우는 층이 생겼다.
