### 2b · 2d. `rankings` 해독이 커버리지 결정을 가로막고 있다

> **닫았다 (2026-08-26).** 2024 하반기 공백을 조사하다 확인했다 — `rankings` 에
> 결측 패치 20개가 들어와 있지만 **챔피언 파일이 패치당 2~106개뿐**이다(전체 약
> 170종). 부분 커버리지에서는 픽률 분모가 안 서고, 그것은 ADR-0002 가 이미
> 실측해 뺀 경우다. **해독해도 예측 지점으로 못 쓴다.**
>
> 아래 원문은 지우지 않는다 — 왜 해독을 시도했는지가 그 기록이다.

`rankings` 원본은 다 받았다(807파일). 그런데 **패치 단위가 아니라 챔피언 단위로 흩어져 들어왔다.**

```
16_3  106종 (62%)      15_16  59종 (34%)      14_18  11종 ( 6%)
16_14  73종 (43%)      15_22  44종 (26%)      14_24  10종 ( 6%)
14_16  60종 (35%)      15_17  39종 (23%)      15_7    5종 ( 3%)
14_17  60종 (35%)      16_7   35종 (20%)      14_20   2종 ( 1%)
15_9   59종 (34%)      15_10  26종 (15%)      15_3   15종 ( 9%) · 14_19 13 · 14_22 13
```

**승률은 멀쩡하다** — 챔피언 자체의 승/판이라 남이 없어도 값이 안 변한다. **픽률·밴율은 못 쓴다** — 분모가 「그 역할의 총 판수」라 전 챔피언이 있어야 선다. 대조군 3패치에서 직접 쟀다.

| 패치 | 커버리지 | 픽률 배율 중앙값 | 최소 | 최대 |
| --- | --- | --- | --- | --- |
| 15_14 | 45.6% | 2.48배 | 1.16 | 3.26 |
| 16_9 | 31.4% | 3.06배 | 1.30 | 21.64 |
| 16_13 | 28.3% | 3.37배 | 1.61 | 18.11 |

**한 패치 안에서도 배율이 챔피언마다 다르다.** 상수라면 나눠서 되돌리는데 그럴 수 없다. 역할별 누락 비율이 달라서다.

누락은 **인기 편향이 아니다** — 판수 상위·하위 구간의 보유율이 거의 같다. 아카이브 크롤러가 무작위로 긁었다.

**그래서 임계값 문제가 아니다.** 60% 임계값을 걸어도 픽률이 1.6배 틀린다. 유일하게 남은 길은 **`rankings` payload 가 u.gg 가 계산해 둔 픽률·밴율(또는 분모)을 들고 있는가**이고, 그건 2b 를 해야 안다.

**2026-08-25 추가 — 2b 결과와 무관하게 결정할 수 있다는 쪽으로 기운다.** 처음에는 「payload 에 분모가 있으면 부분 패치를 쓸 수 있다」고 봤으나, 두 가지가 그것과 상관없이 걸린다.

| # | 걸리는 것 |
| --- | --- |
| ① | **평가 단위.** 대표 지표 `precision@15` 는 그 패치의 후보 171종을 다 세워야 성립한다. 14_20 은 챔피언이 2종이다. 피처가 완벽해도 순위를 못 만든다 |
| ② | **수집 시점이 다르다.** 두 엔드포인트의 절대값이 어디에서도 안 맞았다 — 아카이브 스냅샷 시각이 달라서다. `champion_ranking(t) − rankings(t−1)` 로 만든 변화량은 실제 변화와 시점 차이가 뒤섞인 값이 된다 |

여기에 이득이 **632행 / 8,940행 = 6.6%** 라는 점을 더하면, **권고는 「전 챔피언 보유 53패치만 쓴다, 임계값 없음」이다.**

**2026-08-25 결정됨 — [ADR-0002](adr/0002-prediction-point-coverage-criterion.md).** 전 챔피언 보유 53패치만 쓴다, 임계값 없음. 후보 넷(A 53패치만 · B 챔피언×패치 단위 · C 임계값 · D payload 해독)을 비교했다.

D 를 빠르게 확인해 보려 한 두 시도가 실패했고, **그 실패 원인이 D 를 무력화했다** — 두 엔드포인트의 절대값이 어디에서도 안 맞았는데 아카이브 스냅샷 **수집 시각이 다르기** 때문이다. 해독에 성공해도 부분 패치로 만든 추세는 실제 변화와 시점 차이가 뒤섞인다.

### 8. CommunityDragon 에 스킬 피해량이 있다

**「Data Dragon 에 없다」를 「어디에도 없다」로 넘겨짚고 있었다.** 라이엇 게임 데이터를 미러링하는 CommunityDragon 에는 피해량과 계수가 **버전별로** 들어 있다.

```
Ahri Q   BaseDamage [40, 65, 90, 115, 140]
         TotalDamage = BaseDamage + 0.45×AP     ← 툴팁의 {{ totaldamage }} 가 이것
```

**확인한 것**

| | |
| --- | --- |
| 버전 커버리지 | 우리 범위 표본 12개(13.14~16.15) **전부 200** |
| 값 일치 | 쿨다운·코스트가 Data Dragon 과 맞는다 — 8개 중 7개 |
| **함정** | 배열이 0~6랭크 7칸인데 **항목마다 오프셋이 다르다.** Q 코스트만 `[0:maxrank]` 이고 나머지는 `[1:1+maxrank]` |
| **함정** | 필드 이름이 챔피언마다 다르다 — `BaseDamage` · `RBaseDamage` · `RAPCoefficient` |
| 부담 | 챔피언 170종 × 74버전 = **12,580 요청 · 약 2.9 GB**. 지금 `data/` 전체의 7배 |

**얻는 것**: 채점 범위가 25% → 대부분으로 늘어난다. 지금은 13.15 기록 52건 중 13건만 검증된다.

**전량 확보 완료 (2026-08-25).** 전량 12,580 요청이 아니라 **노트에 이름이 오른 챔피언의 그 버전 + 직전 버전**만 받아 2,795쌍으로 줄였다.

| | |
| --- | --- |
| 받음 | **2,788 / 2,788** · 360 MB · 68분 |
| 못 받은 7건 | **전부 신규 챔피언 출시** — briar · hwei · smolder · aurora · mel · yunara · locke |
| 깨진 파일 | **0** (2,788개 전부 파싱 확인) |

**「직전 버전이 없다」는 실패가 아니라 출시 이벤트다.** 일곱 건 모두 그 버전 Data Dragon 에 없고 다음 버전에 있는 것을 확인했다. **채점기가 이 둘을 구분해야 한다** — 지금 코드는 「파일 없음」을 한 가지로만 본다.

**도입하기로 정했다 — [ADR-0005](adr/0005-skill-damage-data-source.md).** 후보 넷을 재 보니 Data Dragon 툴팁은 자리표시자를 풀 값이 응답에 아예 없고(못 푸는 비율이 51%→66% 로 **커진다**), 패치 노트만으로는 조용한 변경 **8.3% 이상**을 못 본다. 읽는 코드는 아직 없다 — 파서가 다음 작업이다.

### 3. Oracle's Elixir — 주소는 찾았고 할당량에 막혔다

### 9. 잘린 응답이 재시도를 안 탄다

CommunityDragon 전량 수집(2,795쌍)에서 `15_19/sivir` 하나가 실패했는데, 없는 파일이 아니라 **HTTP 200 으로 오다가 중간에 끊긴 응답**이었다.

```
1차   84,469 B 에서 끊김  →  json.loads 실패
재시도 149,054 B 정상
```

**구조가 이렇게 돼 있다.**

```python
body = get_with_retry(url, attempts=3)   # HTTP 실패만 재시도한다
json.loads(body)                         # ← 여기서 깨져도 재시도가 안 붙는다
```

잘린 응답은 HTTP 로는 성공이라 `get_with_retry` 를 그냥 통과하고, 바깥의 `json.loads` 에서 `ValueError` 로 죽는다. **한 번 더 부르면 멀쩡히 온다.** `fetch-ugg-rankings` 도 같은 모양이다.

### 고쳤다 (2026-08-26)

두 겹으로 막았다. **한 겹으로는 안 된다** — 종료 코드는 curl 이 끊긴 것만 잡고, 서버가 잘못된 `Content-Length` 로 깨끗이 끊으면 curl 도 0 을 낸다.

| 겹 | 자리 | 무엇을 잡나 |
| --- | --- | --- |
| ① | `get()` 이 `result.returncode` 를 본다 | curl 이 끊겼다고 말해 주는 경우 (exit 28) |
| ② | `get_with_retry(..., validate=json.loads)` | curl 은 0 인데 내용이 깨진 경우 |

②가 핵심이다. **검증이 재시도 루프 안으로 들어왔다** — 전에는 받는 쪽에서 따로 `json.loads` 를 불렀고, 그 실패는 영구 실패라 재시도 예산이 한 번도 안 쓰였다. 수집기 네 개에서 중복 검사를 걷어냈다.

**확인한 것**

```
실제 네트워크   큰 파일을 1초에 끊음
              → curl 종료 28(382,311 B 받음)  Retryable 로 잡힘
              옛 코드는 이 382 KB 를 성공으로 돌려줬다

테스트         새 테스트 5개 중 4개가 옛 코드에서 실패한다
              (5번째는 「검증기 없으면 동작 그대로」라 양쪽 통과가 맞다)
```

`get()` 은 그동안 **테스트 커버리지가 0** 이었다 — 기존 테스트가 `get_with_retry` 를 통째로 갈아 끼워 `get_archived` 의 형식 선택만 봤다. 이제 `subprocess.run` 을 갈아 끼우는 층이 생겼다.

### 10. 프로 픽·밴율이 왜 방향 예측을 돕는지 — 원인을 확정할 수 없다

방향 예측(②)에서 프로 픽·밴을 넣으면 RAG 가 **0.856 → 0.900** 이 된다. **어디서 오는지는 좁혔지만 왜인지는 못 정한다.**

**이 절에서 너프를 둘로 가른다** — 조정 직전 프로 픽·밴율이 **중앙값 위면 「높은 쪽」, 아래면 「낮은 쪽」**이다. 각 110건. 나머지 용어는 [glossary](glossary.md)에 있다.

**먼저, +0.035 는 전부 프로 피처다.** 거리가중과 `k=50` 은 기여가 0 이다.

```
솔랭4 · k=25 · 다수결   0.856   ← 기준
솔랭4 · k=50 · 거리가중  0.860   거리가중만으로는 오히려 내려간다
프로+ · k=25 · 다수결   0.900   프로 피처만으로 거의 전부
```

**설명 후보 셋 중 둘을 지웠다.**

| | 설명 | 검증 | 결과 |
| --- | --- | --- | --- |
| ㉠ | 프로 경기에만 있는 정보가 조정과 관계있다 | — | **남았다** |
| ㉡ | 어려운 챔피언은 솔랭 승률이 낮을 뿐이다 | 프로 픽·밴율에서 **챔피언별 평균을 뺀다** | ❌ 고유분 AUC **0.548**, 변동분 **0.764** — 신호는 「그 패치에 유독」쪽이다 |
| ㉢ | 프로가 강한 픽을 먼저 찾고 솔랭이 따라온다 | 조정 안 된 5,651쌍에서 **프로 픽·밴율(P) ↔ 승률 변화(P→P+1)** | ❌ 상관 **−0.014**, 사분위 전부 ±0.0001. 대조군인 승률의 평균회귀는 −0.414 로 잡히므로 측정은 작동한다 |

**어디서 갈리는지는 뚜렷하다.** 승률 50% 미만 357행 — 솔랭만 보면 전부 「약하니 버프」로 읽어야 하는 구간이다.

```
너프당한  69종   프로 픽·밴율 0.361
버프받은 292종   프로 픽·밴율 0.080      ← 4.6배
이 구간 단독 AUC   프로 픽·밴율 0.771  >  승률 0.675
```

```
Ryze   16_2   승률 0.483  솔랭밴 3.4%   프로밴 23.6%  프로픽 33.3%   → 너프
Jayce  16_13  승률 0.487  솔랭밴 6.9%   프로밴 42.2%                → 너프
Jinx   15_18  승률 0.509  솔랭밴 1.6%   프로밴  1.1%                → 버프
```

**한 번 과장했다가 잡혔다.** 같은 챔피언의 이력을 늘어놓고 「승률은 거의 같은데 프로 픽·밴율만 갈렸다」고 적었는데, **롤에서 1~2%p 는 큰 차이다.**

```
Jayce    너프 때 0.490  버프 때 0.477   +1.3%p   ← 승률도 일하고 있었다
Ryze     너프 때 0.485  버프 때 0.476   +1.0%p
Qiyana   너프 때 0.493  버프 때 0.498   -0.6%p   ← 이것만 승률로 설명이 안 된다
```

**승률을 1%p 폭으로 잘라 통제하고 다시 쟀다.** 구간 안에서는 승률이 더 말할 게 없어 55번(찍기 50번)으로 떨어지는데, **프로는 75번을 유지한다.**

| 승률 구간 | n | 프로 | 승률 |
| --- | ---: | ---: | ---: |
| 47~48% | 67 | 86번 | 67번 |
| 48~49% | 108 | 84번 | 55번 |
| 49~50% | 133 | 71번 | 51번 |
| 50~51% | 162 | 72번 | 60번 |
| 51~52% | 103 | 69번 | 46번 |
| **계 573** | | **75번** | **55번** |

**승률 차이를 지워도 프로 신호가 남는다.** 사례를 고를 때 승률이 같이 움직이는 것을 안 보면 프로 몫을 과대평가한다.

**그래도 ㉠ 을 「라이엇이 프로 경기를 본다」로 적지 않는다.** 실제 경로는 대회 중계일 수도, 내부 최상위 티어 데이터일 수도, 선수 피드백일 수도 있다. **공통점은 「에메랄드 솔랭 지표에 안 보인다」뿐이고, 그것이 이 저장소가 말할 수 있는 전부다.**

**「평시」를 이 데이터로 못 가른다.** 경기 수로 나눠 보면 적은 쪽 AUC 0.750, 많은 쪽 0.778 로 완만해 「대회 성수기 한정」은 아니다. 다만 **리그가 연중 돌아가서 적은 쪽도 패치당 중앙값 371경기다.** 진짜 0 인 12월 비시즌(13.23 · 14.24)은 프로 데이터가 아예 없어 빠졌다 — **대회가 없는 평시는 이 표본에 존재하지 않는다.**

**틀린 채 문서에 있던 것을 고쳤다.** `README` 가 RAG 개선을 「프로 피처 + 거리가중」으로 적었는데 거리가중은 기여가 0 이다. 해상도(점수 25종 → 206종)는 실제로 올랐지만 **그것이 AUC 를 올린 게 아니다.** 같은 진단이 규칙(B4)에는 맞았고 RAG 에는 틀렸다.

#### 「승률이 실 성능을 잘못 잰다」인가, 「모집단이 둘」인가

원인을 한 겹 더 파고들면 후보가 다시 둘로 갈린다.

| | |
| --- | --- |
| **㉮ 측정 오차** | 진짜 강함은 하나인데 **승률이 그걸 잘못 잰다.** 프로 데이터가 더 정확히 잰다 |
| **㉯ 두 모집단** | 진짜 강함이 하나가 아니다. **솔랭에서 진짜로 약하고 프로에서 진짜로 세다.** 둘 다 맞는 측정이다 |

**㉮ 가 맞다면 그 오차는 「챔피언에 붙은 성질」이어야 한다** — 어려운 챔피언은 늘 승률이 실력을 못 담으니까. 그런데 챔피언 고유분은 AUC **0.548**(찍기 0.5)이고 패치 변동분이 **0.764** 다. **오차가 챔피언이 아니라 순간에 붙어 있다.**

**너프 후 착지점도 ㉮ 와 안 맞는다.** 다만 **처음에 세운 검정이 틀렸고 대화에서 잡혔다.**

```
❌ 「측정 오차를 바로잡는 거라면 균형(50%)으로 수렴해야 한다」
   → 정확히 50% 에 갖다 놓는 것은 사실상 불가능한 밸런싱이다.
     되는 일을 기준으로 삼아야지 안 되는 일을 기준으로 삼으면 안 된다.

✅ 「균형에서 멀어졌는가」  |승률 − 50%| 가 줄었나 늘었나
   → 정확도를 요구하지 않고 방향만 본다. 지나친 것만 걸린다.
```

**바꿔서 재니 오히려 뚜렷해졌다.** 순열 검정 20,000회, 시드 `20260826`, 각 110건.

| | 낮은 쪽 | 높은 쪽 | p |
| --- | ---: | ---: | ---: |
| 너프 전 \|승률−50%\| | 1.40%p | 1.32%p | — |
| 너프 후 \|승률−50%\| | **1.02%p** | **1.41%p** | — |
| **균형에서 멀어진 비율** | 36% | **55%** | **0.0091** |
| **너프 후 48% 미만** | 4% | **20%** | **0.0003** |
| 너프 후 49% 미만 | 14% | **44%** | **0.0000** |
| **이미 50% 아래인데 너프** | 16% | **35%** | **0.0028** |

**낮은 쪽 너프는 균형으로 당긴다**(1.40 → 1.02%p, 64%가 가까워짐). **높은 쪽 너프는 밀어낸다**(1.32 → 1.41%p, 55%가 멀어짐).

**「지나치게」가 어디 있는지도 보인다.** 너프 후 승률 분포다.

```
             ≥51%   50~51  49~50  48~49   <48%
낮은 쪽 너프    24%    34%    29%    10%     4%
높은 쪽 너프    10%    25%    22%    24%    20%    ← 5분의 1이 48% 아래로 간다
```

**높은 쪽 너프의 35% 는 이미 50% 아래인 챔피언을 대상으로 하고, 그중 82% 가 더 내려간다.** 솔랭 관점에서는 교정이 아니라 악화다.

**「그냥 더 센 너프였다」는 아니다.** Data Dragon 이 본 바뀐 수치 개수가 오히려 **적다**(1.39개 vs 1.78개, 상관 −0.054). 다만 개수는 크기의 거친 대리값이다 — 15% 한 방이 2% 세 방보다 크다.

**㉯ 도 하나 안 맞는다 — 보상해 주지 않는다.** 솔랭 손해를 감수했다면 나중에 되돌려 줘야 하는데, 다음 조정이 버프일 확률이 **54%**(낮은 쪽 60%)로 오히려 낮고 사분위로도 56/63/60/48 로 패턴이 없다. **밀어 넣고 그냥 둔다.** 남은 설명은 「우선순위를 그렇게 뒀다」거나 「49% 를 문제로 안 본다」인데 **이 데이터로는 못 가른다.**

#### 왜 높은 쪽 너프가 솔랭 승률을 더 내리는가 — 대화에서 나온 가설 둘

수치를 덜 건드리는데 승률은 더 내려가는 것이 앞뒤가 안 맞아 보였다. **대화에서 도메인 지식으로 가설 둘이 나왔고, Data Dragon 의 변경 항목으로 검정했다.** 순열 검정 20,000회, 시드 `20260826`. 전 챔피언 동시 변경(스키마 변경)은 제외했다.

**가설 1 — 높은 쪽 너프는 「다루기」를 건드려서 일반 유저에게 더 아프다.** 지지된다.

| | 「다루기」(쿨다운·마나·사거리) 비율 |
| --- | ---: |
| 낮은 쪽 너프 (n=57) | **14.3%** |
| 높은 쪽 너프 (n=59) | **30.5%** |

차이 **+16.2%p · p = 0.025.**

```
Skarner  14_12  프로 0.91   Q.cost      30              → 50
Jax      13_20  프로 0.48   R.cost      50              → 100
Orianna  16_4   프로 0.69   Q.cooldown  6/5.25/4.5/…    → 7/6/5/4/3
Trundle  15_15  프로 0.60   W.cooldown  16/15/14/13/12  → 18/17/16/15/14
```

**전부 피해량을 안 깎고 쓰기 어렵게 만든다.** 마나 30→50 은 「수치 하나」지만 프로는 CS 를 안 놓쳐 덜 아쉽고 **일반 유저는 그걸로 스킬 한 번을 덜 쓴다.** 「너프의 크기」와 「일반 유저가 받는 타격」이 다른 축이라는 뜻이고, **적게 바꿨는데 더 내려간 것과 앞뒤가 맞는다.**

**가설 2 — 낮은 쪽 너프는 초반만 깎아서 프로는 체감을 덜 한다.** 못 정한다. **축마다 반대로 나온다.**

| 축 | 낮은 쪽 | 높은 쪽 | |
| --- | ---: | ---: | --- |
| 스킬 레벨 (1레벨 변화 − 5레벨 변화) | **+0.043** | −0.019 | 가설대로. 다만 n=8·18 · **p = 0.44** |
| 기본 스탯 vs 레벨당 | 기본 52% | **기본 61%** | **반대** — 높은 쪽이 더 초반 쪽이다 |

사례에도 둘 다 있다.

```
Orianna  16_4   Q쿨  6/5.25/4.5/3.75/3 → 7/6/5/4/3       5레벨 그대로 = 초반만
Naafiri  15_8   W쿨  22/21/20/19/18    → 26/24/22/20/18   5레벨 그대로 = 초반만
Malphite 16_1   R쿨  130/105/80        → 130/115/100      1레벨 그대로 = 후반만
```

**프로 챔피언에도 초반만 깎는 패치가 있다.** 그래서 안 갈린다.

#### 이 절 전체에 붙는 경고 둘

**하나. 「어떤 항목이 바뀌었나」를 쟀지 「난이도가 올랐나」를 잰 게 아니다.** 마나·쿨다운 너프가 일반 유저에게 더 아프다는 연결은 **가설이고 검증한 것이 아니다.**

**둘. 이 절의 검정은 전부 같은 표본에서 여러 번 돌린 탐색 결과다.** `p = 0.025` 도 그중 하나라 확증으로 읽으면 안 된다. **별도 표본으로 다시 재야 한다.**

### 11. ③ 효과가 「의도대로 움직였나」만 재고 있다 — **밸런스가 좋아졌는지는 안 잰다**

10번을 파다가 걸렸다. **「너프했더니 승률이 내려갔다」와 「밸런스가 좋아졌다」는 다른 말이다.**

지금 ③ 은 앞엣것만 잰다. 뒤엣것도 같이 재면 **인상이 뒤집힌다.**

| 조정 | n | 평균 변화 | **의도대로** | **균형에 가까워짐** | 대조군 대비 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 너프 | 229 | −0.945%p | **79.5%** | **53.3%** | **+2.8%p** |
| 버프 | 350 | +0.849%p | **73.4%** | **63.1%** | **+12.7%p** |
| 조정 없음 (대조군) | 5,746 | −0.004%p | — | 50.5% | — |

**「의도대로」로 보면 너프가 낫고(79.5% > 73.4%), 「균형에 가까워졌나」로 보면 버프가 4배 낫다(+12.7%p vs +2.8%p).** `README` 의 ③ 표는 앞엣것만 실어서 **반대 인상을 준다.**

**대조군이 50.5% 인 것에 주의한다.** 아무것도 안 해도 절반은 균형에 가까워진다(평균회귀). **너프의 53.3% 는 거기서 2.8%p 나은 것뿐이다.**

#### 왜 갈리는가 — **움직이는 크기는 같은데 출발점이 다르다**

| | 조정 전 승률 | 균형까지 거리 | 실제로 움직인 크기 | |
| --- | ---: | ---: | ---: | --- |
| 너프 | 50.85% | **1.38%p** | **1.43%p** | **넘어간다** |
| 버프 | 48.96% | **1.65%p** | **1.41%p** | **못 미친다** |

**너프는 균형까지 1.38%p 남았는데 1.43%p 를 움직인다.** 평균적으로 지나친다. 버프는 1.65%p 남았는데 1.41%p 만 움직여 덜 간다. **조정 크기는 사실상 같다** — 갈리는 것은 **어디서 시작하느냐**다.

10번에서 본 높은 쪽 너프가 이것의 극단이다. 이미 50% 아래인 챔피언을 너프하면 **균형까지 남은 거리가 음수**라 무엇을 해도 멀어진다.

#### 무엇이 걸렸었나 — **기록으로 남긴다**

아래가 결정 전에 적어 둔 걱정이다. **두 번째 문단의 「50% 를 목표로 전제하지
않는 문장이어야 한다」는 대화에서 뒤집혔다** — 50% 는 전체 평균(0.5008)이 맞고,
못 가는 이유가 따로 있는 것이었다. 아래 「결정했다」참조.

**③ 결과표에 「균형에 가까워짐」 열을 나란히 둘 것인가.** 넣으면 정직해지지만 **주장이 하나 늘어난다** — 「라이엇의 조정이 밸런스를 좋게 했는가」는 [`README`](../README.md) 의 「증명하지 않는 것」에 **「라이엇의 조정이 옳았다·틀렸다는 적지 않는다」**로 이미 선을 그어 둔 영역과 가깝다.

**선을 넘지 않는 표현은 있다.** 「좋아졌다·나빠졌다」가 아니라 **「50% 에서 멀어졌다」는 관측 사실**로만 적으면 된다. 밸런스의 목표가 50% 라고 이 문서가 정한 적은 없으므로, **50% 를 목표로 전제하지 않는 문장**이어야 한다.

#### 결정했다 (2026-08-27) — **넣는다. 다만 성패로 읽지 않는다**

**대화에서 전제 하나가 깨졌다.** 「50% 아래로 내려간 너프는 지나친 것」이라고
읽고 있었는데, **50% 를 정확히 맞추는 것은 가능한 작업이 아니다.** 되는 일을
기준으로 삼아야 한다.

그리고 「Azir 는 50% 가 목표가 아닌 챔피언」이라고 적었던 것도 **틀렸다.**

```
❌ 「Azir 는 47% 가 제자리다」          ← 라이엇이 그 자리를 의도했다는 말
✅ 「Azir 를 올리면 프로 경기가 망가진다」    ← 제약에 묶여 있다는 말
```

**뒤엣것이 데이터에 있다.** 평생 평균 승률과 평생 평균 프로 픽·밴율의 상관이
**−0.430** 이고, 버프하면 프로 단골만 프로 경기 출전이 **+37%** 뛴다(그 외 +0.0%).

**그래서 이 열이 재는 것이 무엇인지가 정해졌다.**

| | |
| --- | --- |
| ❌ **성패** | 「라이엇이 밸런싱을 잘했나」 — [`README`](../README.md) 가 안 하기로 한 주장이다 |
| ✅ **관측** | **「두 지표가 어긋나는 방향과 크기」** — 한쪽만 보면 다른 쪽이 흔들린다 |

`ADR` 은 쓰지 않는다. **주장 범위를 넓히는 게 아니라 기존 관측에 열을 하나
더하는 것**으로 정리됐다. 본문은 [results](results/README.md#두-지표가-어긋난다)에 있다.

#### 되돌린 판단 — **「너프도 프로 단골이 5배 빠진다」는 착시였다**

절대 변화만 보고 적었다. 프로 단골은 **조정 전 프로 픽·밴율이 0.551 로 높아** 절대 변화가
클 수밖에 없다. 상대 변화로 보니 방향이 갈렸다.

```
             조정 전   절대 변화    상대 변화
버프 프로 단골     0.190   +0.0916    +37.1%    ← 버프 쪽은 상대로도 유지된다
버프 그 외      0.039   +0.0104     +0.0%
너프 프로 단골     0.546   −0.1087    −18.0%    ← 너프 쪽은 차이가 없다
너프 그 외      0.118   −0.0150    −17.5%
```

**철회하면서 더 나은 것이 나왔다** — 비율로는 프로 단골이 **덜** 빠진다. **들어오기는
쉽고 나가기는 어렵다.** 되돌리기가 비싸니 애초에 안 올린다는 설명이 된다.
평균회귀로는 설명이 안 된다 — 프로 단골은 프로 픽·밴율이 튄 패치에 너프당해 자기 범위
꼭대기에 있으므로 **더** 떨어져야 한다.

#### 범위를 못박았다 — **11% 에서만 일어난다**

패치 30개 이상 나온 167종 기준이다.

| | 프로 단골 | 비프로 단골 | 계 |
| --- | ---: | ---: | ---: |
| 승률 낮음 (평생 <49.5%) | **18** | **20** | 38 |
| 승률 보통 이상 | 24 | 105 | 129 |

**승률 낮은 38종의 절반은 프로 경기와 무관하게 약하다**(Yuumi 0.01 · Shyvana 0.01 ·
Zed 0.02). **어렵다고 프로 단골인 것도 아니다** — Yasuo·Zed 는 어렵기로 유명한데
프로 픽·밴율이 0.03·0.02 다. **프로 단골 42종 중 24종은 승률이 보통 이상이다.**

**이 경계를 안 그으면 「라이엇은 프로 때문에 솔랭을 희생한다」로 읽힌다.**
그것은 11% 에서만 참이다.

| --- | --- |
| 자동 판정과의 충돌 | **0건** |
| 같은 패치에 같은 챔피언 두 번 | **0건** |
| 근거가 비었는데 방향을 붙인 것 | **0건** |

```
              → 53건이 「조정 안 됨」으로 기록돼 있었다
Nunu 이름     위키 `Nunu` ↔ Data Dragon · 패널 `Nunu & Willump`
              → 5개 패치의 조정과 방향 라벨 4건이 패널에 못 붙었다
```

Arena·Doom Bots 절은 형식이 같아도 **협곡이 아니라 그대로 제외**한다.
`build-panel` 이 이제 노트 이름과 패널 이름을 대조해, 새 어긋남이 생기면 그
자리에서 경고한다.

양성 1,546 → **1,595**, 방향 라벨 1,564 → **1,568**. 충돌은 계속 0 이다.

#### 결론 셋이 바뀌었다

| | 전 | **후** |
| --- | --- | --- |
| 이력 피처 | 「신호는 있는데 안 먹는다」(−0.93%) | **도움이 된다**(+0.34%) — [경위](spec/prediction-signals.md#뒤집혔다-2026-08-27--핫픽스-누락이-이력-신호를-누르고-있었다) |

이력 피처 쪽이 특히 말이 된다. **핫픽스는 「방금 손댄 챔피언을 곧바로 또 손대는」
사례**라, 그것이 전부 「조정 안 됨」이었으니 이력 피처가 맞혀야 할 자리가 오답
으로 채워져 있었다.

### 15. 핫픽스 시점 어긋남 — **같은 조정이 두 행에 나뉜다**

패치 P 중간에 핫픽스가 나가면 이렇게 갈린다.

```
노트          P 문서의 「January 12th Hotfix」 절   → adjusted_next 는 P−1 행에
Data Dragon   P 스냅샷은 핫픽스 전에 떴다
              그래서 P → P+1 diff 가 그것을 본다   → direction_next 는 P 행에
```

**한 사건이 한 행 어긋나 두 곳에 적힌다.** 그 결과 P 행은 「조정 안 됨인데 방향은
너프」라는 모순을 갖는다.

**Data Dragon 이 붙인 방향 라벨 15건이 전부 이것이다.** 문서화 안 된 변경은 0건
이었다 — 즉 이 폴백은 지금 맞는 라벨을 하나도 못 만들고 있다.

| | 어디에 |
| --- | --- |
| 손 라벨 | 1,551건 — 영향 없다 |
| cdragon | 2건 |
| **Data Dragon** | **15건 · 전부 어긋남** |

#### 고쳤다 (2026-08-27) — **둘째 후보를 골랐다**

세 후보 중 **「P 노트에 있는 챔피언은 P+1 의 기계 판정에서 뺀다」**를 골랐다.
`adjusted_next` 의 뜻은 그대로 두므로 ADR 이 필요 없고, 결함 수정이다.

Corki 가 결정적이었다. 핫픽스 라벨을 붙이는 중에 `score-labels` 가 충돌을 냈다.

```
13.24 노트   체력 588→610 · 성장 105→103 · 공격력 55→59 · 성장 2.8→2.5   → mixed
14.1  노트   공격력 59→61 · R 계수 상향                                  → buff
DD 14.1 diff  체력 588→610 · 성장 105→103 · 공격력 55→59 · 성장 2.8→2.5
              ↑ 13.24 핫픽스 그대로다. 14.1 자신의 변경은 아예 없다
```

**그래서 자동 판정이 13.24 것을 14.1 것으로 말하고 있었다.**

| | 전 | **후** |
| --- | ---: | ---: |
| direction 있는데 adjusted=0 | 15행 | **0행** |
| adjusted=1 인데 direction 없음 | 0행 | **0행** |
| 기계 판정으로 붙은 방향 라벨 | 17건 | **0건** |

**기계 판정이 0 이 된 것이 결과다.** 손 라벨이 52패치 전량을 덮으므로 폴백이
채울 자리가 없고, 남아 있던 17건은 전부 오귀속이었다. cdragon 2건도 같은
지연이었다(Zac 14_2 · Hwei 14_8).

### 16. 핫픽스 라벨 44종 — **완료 (2026-08-27)**

핫픽스 절이 드러나며 보인 51종 중 신규 출시 7종을 뺀 **44종에 라벨을 붙였다.**

```

커버리지 96.8% → 100%                        방향 라벨 1,555 → 1,599
```

**①·② 가 좋아졌다.** 너프 대상 예측이 5.7배 → **6.5배**(19.0% → 22.3%), 프로
피처를 붙이면 **6.7배**다. 버프 대상은 프로 피처의 기여가 커졌다(11.1% →
**15.3%**).

**③ 은 내려갔고, 그 이유가 분명하다** — 84.6% → 79.5%. 핫픽스는 패치 한가운데서
나가 측정 창이 조정을 못 감싼다. 쪼갠 표와 설명은
[results](results/README.md#핫픽스는-이-방식으로-못-잰다-2026-08-27).

비율이 229/239 가 됐고, 다수결과의 차이가 −0.031 [−0.057, −0.005] 에서
**−0.020 [−0.045, +0.004]** 로 바뀌었다. **「진다」가 아니라 「이긴다고 말할 수
없다」가 지금 말할 수 있는 전부다.**

### 13. 조합(듀오) 너프를 확인할 수 없다 — **두 군데가 막혀 있다**

**「강한 원딜–서폿 조합이 있으면 그 조합을 겨냥해 너프한다」**는 대화에서 나온
가설이다. **현상은 보이는데 증명이 안 된다.**

#### 현상은 뚜렷하다

프로 경기에서 조합 출전 비율을 뽑으면 상위 20 중 **17건이 너프**다.

```
16_9   Ashe      Seraphine  114경기 15.3%  nerf
14_14  Ezreal    Leona       41경기 12.7%  nerf   ← 둘 다 너프
14_14  Leona     Ezreal      41경기 12.7%  nerf   ←
14_3   Varus     Nautilus    84경기 12.7%  nerf
13_14  Kai'Sa    Nautilus    98경기 12.3%  nerf
15_13  Braum     Lucian      35경기  9.1%  nerf
15_14  Braum     Lucian      53경기  8.9%  nerf
```

**Nautilus 가 짝으로 다섯 번, Braum–Lucian 이 두 번** 나온다.

#### 그런데 개인 존재감과 못 가른다

| 신호 | AUC |
| --- | ---: |
| 개인 프로 픽·밴율 | **0.796** |
| 최다 조합 출전 비율 | 0.740 |
| 회귀에 조합을 더하면 | 0.893 → **0.888** |

**둘의 상관이 0.729 다.** 강한 조합에 낀 챔피언은 개인 출전도 이미 많아 새
정보가 거의 없다. 표본도 얇다 — 바텀 + 방향 라벨 171행, 평가 구간 73행.

**동시 너프도 확인 안 된다.** 3경기 이상 조합 3,287쌍 중 둘 다 너프된 것이
16건(0.5%)이고 우연 기대(0.3%)의 1.5배지만 `p = 0.070` 이다. 사건이 희소해
힘이 안 나온다.

#### 막힌 곳 둘

**하나. 아이템 변경이 라벨에 없다.** 조합을 깨는 실제 수단이 아이템인 경우가
많다. Lucian–Nami 가 `14_9` 24.0% → `14_10` 6.0% 로 무너졌는데 두 챔피언 모두
「조정 안 됨」이다 — 무너뜨린 것은 `Items` 절의 `B. F. Sword` 빌드 경로 변경
이었다. 자세한 것은
[results](results/README.md#아이템으로-이뤄진-조정을-놓친다).

**둘. 솔랭에 조합 데이터가 없다.** u.gg 는 챔피언별 집계라 누구와 짝이었는지가
없다. 프로 경기에서만 뽑을 수 있는데, **본 분석은 솔랭 지표**라 이미 확장 분석
영역이 된다.

#### 절반 열었다 (2026-08-27) — **아이템 변동은 잰다**

「아이템 변경이 라벨에 없다」를 둘로 나눠 보니 앞쪽은 이미 가진 출처로 됐다.

| | 어디서 | 상태 |
| --- | --- | --- |
| **아이템이 언제 어떻게 바뀌었나** | Data Dragon `item.json` | **된다.** 같은 CDN · 키 불필요 · 74버전 |
| 어느 챔피언이 그 아이템을 사나 | 아래 표 | **아직 막혔다** |

`./scripts/fetch-items` 로 74버전을 받았고 실패 0 이다. 협곡에서 살 수 있는
아이템만 세면 완성템 변경이 **중앙값 1종 · 90% 분위 8종**인데, `14_10` 은
**30종**으로 73패치 중 3위다. Lucian–Nami 가 무너진 그 패치다.

경고는 패치 단위로 붙인다. 챔피언마다 띄우면 그 패치 목록 전체에 붙어
「항상 뜨는 경고」가 된다. `run-effect` 는 **③ 의 16% 가 그런 패치에서 왔다**고
같이 적는다.

#### 챔피언별 구매율 — **조사했고 못 쓴다**

u.gg 에 `overview` 엔드포인트가 있고 아카이브에도 남아 있다. 그런데 커버리지가
안 된다.

```
stats2.u.gg/lol/1.5/overview/{패치}/{큐}/{챔피언ID}/1.5.0.json
솔랭 스냅샷 2,565개 · 패치 73종
패널이 필요한 8,767쌍 중 아카이브에 1,164쌍 → 13.3%
커버리지 50% 넘는 패치 2 / 52
```

경로에 지역·티어가 없고 페이로드 안에 숫자 키로 들어간다(`rankings` 와 같은
형식). 해독해도 커버리지가 안 되므로 [2b](#2b--2d-rankings-해독이-커버리지-결정을-가로막고-있다)와 같은 결론이다.

### 17. 답변 형식(ADR 0007) — **재검토 조건 셋**

판단 저장 형식에 선택 칸 다섯을 더했다(`as_of` · `abstain` · `adjust_prob` ·
`evidence` · `warnings`). **기존 314건은 손대지 않았고 측정값도 안 움직였다** —
형식은 「무엇을 예측하는가」가 아니라 「답을 어떻게 적는가」다.

| 언제 다시 보나 | 무엇을 하나 |
| --- | --- |
| 판단 50건을 새로 만들었는데 **절반 이상 `evidence` 가 비어 있다** | 그 칸을 뺀다 — 값을 못 한 것이다 |
| **에이전트(A6)가 생겨 답이 자동으로 나온다** | 사람이 손으로 적는 것과 감당 가능한 칸 수가 다르다 |
| **① 판단 arm 을 만들 길이 생긴다** | `adjust_prob` 의 위치를 다시 정한다 |

셋째가 지금은 막혀 있다. ① 대상은 패치 안 줄 세우기라 한 패치(약 171종)를 통째로
판단해야 하는데, 평가 구간이 **20패치 · 3,433행**이라 손으로는 R-정확도를 못
낸다. `B6` 이 229건에 여덟 묶음 걸렸다.
