# 데이터 출처 조사 (2026-08-24)

전부 실제로 요청해서 확인한 것이다. 검색 결과를 옮긴 것이 아니라 응답 크기와 내용을 직접 봤다. 검증 상태를 항목마다 표시했다.

## 왜 이 문서가 먼저인가

확보할 수 없는 데이터를 전제로 쓴 계획서는 다시 써야 한다. 그래서 데이터부터 확인했고, 실제로 그 과정에서 설계가 세 번 바뀌었다.

- 솔랭 승률이 안 잡히는 줄 알고 프로 데이터로 갈 뻔했다 → 아카이브에서 찾았다
- 한국 서버로 가려다 → 라이엇이 글로벌을 본다는 지적에 `world` 로 바꿨다
- 2016~2022 로 가려다 → 티어 체계 변경을 발견하고 2023 이후로 좁혔다

## 1. Data Dragon — 정답지 ✅ 확정

라이엇 공식. 인증 불필요.

```
버전 목록   https://ddragon.leagueoflegends.com/api/versions.json
챔피언      https://ddragon.leagueoflegends.com/cdn/{버전}/data/{로케일}/champion/{이름}.json
```

**실측**

| 버전 | Ahri.json |
| --- | --- |
| 16.16.1 (최신) | 16,823 B |
| 14.1.1 | 9,248 B |
| 12.1.1 | 8,837 B |

- **버전 550개**가 보존돼 있다 (`16.16.1` ~ `lolpatch_3.7`)
- 로케일 다국어 (`ko_KR`, `en_US` 등)
- 스킬 툴팁이 `{{ e1 }}` 형태의 변수 + `effect` 배열로 **분리 저장**된다

**용도**: 버전 간 diff 로 **기본 스탯·쿨다운·코스트·사거리** 변경을 정확히 뽑는다. 노트에 안 적히는 조용한 변경까지 잡힌다.

> **2026-08-24 정정.** 한때 「패치 노트를 긁을 필요가 없다」고 적었으나 **틀렸다.** 대부분 스킬의 피해량이 Data Dragon 에 없다 — 툴팁이 `{{ totaldamage }}` 플레이스홀더이고 `datavalues` 는 모든 스킬에서 비어 있다. **정답지는 패치 노트여야 하고 Data Dragon diff 는 그 추출을 검증하는 수단이다.** 근거와 한계는 [`ddragon-format.md`](ddragon-format.md).

### 1b. 아이템 — 같은 CDN, 같은 버전 체계 (2026-08-27 추가)

```
아이템   https://ddragon.leagueoflegends.com/cdn/{버전}/data/{로케일}/item.json
받는 곳  ./scripts/fetch-items  →  data/items/{버전}.json
```

**왜 받았나.** 정답지는 패치 노트의 챔피언 절에서 오는데 조정의 상당수가
아이템으로 이뤄진다. Lucian–Nami 가 `14_9` 24.0% 에서 `14_10` 6.0% 로 무너졌을
때 두 챔피언 모두 「조정 안 됨」이었고, 무너뜨린 것은 `Essence Reaver` 의 골드가
2900 에서 3200 으로 오른 것이었다.

**출처를 안 섞는다.** 챔피언 스냅샷과 같은 CDN·같은 버전 체계이고, 아이템은
애초에 지역별로 다르지 않다.

**실측** — 74버전 전부 받았고 실패 0.

| | |
| --- | --- |
| 한 버전 | 약 530~580 KB · 아이템 640~710종 |
| 협곡에서 살 수 있는 것 | 약 254종 (`maps.11` 이고 `gold.purchasable`) |
| 완성템 근사 | 골드 2000 이상 약 140종 |

**패치별 변동 규모** (완성템 기준, 73패치)

```
중앙값  1종        90% 분위  8종  ← 경고 문턱
14_19  75종      14_1  65종      14_10  30종
```

못 하는 것: 어느 챔피언이 그 아이템을 사는가. 챔피언별 구매율은 u.gg
`overview` 엔드포인트에 있는데 아카이브 커버리지가 **13.3%** 이고 52패치 중
50% 를 넘는 것이 2개뿐이라 못 쓴다. 조사 결과는
[followups](../followups.md) 13번.

그래서 경고는 패치 단위다. 「이 패치의 승률 변화를 챔피언 조정으로만 읽지
마라」까지가 지금 말할 수 있는 전부다.

## 2. u.gg 아카이브 — 솔랭 승률 ✅ 확보, ⚠️ 해독 필요

라이브 API 는 Cloudflare 가 막는다(403). **웹 아카이브를 경유하면 받아진다.**

```
원본   https://stats2.u.gg/lol/1.5/champion_ranking/{지역}/{패치}/{큐}/{티어}/1.5.0.json
경유   https://web.archive.org/web/{타임스탬프}id_/{원본 URL}
```

패치가 URL 경로에 `16_9` 형태로 들어간다.

**실측 (2026-05-08 아카이브, 패치 16_9)**: 110,991 B, JSON 파싱 성공

**형식이 두 가지다**

```
읽기 쉬운 형태 (일부 응답)
  {"win_rates":{"none":[{"win_rate":57.22,"pick_rate":2.16,"ban_rate":0,...}]}}

위치 기반 배열 (champion_ranking 다수)
  [{"adc":[["154",[[67,0,1]],1,1,17914,14505,9,12,6,146], ...
     챔피언ID ─┘        승┘ 판┘  딜┘   골드┘ K┘ D┘ A┘ CS┘   ← 추정
```

위치 기반 배열의 필드 의미를 확정하는 것이 첫 작업이다. 승/판 수가 있으므로 승률은 계산된다. 알려진 값과 대조하면 확인된다.

### 패치마다 긁힌 시각이 다르다 (2026-08-29) — **가장 이른 스냅샷을 쓰고 있다**

`fetch-ugg` 가 패치마다 **제일 먼저 찍힌 스냅샷**을 고른다.

```
"&collapse=urlkey"               URL당 스냅샷 하나로 접는다
by_patch.setdefault(patch, ...)  그중 첫 번째 = 가장 이른 것
```

그래서 어떤 패치는 **출시 직후 값**만 들어 있다.

| 패치 | 총 게임 | `updated_at` |
| --- | ---: | --- |
| 16_10 | 2,234,436 | 2026-05-26 |
| 16_12 | 1,748,647 | 2026-06-20 |
| 16_13 | 2,254,893 | 2026-07-06 |
| **16_15** | **334,500** | 2026-07-31 |

연도별로 보면 계통적이다 — 2023년 중앙값 3,649 · 2026년 68,869 로 19배 차이가
난다. **실제 플레이어 증가가 아니라 아카이브가 옛 페이지를 덜 조밀하게 긁은
결과로 보인다.**

**53패치 중 32개(60%)에 더 나중 스냅샷이 있고 간격 중앙값이 14일이다.** 그것으로
다시 받으면 성숙한 값이 되지만, **모든 결과가 바뀌므로 전량 재측정이 따른다.**
지금은 하지 않고 알려진 한계로 적어 둔다.

#### `16_15` 는 고칠 수 없다

실시간 예측이 쓰는 패치라 이것만이라도 고치려 했는데 세 경로가 다 막혔다.

| 시도 | 결과 |
| --- | --- |
| 아카이브 CDX | **스냅샷 1개뿐** (2026-07-31) |
| u.gg 직접 | **403** — Cloudflare |
| Save Page Now | **520** — 새 스냅샷이 안 생긴다 |

그래서 **고치는 대신 둘로 대응한다.** 이웃 패치의 40% 에 못 미치면 「승률이 아직
안 굳었다」를 패치 머리말에 내고(`explain.sample_note`), **예측 기준 패치로도 안
고른다**(`panel.settled_patch`). 그래서 `./scripts/predict` 는 `16_15` 가 아니라
`16_13` 에서 출발한다.

**문턱은 이웃과 견준 값이지 절대 크기가 아니다.** 2023년 패치는 통째로 작은데 그건
그 시절이 그런 것이라 걸러선 안 된다. 잡으려는 것은 **「이 패치만 덜 찼다」**뿐이다.
고정값으로 안 박은 이유는, 아카이브가 `16_15` 를 다시 긁으면 **저절로 최신 패치로
돌아오게** 하기 위해서다.

### `rankings` 엔드포인트로 결측을 메운다

`champion_ranking` 만으로는 53종이다. **같은 출처의 다른 엔드포인트에 17종이 더 있다** — 다만 챔피언 단위로 흩어져 있어 같은 급이 아니다. 아래 「부분 커버리지」 참조.

```
champion_ranking   .../champion_ranking/{지역}/{패치}/{큐}/{티어}/1.5.0.json    전 챔피언 한 번에
rankings           .../rankings/{패치}/{큐}/{챔피언ID}/1.5.0.json               챔피언별
```

`rankings` 는 지역·티어가 경로에 없다. JSON 안에 중첩돼 있다.

```json
{"1": {"1": {"2": [35, 77, 43, 48, 1553805, 709741, 312, ...
  ↑지역   ↑티어  ↑라인      ↑판?     ↑승?
```

지역·티어 키가 숫자라 **무엇이 `world` 이고 무엇이 `emerald_plus` 인지 알아내야 한다.**

받을 때 `--compressed` 가 필요하다. 없으면 압축된 바이너리가 그대로 와서 JSON 파싱이 실패한다. 실제로 한 번 「형식이 깨졌다」고 오판할 뻔했다.

```bash
curl -sL --compressed -A "<UA>" "https://web.archive.org/web/{ts}id_/{원본URL}"
```

### `id_` 가 빈 응답이면 `if_` 로 받는다 (2026-08-25 확인)

replay 형식 하나가 응답을 못 한다고 스냅샷이 없는 것이 아니다.

`id_`(원본 그대로)로 0 B 가 오던 스냅샷이 `if_` 로는 그대로 나온다. 둘 다 배너를 끼워 넣지 않은 원본 바이트다.

```
15_2  id_ →     0 B      if_ → 119,502 B   항목 830 · 승률 49.9986% · 항등식 통과
```

재시도로는 안 걸러진다. 15_2 · 15_6 · 16_2 는 여덟 시간에 걸쳐 11회 넘게 시도해도 `id_` 가 계속 0 B 였다. 그대로 두었으면 **「아카이브에 없는 패치」로 잘못 적을 뻔했다.**

수집기는 `id_` → `if_` 순으로 시도한다 — [`fetch.get_archived`](../../src/lol_balance/fetch.py), 검사는 [`tests/test_fetch.py`](../../tests/test_fetch.py).

15_12 는 안 긁힌 것이 아니다. `champion_ranking` 이 있는데 `master_plus` 다. 그래도 쓰지 않는다 — 「platinum_plus 로 앞을 늘릴 수 없다」와 같은 이유로, **티어를 바꿔 가며 이어 붙이면 그 지점에서 승률이 통째로 튄다.** 마스터 이상은 에메랄드 이상과 모집단이 완전히 다르다.

다른 사이트에는 있을 수 있으나 **출처를 섞지 않는다.**

### 부분 커버리지 패치에서는 픽률·밴율이 안 나온다

`rankings` 는 챔피언당 파일 하나다. 아카이브가 그 패치의 챔피언을 다 긁지 않았다.

```
16_3  106종 (62%)     15_16  59종 (34%)     14_18  11종 ( 6%)
16_14  73종 (43%)     15_22  44종 (26%)     14_24  10종 ( 6%)
14_16  60종 (35%)     15_17  39종 (23%)     15_7    5종 ( 3%)
14_17  60종 (35%)     16_7   35종 (20%)     14_20   2종 ( 1%)
15_9   59종 (34%)     15_10  26종 (15%)     15_3   15종 ( 9%) · 14_19 13 · 14_22 13
```

| 지표 | 부분 커버리지에서 | 왜 |
| --- | --- | --- |
| **승률** | ✅ 정확 | 그 챔피언의 승/판이다. 남이 없어도 안 변한다 |
| **픽률·밴율** | ❌ 못 구한다 | 분모가 「그 역할의 총 판수」다. 전 챔피언이 있어야 선다 |

대조군 3패치로 직접 쟀다. 참값(`champion_ranking`)과 부분 집합으로 구한 값을 비교한 결과다.

| 패치 | 커버리지 | 픽률 배율 중앙값 | 최소 | 최대 |
| --- | --- | --- | --- | --- |
| 15_14 | 45.6% | 2.48배 | 1.16 | 3.26 |
| 16_9 | 31.4% | 3.06배 | 1.30 | **21.64** |
| 16_13 | 28.3% | 3.37배 | 1.61 | **18.11** |

한 패치 안에서도 배율이 챔피언마다 다르다. 상수라면 나눠서 되돌리는데, 역할별 누락 비율이 달라 그럴 수 없다. **임계값으로 못 푼다** — 62% 인 16_3 조차 픽률이 1.6배 틀린다.

누락 자체는 **인기 편향이 아니다.** 판수 상위·하위 구간의 보유율이 거의 같다 — 크롤러가 무작위로 긁었다. 그래서 **남아 있는 값은 편향되지 않았다.**

**남은 길은 하나다** — `rankings` payload 가 u.gg 가 계산해 둔 픽률·밴율(또는 분모)을 들고 있는가. 그건 배열을 해독해야 안다([followups 2b·2d](../followups.md)). **그때까지 부분 17패치를 예측 지점으로 세지 않는다.**

### 결측을 보간하지 않는다

빈 것은 빈 채로 둔다. 앞뒤 값으로 메우면 「이 값은 추정치」라는 사실이 사라지고, 나중에 그것이 결과에 얼마나 섞였는지 알 수 없게 된다.

이 문제는 **연속성이 필수가 아니다.** 각 패치가 독립적인 예측 지점 하나이고, 결측은 표본이 줄어드는 것이지 다른 지점을 오염시키지 않는다.

| 피처 | 쓸 수 있는 지점 |
| --- | --- |
| 수준 (지금 승률·픽률·밴율) | **53** |
| 추세 (직전 패치 대비 변화) | **42** — 직전 패치가 없는 11곳 제외 |

챔피언-패치 행으로는 **8,940행**이다. 부분 17패치를 넣어도 632행(6.6%)이 느는데, **그 632행은 픽률·밴율이 없어 피처 집합이 다르다.**

25패치 완전 구간(13_14~14_14)은 대조군으로 쓴다. 53패치 결과와 비슷하면 결측이 무해했다는 증거가 된다.

### 두 엔드포인트가 서로를 검증한다

**같은 패치에서 두 엔드포인트가 같은 승률을 주는지** 확인하면 배열 해독이 맞았는지 알 수 있다. 다르면 해독이 틀렸거나 집계 기준이 다르다는 뜻이다.

실제로 확보한 대조군은 3패치다 — 15_14(78종) · 16_9(55종) · 16_13(49종). 대조군으로 노린 13_20 과 14_5 는 아카이브에 `rankings` 자체가 없었다. 챔피언 182종분이 있으므로 해독에는 충분하다.

### 2024년 하반기 4개월 공백은 왜 생겼나 (조사 2026-08-26)

`14_15`~`14_22` 8패치가 연속으로 빈다. 프로 경기 날짜로 재면 **2024-08-03 ~ 11-28** 이다.

**「아카이브가 그 시기를 안 긁었다」로 적어 뒀는데 틀렸다.** CDX 를 티어 필터
없이 다시 조회해 보니 긁긴 긁었다 — **다른 티어를 긁었다.**

```
14_17   iron · master_plus       ← emerald_plus 가 없다
14_18   silver
14_22   diamond_plus
14_23   diamond_plus · emerald_plus   ← 그래서 14_23 만 우리에게 있다
```

아카이브 수집은 사람이 실제로 본 화면을 찍는다. 사이트 기본값이
`emerald_plus` 라 그것이 제일 많이 잡히지만(74패치 중 53), 누군가 티어를 바꿔
본 순간이 찍히면 그 패치는 그 티어로만 남는다.

전 범위 census 는 이렇다.

| 티어 | 스냅샷 |
| --- | ---: |
| `emerald_plus` | **53** — 우리가 가진 것과 정확히 같다 |
| `platinum_plus` | 17 (에메랄드 도입 전. 아래 절 참조) |
| `master_plus` | 9 |
| `gold` · `overall` · `iron` · `diamond_plus` · 기타 | 각 1~5 |

결측 21패치는 둘로 갈린다.

| | 패치 |
| --- | --- |
| 아무 티어도 없다 (13) | `14_15` `14_16` `14_19` `14_20` `14_21` `14_24` `15_3` `15_7` `15_10` `15_11` `15_16` `15_17` `16_7` |
| 다른 티어만 있다 (8) | `14_17` `14_18` `14_22` `15_9` `15_12` `15_22` `16_3` `16_14` |

### `rankings` 로도 못 메운다 — 챔피언이 듬성하다

다른 엔드포인트(`rankings`)에는 결측 패치가 20개 들어와 있다. 그런데 **챔피언
파일이 패치당 2~106개뿐**이다(전체 약 170종).

```
14_20   2종      14_18  12종     14_19  13종     14_22  14종
15_7    5종      14_24  10종     15_3   15종     15_10  26종
```

부분 커버리지에서는 픽률 분모가 안 선다. 「그 역할의 총 판수」로 나누므로 전
챔피언이 있어야 한다. [ADR-0002](../adr/0002-prediction-point-coverage-criterion.md)
가 이것을 대조군 3패치에서 실측해 **부분 커버리지 패치를 예측 지점에서 뺐다.**

즉 공백은 메울 수 없다. 원인은 「안 긁었다」가 아니라 **「긁힌 것이 다른
모집단이거나 조각이다」**이고, 둘 다 이 저장소의 「출처를 섞지 않는다」 규칙에
걸린다.

### platinum_plus 로 앞을 늘릴 수 없다

`platinum_plus` 도 13.x~16.x 에 15종 있지만 **에메랄드 도입 전후로 뜻이 다르다.** 에메랄드가 플래티넘과 다이아 사이에 들어가면서 기존 플래티넘 인구가 둘로 쪼개졌다. 도입 전 `platinum_plus`(플래+다이아+…)와 도입 후 `platinum_plus`(플래+에메+다이아+…)는 같은 모집단이 아니다.

티어를 바꿔 가며 이어 붙이지 않는다.

## 6. 막힌 것과 이유

| 출처 | 결과 |
| --- | --- |
| u.gg 라이브 API | **403** — Cloudflare. 아카이브 경유로 우회 |
| League of Graphs | **403** |
| op.gg 라이브 | 패치 선택 기능 자체가 없음 (오늘/7일/한달) |
| lolalytics 과거 패치 | 페이지는 오는데 **데이터가 없는 껍데기**(48,836 B 동일) |
| lolalytics 아카이브 | 스냅샷 305개 있으나 **SPA 껍데기** |
| mobalytics | 403 |
| Wayback availability API | 짧은 시간에 몰아 치면 **429**. 간격을 둬야 한다 |

아카이브가 간헐적으로 일시 장애(`Temporarily Offline`)를 낸다. 응답이 11,832 B 로 오면 그것이다. 데이터가 없는 것과 구분해야 한다 — 실제로 한 번 오판할 뻔했다.

**619 B 는 봇 차단이다 (2026-09-01 확인).** 하루에 많이 두드리면 아카이브가
`suspected abusive bot traffic` 이라는 619 B 짜리 안내를 돌려준다. 재시도로는
안 풀린다 — 5회 × replay 형식 2종을 다 써도 같은 응답이다. **간격을 두거나
날을 넘겨야 한다.** 일시 장애(11,832 B)나 요청 제한(`429`)과 다른 것이다.

| 응답 | 뜻 | 할 일 |
| --- | --- | --- |
| 11,832 B | 일시 장애 | 간격을 두고 다시 |
| **619 B** | **봇 차단** | **그날은 그만둔다. 재시도로 안 풀린다** |
| `429` | 요청 제한 | 간격을 늘린다 |
| 0 B | 그 replay 형식만 응답을 못 한다 | `id_` → `if_` |

### 중국 솔랭은 제외한다 — 그리고 결과에 명시한다

텐센트가 중국 리그오브레전드를 따로 운영하고 라이엇 API 로 열어 주지 않는다. 그래서 **서구 통계 사이트에는 중국이 구조적으로 없다.** LoLalytics 도 자기 설명에 "global data coverage (**excluding Chinese server**)" 라고 적어 둔다.

중국 사이트(`101英雄联盟攻略中心`, `搜联盟` 등)에는 있다. **그래도 합치지 않는다.**

| 이유 | |
| --- | --- |
| **출처를 섞는다** | 집계 방식·티어 구분·표본 기준이 u.gg 와 다를 게 확실한데 얼마나 다른지 알 수 없다 |
| **가중치를 모른다** | u.gg 의 `world` 가 지역을 어떻게 가중하는지 모른다. 거기에 중국을 얹으면 **라이엇 시각에 가까워지는 게 아니라 제3의 값이 된다** |
| **과거 데이터가 더 부족하다** | 중국 사이트는 아카이브 커버리지가 더 나쁘다. 양쪽 다 있는 패치만 쓰면 **표본이 오히려 준다** |
| **중국 프로는 이미 있다** | Oracle's Elixir 에서 **LPL 이 가장 큰 리그**다. 빠진 것은 중국 *솔랭* 뿐이다 |

이 선택이 예측 정확도의 상한을 만든다. 라이엇이 보는 신호의 일부가 우리 입력에 없다. 그래도 그것은 **알고 있는 한계**다 — 억지로 합치면 모르는 한계가 되고 그쪽이 더 위험하다.

한계를 측정 가능한 형태로 다룬다. 예측이 빗나간 챔피언이 중국에서 선호되는 챔피언에 몰리는지 확인한다.

- 몰린다 → "중국 데이터 부재로 설명 못 한 부분이 이만큼" 이라는 정량적 발견
- 안 몰린다 → "중국 유무가 조정 예측에 큰 영향을 주지 않는다" 도 발견

어느 쪽이든 결과가 된다.
