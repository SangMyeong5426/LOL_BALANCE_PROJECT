# 정답지 — 무엇이 어떻게 만들어졌나

**여기 있는 것은 「정리한 결과」이고 다시 만들면 같다는 보장이 없다.** 그래서 커밋한다([ADR-0004](../docs/adr/0004-processed-data-storage-format.md)). 어떻게 만들었는지가 값 자체만큼 중요하다.

## `directions/` — 조정 방향 라벨

챔피언 한 종이 한 패치에서 **너프됐는지 버프됐는지.**

| | |
| --- | --- |
| 규모 | **1,555종 · 52패치 — 예측 대상 전량** |
| 분포 | `adjust` 641 · `buff` 411 · `nerf` 273 · `mixed` 230 |
| 만든 방법 | **대화 중 Claude 가 패치 노트를 읽고 붙였다** |
| **API 호출** | **없다.** `ANTHROPIC_API_KEY` 를 쓴 적이 없다 |
| 채점 | Data Dragon diff 와 대조 — 채점 대상 407종, **충돌 0** ([`score-labels`](../scripts/score-labels)) |
| 기준 | [labeling-guide.md](../docs/spec/labeling-guide.md) |

**전량이라 이제 표본 편향이 없다.** 1,562종 중 1,555종에 라벨이 있고, 빠진 7종은
그 패치에 처음 나온 챔피언이다(직전 버전이 없어 방향을 물을 수 없다).

여기까지 오는 동안 패치는 **시드 고정 무작위**로 뽑았다(`label-material --sample`).
처음에는 크기가 작은 패치를 골랐다가 표본을 편향시켰고, 그 사실과 근거는
labeling-guide 에 있다. **전량을 붙인 지금도 그 기록은 지우지 않는다** — 중간
결과가 왜 그렇게 나왔는지 설명하는 것이 그 기록이다.

## `records/` — 수치 변경 기록

「무엇이 **몇에서 몇으로**」다. 방향 라벨과 같은 방식으로 대화 중 Claude 가 노트를 읽고 뽑는다.

| | |
| --- | --- |
| 규모 | **52건 · 1패치** (13.15) |
| 만든 방법 | **대화 중 Claude 가 패치 노트를 읽고 뽑았다** |
| 채점 | Data Dragon diff 와 대조 — **재현율 88.9%** ([`save-records`](../scripts/save-records)) |

### 채점 결과를 읽는 법

```
채점 대상 9건 (Data Dragon 이 아는 변경) — 맞음 8 · 놓침 1
대조 불가 44건 — 대부분 피해량이다
조용한 변경 1건 — 노트에 없다. 라이엇이 안 적고 바꿨다
→ 노트에 적힌 것은 전부 뽑았다
```

**세 갈래를 가른다.**

| | 뜻 |
| --- | --- |
| **대조 불가** | 추출에만 있다. **환각이 아니다** — 스킬 피해량은 Data Dragon 에 아예 없어서 노트에만 있는 것이 정상이고, 그것을 뽑으라고 사람이 읽는다 |
| **놓친 것** | 노트에 수치가 적혀 있는데 못 뽑았다. **이것만 실수다** |
| **조용한 변경** | Data Dragon 은 잡았는데 노트에 그 챔피언의 수치 문장이 없다. **라이엇이 안 적고 바꿨다** |

13.15 의 `Naafiri movespeed 340 → 335` 가 세 번째다. 노트에는 버그 수정 다섯 줄뿐이고 이동속도 얘기가 없다. **채점기가 양방향으로 작동한다** — 내가 놓친 것도 잡고, 라이엇이 안 적은 것도 드러낸다.

### 이것은 「남은 일」이 아니다

**한때 「예측 대상 52패치 전량을 뽑아 약 6,092건을 만든다」로 적어 뒀다. 그
계획은 이제 필요 없다.**

그때는 이 기록이 방향 라벨을 자동으로 만드는 재료였다. 그런데 그 목적은 다른
둘이 이미 달성했다.

| | |
| --- | --- |
| **CommunityDragon 도입** | 피해량·계수를 기계가 직접 읽는다([ADR-0005](../docs/adr/0005-skill-damage-data-source.md)) |
| **방향 라벨 전량** | 1,555종 · 52패치 · 커버리지 99.6% |

**그리고 이 기록은 세 과제 어디에도 안 들어간다.** 실제로 확인했다 — `arms.py`
는 `panel` · `baseline` · `retrieval` · `rules` 만 읽고, `records/` 를 읽는 것은
그것을 만들고 채점하는 도구 둘(`save-records` · `score-records`)뿐이다.

```
① 대상 · ② 방향 · ③ 효과   ←  records/ 를 안 읽는다
```

**남겨 두는 이유**는 다른 데 있다. 「노트에 적힌 수치를 사람·LLM 이 정확히
뽑을 수 있는가」의 표본이고, 채점기가 양방향으로 도는 것(내가 놓친 것도 잡고
라이엇이 안 적은 것도 드러내는 것)을 보인 증거다. **늘리면 좋지만 늘리지
않아도 결과가 안 바뀐다.**

## `../rules/proposed.jsonl` — 밸런스 기준 규칙

| | |
| --- | --- |
| 규모 | 9개 제안 → **8개 통과** |
| 만든 방법 | **대화 중 Claude 가 학습 32패치를 읽고 제안했다** (`proposed_by: conversation`) |
| **API 호출** | **없다** |
| 채점 | 평가 20패치에서 향상 1.3배 이상 ([`run-rules`](../scripts/run-rules)) |

## 그래서 「LLM arm」이 무슨 뜻인가

비교표의 `A4` · `B4` 는 `uses_llm=True` 인데, **실행할 때 API 를 부른다는 뜻이 아니다.**

```
모델이 산출물을 만드는 데 관여했다      →  uses_llm = True
그 산출물은 저장소에 텍스트로 있다      →  rules/proposed.jsonl
실행할 때는 그 텍스트를 읽어 채점만 한다 →  API 호출 없음
```

**돌아가는 LLM 파이프라인은 아직 없다.** 에이전트(A5 · A6)도 없다.
