# 리그 오브 레전드 밸런스 패치 예측

과거 패치 이력에서 **개발사의 밸런스 조정 기준을 역추출**하고, 그 기준으로 다음 패치 내용을 예측한 뒤, 실제 패치와 대조해 **적중률을 측정한다.** 그리고 **그 조정이 실제로 어떤 결과를 냈는지**까지 잰다.

```text
통계 상태  ──→  조정 행위  ──→  조정 후 결과
승률·픽률·밴율    누가·어느 방향    의도대로 갔나 · 균형에 가까워졌나
      └── 역추출 ──┘   └── 예측 ──┘   └──── 효과 측정 ────┘
```

## 결과

52패치 · 8,767행 백테스트. **시간순 분할**(`15_13` 앞뒤)이고 무작위 분할이 아니다 — 그건 미래가 과거로 샌다.

**보는 것은 솔랭 지표뿐이다** — 승률·픽률·밴율. 프로 경기 데이터는 [따로 뒀다](#솔랭-지표가-못-보는-것). 용어는 [`docs/glossary.md`](docs/glossary.md)에 정의돼 있다.

| 과제 | 최고 성적 | 기준선 | 어떻게 |
| --- | ---: | ---: | --- |
| **① 누가 조정되나** | R-정확도 **25.8%** | 14.5% | 패치 안에서 줄 세우기 |
| **② 너프인가 버프인가** | AUC **0.866** | 0.799 | 조정된 챔피언만 · 평가 234건 |
| **③ 조정이 먹혔나** | 의도대로 — 너프 **84.6%** · 버프 **75.1%** | — | 조정 안 된 챔피언을 대조군으로 |
| **③′ 균형에 가까워졌나** | 너프 **54.8%** · 버프 **64.3%** | **50.4%** | **같은 조정, 다른 지표** |

**이 격차가 결론이다.**

> **누구를 건드릴지는 공개 지표로 잘 안 갈린다. 어느 쪽으로 건드릴지는 잘 갈린다.**

**③ 을 두 줄로 적은 이유가 있다.** 「의도대로 갔나」로 보면 너프가 낫고(84.6% > 75.1%), 「균형에 가까워졌나」로 보면 버프가 낫다(64.3% > 54.8%). **아무것도 안 해도 50.4% 는 가까워지므로** 너프의 실질은 +4.4%p, 버프는 +14.0%p 다. **무엇을 재느냐가 결론을 바꾼다.**

① 은 **세 번 밀어 봤고 세 번 다 안 움직였다** — 부스팅 +0.2%p, 이력 피처 −0.2%p, **프로 경기 피처 +0.001 AUC.** ② 방향을 +0.046 올린 신호인데 여기서는 꿈쩍도 안 한다. **모델 한계가 아니라 데이터 한계다.**

어떤 규칙에도 안 걸리는 28건은 평균 승률이 **0.5000**, 너프 비율 **53.6%** 다. **밸런스 지점에 정확히 앉아 있어 공개 지표가 어느 쪽으로도 안 기운다.**

전체 비교표(26개 arm)와 검증 내역은 [`docs/results/README.md`](docs/results/README.md)에 있다.

## LLM 이 통계를 이겼는가 — **못 이겼다**

솔랭 지표만 쓰는 arm 들이다.

| arm | 방법 | AUC | 정확도 |
| --- | --- | ---: | ---: |
| **B5** | **사례 검색 + 다수결** (RAG 검색부) | **0.866** | 75.6% |
| B7 | 부스팅 트리 | 0.851 | 75.2% |
| **B4** | **LLM 규칙** | **0.836** | **77.8%** |
| B2h | 로지스틱 회귀 + 이력·역할 | 0.836 | 78.2% |
| **B6** | **사례 검색 + 판단** — 대화 중 | **0.834** | **77.8%** |
| B1 | 로지스틱 회귀 — 수준 | 0.833 | 75.6% |
| B0b | 승률 한 줄 | 0.799 | — |

**둘 다 못 이겼다.**

> **대화로 뽑은 규칙(B4)은 로지스틱 회귀와 동률이고, 검색 위에 올린 판단(B6)은 다수결(B5)에 진다.**

이기지 못했고, **못 이겼다고 적는다** — [작업 규칙](AGENTS.md)이 「통계 베이스라인 없이 LLM 성능을 주장하지 않는다」로 정해 둔 것이다.

### 검색 위에 판단을 올려 봤다 — **다수결을 못 이긴다**

`B5` 는 이웃 `k` 개를 찾아 **라벨을 다수결**할 뿐 생성 단계가 없다. 그래서 `B6` 을 만들었다 — **같은 이웃 25종**을 놓고 대화 안에서 0~100 점을 매기고 근거를 적은 뒤, 코드가 그것을 읽어 채점한다. **실행 시점 API 호출은 0회다.**

```
B5  같은 이웃 다수결   AUC 0.866   정확도 75.6%   점수 25종
B6  같은 이웃 + 판단   AUC 0.834   정확도 77.8%   점수 50종
```

**차이 −0.032, 95% [−0.058, −0.006].** 짝지어 부트스트랩 2만 회에서 0 을 안 넘는다. **줄 세우기로는 지고 정확도로는 이긴다.**

**해상도는 병목이 아니었다** — 점수 종류가 두 배가 됐는데 AUC 는 내려갔다. **판단이 검색에 닻을 내리기 때문으로 보인다**: 같은 이웃을 보므로 이웃이 틀린 곳에서 같이 틀리고, 이웃이 하나도 없는 대상(약 20%)에서는 승률·밴율만으로 판단하게 된다.

**판단자의 오염은 재서 배제했다.** 방향 라벨 1,555종을 대화 안의 Claude 가 붙였으므로, **이름과 패치만 주는 조건**을 80건 따로 돌렸다 — **AUC 0.505** 로 찍기와 구별이 안 된다. 설계 근거는 [ADR 0006](docs/adr/0006-rag-generation-and-contamination-control.md), 용어는 [glossary](docs/glossary.md#rag--판단을-올려-봤고-못-이겼다).

### 규칙은 0.807 이었다 — **판단이 아니라 해상도가 문제였다**

234행에 낸 점수가 **5종**뿐이었다. AUC 는 줄 세우기 점수라 **5칸에 몰아넣으면 칸 안에 순서가 없다.**

한쪽 근거만 걸린 행이 크기와 무관하게 `1.0`/`0.0` 으로 뭉개지고 있었다. 사전확률과 섞으니 점수가 19종으로 늘고 **0.807 → 0.836.** **규칙을 바꾼 것이 아니라 점수 내는 방식을 고쳤다.**

### 같은 진단을 사례 검색에 적용했다가 틀렸다

사례 검색도 점수가 25종뿐이라 같은 원인이라 보고 거리가중을 넣었다. **쪼개 보니 기여가 0 이었다.**

```
솔랭4 · k=25 · 다수결   0.866   ← 본 분석
솔랭4 · k=50 · 거리가중  0.860   거리가중만 켜면 오히려 내려간다
```

점수 종류는 25 → 234 로 늘었지만 AUC 는 안 올랐다. **해상도 진단은 규칙에만 맞았다.**

피처·이웃 수·가중 방식은 **학습 구간 3겹 시간순 교차검증으로 골랐다** — 평가 구간을 보고 고르면 그것이 곧 누출이다.

## 솔랭 지표가 못 보는 것

**본 분석 밖이다.** 이 프로젝트의 질문은 「**지금 솔랭 지표로** 다음 패치를 예측할 수 있는가」이고 프로 경기는 거기 안 들어간다. **그런데 빼고 나면 남는 오차가 어디에 몰려 있는지가 보인다** — 프로 픽·밴을 넣으면 **0.866 → 0.900** 이다.

### 승률 50% 미만인데 너프당한 65종

솔랭만 보면 전부 「약하니 버프」로 읽어야 하는 구간인데, **프로 픽·밴율이 4.6배 차이 난다**(0.366 vs 0.080).

```
Ryze  16_2   승률 0.483  솔랭밴 3.4%  프로밴 23.6%  프로픽 33.3%  → 너프
```

**Ryze 는 솔랭에서 지고 있었다.** 승률 48.3% 에 밴율 3.4% — 일반 플레이어는 신경도 안 쓴다. **프로 경기에서는 셋 중 하나가 뽑았다.**

**더 센 신호라서가 아니다.** 프로 밴율 단독은 AUC 0.698 로 승률(0.804)보다 **약하다.** 승률과 상관이 **0.06~0.10** 밖에 안 되는 **다른 신호**라서 보태면 오른다.

### 두 지표가 어긋난다

**조정 한 번이 솔랭과 프로 경기 양쪽에 닿는데, 챔피언마다 배분이 다르다.**

| 버프하면 | n | 솔랭 승률 | **프로 픽·밴율** |
| --- | ---: | ---: | ---: |
| **프로 단골** | 83 | +0.85%p | **+35.0%** |
| 그 외 | 244 | +0.92%p | **−0.5%** |

**솔랭 승률은 %p, 프로 픽·밴율은 자기 값 대비 비율이다.** 픽·밴율은 챔피언마다 자릿수가 달라 %p 로는 비교가 안 된다.

**솔랭에는 똑같이 닿는데 프로 경기에는 한쪽만 닿는다.** 되돌리기도 비싸다 — 프로 단골을 너프해도 픽·밴율은 **−14.6%** 만 빠진다(그 외 −23.1%). **들어오기는 쉽고 나가기는 어렵다.**

**반대로 프로 경기만 보면 솔랭이 상한다.** 너프를 직전 프로 픽·밴율 중앙값으로 갈랐다.

| 너프 후 | **높은 쪽** | 낮은 쪽 |
| --- | ---: | ---: |
| 승률 48% 미만 | **20%** | 4% |
| 이미 50% 아래인데 너프했다 | **35%** | 16% |

**50% 를 정확히 맞추는 것은 가능한 작업이 아니다.** 50% 아래로 간 것 자체를 실패로 적지 않는다 — **적는 것은 두 지표가 어긋나는 크기다.**

### 경계 — **11% 에서만 일어나고, 원인은 못 밝혔다**

**승률 낮은 38종 중 18종만 프로 단골이다.** 나머지 20종(Yuumi·Shyvana·Zed)은 프로 경기와 무관하게 약하고, **어렵다고 프로 단골인 것도 아니다** — Yasuo·Zed 는 어렵기로 유명한데 프로 픽·밴율이 0.03·0.02 다.

**원인도 확정하지 못했다.** 후보 셋 중 둘을 지웠지만(「어려운 챔피언이라서」 ❌ · 「프로가 먼저 찾아서」 ❌) 남은 하나를 **「라이엇이 프로 경기를 본다」로 적지 않는다** — 이 데이터로 알 수 있는 것이 아니다.

**① 대상에는 안 듣는다** — 같은 피처를 넣어도 AUC 0.596 → 0.597 이다. **어느 쪽인지 아는 데는 쓰이고 누구인지 아는 데는 안 쓰인다.**

검정 내역과 되돌린 판단은 [`docs/results`](docs/results/README.md#확장-분석--솔랭-지표가-못-보는-것)와 [`docs/followups.md`](docs/followups.md) 10번에 있다.

## 증명하려는 것

| # | 주장 | 상태 |
| --- | --- | --- |
| 1 | 공개 데이터만으로 조정 기준을 문서화할 수 있다 | ✅ 규칙 11개 통과 |
| 2 | 그 기준으로 다음 조정을 예측할 수 있다 | ✅ ① R-정확도 25.8% · ② AUC 0.866 |
| 3 | 조정 결과를 측정할 수 있다 | ✅ **두 지표가 다른 말을 한다** — 의도대로 84.6% / 균형 접근 54.8% |
| 4 | **어디까지 예측되고 어디부터 안 되는가** | ✅ **가장 정직한 결과** |
| 5 | LLM·RAG·Agent 가 값을 하는가 | ✅ **쟀고 둘 다 못 이겼다** — 규칙은 회귀와 동률, 검색 위의 판단은 다수결에 진다. Agent 는 아직 없다 |

### 증명하지 않는 것

- ❌ 우리가 개발사보다 밸런스를 잘 잡는다 — 판단을 **예측**하는 것이지 평가가 아니다
- ❌ 예측이 정확하다 — 정확도는 측정 대상이지 전제가 아니다
- ❌ 개발사의 내부 프로세스가 이렇다 — **관측된 패턴**일 뿐이다
- ❌ 라이엇의 조정이 옳았다·틀렸다 — 「너프했는데 승률이 올랐다」는 적어도, 「그러니 이렇게 했어야 한다」는 적지 않는다
- ❌ 이 도구로 밸런스를 대신 잡을 수 있다 — 판단 보조다

원자료는 커밋하지 않는다. 수집부터 하려면:

```bash
./scripts/fetch-ddragon      # 버전별 챔피언 스펙
./scripts/fetch-patchnotes   # 공식 위키 패치 노트
./scripts/fetch-ugg          # 솔랭 통계 (웹 아카이브 경유)
./scripts/fetch-cdragon      # 스킬 피해량
```

패널을 만들고 리포트를 낸다:

```bash
./scripts/build-panel        # 8,767행 패널
./scripts/run-report         # 26개 arm 비교표 → runs/
./scripts/check-leakage      # 누출 검사
```

검사:

```bash
ruff check . && pytest && mypy
pytest --cov              # 커버리지 92%
```

`pre-commit` 이 커밋 전에 ruff 를 돌린다. **`pytest`(215개)와 `mypy` 는 자동으로 돌지 않으므로 직접 실행한다.**

## 기술 스택

| 기술 | 용도 |
| --- | --- |
| Python 3.11 | 전반 |
| numpy · scikit-learn | **통계 베이스라인** — LLM 이 값을 하는지 비교 대상 |
| pydantic | 구조화 출력 강제 |
| beautifulsoup4 | 패치 노트 HTML 파싱 |
| sqlite (표준 라이브러리) | 패널 저장 |
| pytest · ruff · mypy · pre-commit | 코드 품질 — **테스트 215개 · 커버리지 92%** |

**의존성은 직접 import 하는 것만 선언한다.** 전이 의존성은 적지 않는다 —
`scipy` 는 `scikit-learn` 이 끌어오지만 우리가 직접 쓰지 않으므로 안 적는다.

**실행 시점에 LLM API 를 부르지 않는다.** 모델이 만든 산출물(라벨·규칙)은 저장소에 텍스트로 있고, 코드는 그것을 읽어 채점한다. 근거는 [`ground_truth/README.md`](ground_truth/README.md).

### 도입하지 않는 것

| 기술 | 사유 |
| --- | --- |
| 파인튜닝 (LoRA·SFT) | 데이터가 표에 가까워 언어 모델의 강점이 안 살아난다. **판단 근거가 안 남아** 기획 산출물이 되지 못한다 |
| 벡터 검색을 수치 조회에 | SQL 이 더 정확하고 빠르다. 벡터는 **텍스트**에만 쓴다 |
| LangChain / LangGraph | 도구 몇 개짜리 단일 루프라 오케스트레이션이 과하다 |
| FastAPI | 지금은 API 로 감쌀 이유가 없다 |

## 남은 것

**에이전트 한 칸이다.** 검색기 셋([`retrieval.py`](src/lol_balance/retrieval.py))은 완성돼 있고 `as_of` 로 미래도 막혀 있다. 사례 검색(R1)과 노트 검색(R2)은 `B6` 이 이미 쓰고, **수치 조회(R3)만 아직 호출하는 arm 이 없다** — 대화 중에 조회하려고 만든 도구라 단발 판단 구조에는 자리가 없다.

**없는 것은 그것들을 쥐고 도는 판단 루프뿐이다.** 단발 판단은 `B6` 으로 재 봤고 다수결을 못 이겼다.

미뤄 둔 것은 [`docs/followups.md`](docs/followups.md)에 있다.
